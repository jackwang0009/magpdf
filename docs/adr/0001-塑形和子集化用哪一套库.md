# ADR 0001：塑形和子集化用哪一套库

| 项 | 内容 |
|---|---|
| 状态 | **提议（草稿）**。等 P0 复盘会定（《P0 第二轮文档修订记录》C17）；定之前方案 3.4 的条文不改 |
| 日期 | 2026-11-17 |
| 影响 | 《方案》3.4（技术选型表“塑形与子集化”一行）、5.3、5.4；《开源许可与合规清单》2.1、2.2；`engine/magpdf-text` |

这一页是给做决定的人准备的：两条路各是什么、原型验证到了哪里、哪些是没有验证的。最后一节的“建议”只是建议。

## 背景

- 《方案》3.4 选的是 **HarfBuzz（含 hb-subset）**：C++ 库，Chrome、Firefox、Android 都在用，塑形和子集化在一个项目里。
- P0 的 V08（改一行字）没有接它。原型用的是三个纯 Rust 的库（`engine/magpdf-text/Cargo.toml`）：
  - 塑形：**harfrust 0.15.0**，HarfBuzz 项目自己的 Rust 移植（移植自 HarfBuzz 15.0），MIT；
  - 子集化：**subsetter 0.2.6**，typst 项目的，为往 PDF 里嵌字体做的，TrueType 和 CFF 轮廓都支持，MIT 或 Apache-2.0；
  - 读字体表和字形轮廓：**skrifa 0.42.1**，Apache-2.0 或 MIT。
- 当时这么选的原因：做原型不想先接一套 C++ 构建；另一个常见的 Rust 移植 rustybuzz 已经被维护者标成停止维护（RUSTSEC-2026-0206），`cargo deny` 过不了。
- 这样方案写的和代码用的就不是同一套。按《工程规范》第 9 节，技术选型变更要写一页 ADR：要么把原型换回 HarfBuzz，要么把方案改成 Rust 这一套。

## 原型验证到了哪里（V08 报告）

- 合成样本上 108 次改字全部成功，三级回退（用原字体、补字形、换字体）各不少于 5 例；补 10 个汉字，文件增加约 6.5 KB。样本是横排的中文和西文，用的是系统字体（宋体、黑体、仿宋、楷体、Times、Arial 等，都是 TrueType 轮廓），子集嵌入、完整嵌入、不嵌入三种都有。
- Chrome 里显示和复制验过。**没有验的**：阅读器里的搜索，Acrobat 和 WPS，真实的合同和单证。
- 用下来碰到的事：
  - subsetter 把字形重排成从 1 开始的连续编号，返回新旧对照。宽度表、ToUnicode、内容流里的字符码都得跟着换；原型里有一处漏换（子集之后仍用旧编号查宽度），重复的汉字叠在了一起，已修。
  - harfrust 和 skrifa 依赖的 read-fonts 不是同一个版本（0.46 和 0.39），依赖树里各有一份；`deny.toml` 对重复版本只告警。
  - 完整嵌入的大字体，调试版里每次改字都整份载入再子集化，慢到分钟级；发布版是 0.5–4.8 秒。要做缓存或者增量补字形，哪条路都要做。

## 两条路

| | A：按方案，HarfBuzz + hb-subset（C++） | B：沿用原型，harfrust + subsetter + skrifa（Rust） |
|---|---|---|
| 横排中文、西文、混排 | 能（成熟） | 能，原型验过（合成样本） |
| 竖排、从右到左、复杂文字 | 能（成熟） | **没有验证**。harfrust 是 HarfBuzz 塑形部分的移植，按理应该能，本项目没有试过 |
| 子集化：TrueType、CFF | 能 | TrueType 原型验过；CFF（思源黑体、思源宋体通常发布的是这一类）库的说明里写着支持，原型的样本里**一份也没有** |
| 子集化：CFF2、可变字体 | hb-subset 支持，还能把可变字体实例化 | **不知道**，要查、要试 |
| 子集之后字形编号 | 可以选保留原编号 | 重排，要换三处的编号（见上） |
| 许可 | Old MIT | MIT、MIT 或 Apache-2.0，都在白名单里 |
| 构建 | 要接一套 C++ 构建（或者预编译库），写 Rust 绑定；多一个带 `unsafe` 的绑定 crate，《工程规范》第 4 节允许出现 `unsafe` 的清单要加上它 | 只是 Cargo 依赖，没有 `unsafe`，现在就能构建 |
| 成熟度 | 很多年，大量产品在用 | harfrust 0.15、subsetter 0.2，都还没到 1.0，接口还在变（原型里已经碰到两个库的 read-fonts 版本对不上） |
| 性能、体积 | 没有量 | 没有量（发布版里补字形是秒级以内，见上） |
| 换过去的工作量 | 重写 `magpdf-text` 的 `shaping.rs`、`subset.rs`，接构建、写绑定、接许可声明；估不准，周这个量级 | 0 |

A 这一栏是照 HarfBuzz 的文档写的，本项目没有接过它；B 这一栏写“能”的是原型验过的，其余都标明了。

两条路都要做的：字体对象和子集的缓存；Acrobat、WPS 和真实样本上的验证。

## 建议

**倾向 B，带条件。** 理由：

1. v1.0 和 v1.1 的范围里没有竖排和从右到左的文字（《方案》1.3、5.5：竖排、从右到左排在 P4），A 多出来的能力暂时用不上；原型在范围内的那部分已经跑通。
2. B 没有 C++ 构建和绑定要维护。引擎服务用 Rust 的理由是内存安全（《方案》3.4）；字体文件是不可信输入（用户打开的 PDF 里嵌的字体），放在 Rust 里解析和这个理由是一致的。
3. 换回 A 是实打实的工作量，换来的是眼下用不上的能力。

**条件：进 P1 之前先验这几件，哪一件过不了，那一部分就回到 A（塑形和子集化可以分开换）：**

1. 内置的四款字体（思源黑体、思源宋体、霞鹜文楷、朱雀仿宋）和系统的五款中文字体，逐款做一遍子集化，用 Acrobat、WPS、Chrome 看显示、复制、搜索。思源两款是 CFF，要专门看。
2. 塑形的结果和 HarfBuzz 自己比：拿一批横排的中文、西文、混排文字，harfrust 的输出和 `hb-shape` 的逐字形比（编号、进距、偏移）。
3. 查清 subsetter 对 CFF2 和可变字体的支持；内置字体如果要用可变字体的版本，这一条定去留。
4. 真实的合同和单证（V08 还欠的 20 + 20 份）上重跑改字。

P4 要做竖排和从右到左的时候再评估一次：那时 harfrust 应该到 1.0 了，按上面第 2 条的办法加上这两类文字再比。

## 后果

- **选 B**：改《方案》3.4 那一行和 5.3 的“用 HarfBuzz 塑形”，《开源许可与合规清单》2.1 的 HarfBuzz 一行删掉、2.2 写上三个库；`magpdf-text` 不动。上面四件验证排进 P1 前两周。依赖还没到 1.0，升级时要重跑第 2 条的比对（值得做成一条自动的测试）。
- **选 A**：`magpdf-text` 的塑形和子集化重写；`third_party/` 多一个 HarfBuzz，构建脚本、许可声明、绑定 crate 都要加；《工程规范》第 4 节改一句。原型的 108 次改字要在新实现上重跑。
- **不定**：方案和代码继续不一致，P1 的文字组排不了计划。
