## 2. 怎么用

### 2.1 在本机跑一遍

```powershell
pwsh scripts/nightly-roundtrip.ps1 -Cli <magpdf-cli.exe> -PublicPdfium <PDFium 的 testing\resources>
```

- 不给 `-Cli` 时用 `target\release\magpdf-cli.exe`（先 `cargo build --release --locked -p magpdf-cli`）；`pdfium.dll` 用它旁边的那一份。
- 不给 `-PublicPdfium` 时只跑自制样本。真实样本的目录用 `-Corpus <目录>` 给，来源是它下面的第一级目录名（`office-word`、`design`……）。
- 三个位置也可以用环境变量给：`MAGPDF_CLI`、`MAGPDF_PUBLIC_PDFIUM`、`MAGPDF_CORPUS`。
- Windows PowerShell 5.1 和 PowerShell 7 都能跑。

输出在 `tests/out/nightly/`（不入库，每次运行先清掉上一次的）：

| 文件 | 内容 |
|---|---|
| `report.html` | 报告页面。点开看原图要连同各语料集的 `diff/` 目录一起拿走 |
| `summary.md`、`summary.json` | Markdown 摘要（流水线上会贴到这一次运行的页面上）、机器可读的摘要 |
| `baseline-candidate/<语料集>.json` | 这一次的结果，按基线的格式写出 |
| `run.json`、`timings.json` | 这一次的输入和环境、各步耗时 |
| `<语料集>/roundtrip.json`、`calibrate.json`、`ops.json`、`diff/`、`saved/` | 原始结果、没通过的页的三张图、保存结果 |

退出码：0 没有退步（或者没有基线）；2 到了报警线；3 有退步但没到报警线；1 脚本或工具出错。`-FailOn alarm` 时 3 改成 0，`-FailOn never` 时 2、3 都改成 0；`-RequireBaseline` 时缺基线算出错（流水线上用）。

要和上一晚比、而不是和入库的基线比：把上一晚产物里的 `baseline-candidate` 目录当 `-BaselineDir`。

### 2.2 更新基线

```powershell
pwsh scripts/nightly-roundtrip.ps1 -PublicPdfium <目录> -UpdateBaseline
git diff --stat tests/baselines/roundtrip
```

什么时候该更新、怎么审，见 `tests/baselines/README.md`。

### 2.3 手里只有一份 `roundtrip --json`

```powershell
python tests/corpus/tools/roundtrip_report.py --roundtrip x.json [--ops x-ops.json] [--diff-dir x-diff] `
    [--baseline tests/baselines/roundtrip/synthetic.json] --out x-report.html
```

### 2.4 流水线

合进主干并推送之后，`Nightly` 每天北京时间 02:00 跑一次，也可以在 GitHub 的 Actions 页面上手动触发（可以选什么情况算失败）。结论贴在那一次运行的摘要里；报告页面和 JSON 在产物 `roundtrip-report-<运行序号>` 里，保留 30 天，下载解压后打开 `report.html`。

## 3. 报告页面

页面最上面是一行环境（生成时间、提交、命令行工具和 PDFium 的版本、机器）和一条横幅：到了报警线是红色，有退步但没到线是黄色，没有退步是绿色，没有基线是灰色。横幅里逐条写明是哪个来源、从多少降到多少、几页新变坏。下面六节：

1. **按来源汇总（像素比对）**：每个来源一行。文件数、页数、比对页、无差异、有差异、比例（全部比对页）、有对象的比对页、其中无差异、比例（扣除无对象页）、比基线变了多少个百分点、页错误、打开失败、保存或重开失败、崩溃、超时、差异页的主要线索。每个语料集一行小计，最后一行合计（只作参考）。
2. **和基线比较**：每个来源基线的比例、这次的比例、变化，新变坏和新变好的页数，像素和操作符两项合起来的比例；然后是新变坏的页（带三张图）、操作符级新变坏的页、状态变了的文件、新变好的页、基线里有这次没跑到的文件、这次有基线里没有的文件。
3. **没通过的页**：按来源分组，每页一行。文件、页码、差异像素数、占页面的比例、最大连通区域、归因线索、操作符级结果、和基线比是新变坏还是原来就有差异、三张缩略图（原件、保存结果、差异热图）。点缩略图，打开整页大小的三张图和这一页的明细（页面尺寸、差异包围盒、往返前后的对象数、文字位置、操作符级差异的种类）。
4. **操作符级比对**：每个来源做成了多少页、没做成多少页、有操作符差异的页、其中像素无差异的页、两项都无差异的比例、五类差异的处数；像素无差异但操作符有差异的页逐页列出。
5. **崩溃、超时、打不开的文件和加载不了的页**：退出码、工具给的原因、基线里是不是也这样。
6. **这一次是怎么跑的**：各语料集的文件数、页数、语料指纹、校准轮的结果、耗时；判定阈值、超时、提交、命令行工具和 `pdfium.dll` 的 SHA-256、机器。

几个做法：

- **一个文件，没有脚本。** 样式写在页面里。“点开看大图”用的是 CSS 的 `:target`，不用 JavaScript。页面不引用任何外部地址（单元测试里查了）。
- **缩略图内嵌，原图是相对链接。** 每页三张 200 像素宽的 JPEG，直接写在页面里，所以光拿走 `report.html` 一个文件也能看到每一页差在哪；整页大小的原图是 `<语料集>/diff/` 里的 PNG，用相对路径，要整个输出目录一起拿走。最多给 300 页内嵌缩略图，超过的只给链接。这一次 44 页没通过，页面 683 KB。
- **不放文档里的文字。** 页面里只有文件的相对路径、页码和数字。两处会带出文档内容的地方去掉了：崩溃文件的错误信息里跟着的子进程标准错误；操作符级明细里的专色名和字体名（只留颜色空间的种类，字体变化写成“字体换了”）。图的文件名是命令行工具按文件路径起的，没有文档内容。
- 归因线索（颜色、渐变丢失、Type3……）是命令行工具推的，页面上写明“不是确诊”。

## 4. 口径和退步判定

口径（《P0 技术验证计划》V02、《测试计划》第 7 节），实现在 `roundtrip_model.py`：

- 比对页 = 像素判定出了结果的页（无差异 + 有差异）。原件这一页就加载不了的（页错误）、崩溃或超时的文件里的页，都不算比对页。
- 无对象页 = 无差异并且页上一个对象也没有的页，和命令行工具汇总里的 `empty_passed` 是同一个数。
- 比例（全部比对页）= 无差异 ÷ 比对页；比例（扣除无对象页）=（无差异 − 无对象页）÷（比对页 − 无对象页）。**退步判定用后一个。**
- 两项都无差异 = 像素无差异，并且操作符级五类差异都是 0。它的比例同样扣除无对象页，只在做成了操作符级比对的页里算。

退步判定：

| 情况 | 结果 | 退出码 |
|---|---|---|
| 任一来源的无差异比例比基线低 0.5 个百分点以上（《测试计划》第 7 节）；“两项都无差异”的比例同样算一次 | 到了报警线 | 2 |
| 出现基线里没有的崩溃或超时 | 到了报警线 | 2 |
| 有新变坏的页（基线里无差异，这次是有差异、页错误，或者文件崩溃了没比对到），但比例没掉过线 | 有退步，没到报警线 | 3 |
| 像素仍无差异，操作符级从没有差异变成有 | 有退步，没到报警线 | 3 |
| 基线里的文件这次没跑到；文件从正常变成打不开或保存失败；基线里有操作符级结果而这次没有；校准轮有差异 | 有退步，没到报警线 | 3 |
| 有新变好的页；有基线里没有的新文件；PDFium 库、机器、语料指纹、阈值和基线不一样 | 只提示 | 0 |

《测试计划》只写了第一行。其余几行是这一轮补的，理由：

- **崩溃和超时单独算。** 崩溃文件里的页不算比对页，从比例上看不出来，甚至会让比例升一点（崩溃的文件里原来有差异页的话）。
- **新变坏的页不到线也让退出码非 0。** `resources` 有 227 页有对象，掉 1 页是 0.44 个百分点，不到线；只看比例的话，每晚坏一页可以一直不报。真实样本上千页之后更是这样。《测试计划》对 PR 子集的要求本来就是“不能出现主干上没有的失败页”，每晚按同一个标准报出来，只是级别比报警低一级。嫌它太严可以用 `-FailOn alarm`。
- **和基线比的比例，两边都只拿基线里有、这次也有的文件算。** 真实样本是陆续收进来的；按全部文件算的话，每加一批文件比例都会变，可能平白报警，也可能盖住老文件的退步。新文件、少了的文件在页面上单独列出。
- **来源小的时候，报警线等于“坏一页就报警”。** `pixel` 只有 31 页有对象，坏一页就是 3.2 个百分点。这是规则本身的结果，没有另外处理。

## 5. 基线

- **放哪里**：`tests/baselines/roundtrip/<语料集>.json`。一个语料集一个文件：`synthetic.json`、`public-pdfium.json`，真实样本到位后是 `corpus.json`。
- **存什么**：每个文件的相对路径、来源、状态；每页的页码、像素判定、对象数、差异像素数、最大连通区域、操作符级五类差异的处数；`meta` 里是生成时间、提交、命令行工具和 PDFium 的版本、`pdfium.dll` 和命令行工具的 SHA-256、机器、阈值、渲染倍率、语料指纹。不存图，不存耗时，不存归因线索。一页一行，按来源和路径排序，`git diff` 能直接看出哪几页变了。两份加起来 74 KB。
- **基线是什么意思**：主干上认可的现状，不是目标值。原版 PDFium 写不好的页，在基线里就是“有差异”；它从有差异变成无差异是“新变好”，从无差异变成有差异才是退步。
- **什么时候更新**：改动让结果变了（修了生成器、换了默认链接的 PDFium、改了阈值），在同一个 PR 里更新；语料变了，和语料一起更新；每晚报了退步时不要为了变绿去更新。
- **怎么审**：看 `git diff` 里 `pixel` 从 `pass` 变成别的、`status` 从 `ok` 变成别的、`ops` 从 `{}` 变成有数的每一行，PR 里都要有说法；看更新那一次的报告页面第 2 节（它是和旧基线比的）；看 `meta` 里的 PDFium、机器、语料有没有变。
- **和机器有关**：没有嵌入的字体换成什么，各台机器不一样。现在入库的两份是在开发机上生成的；流水线第一次在 GitHub 上跑出来之后，如果结果不一样，用它产物里的 `baseline-candidate/` 换掉。

**结果稳不稳**：这一轮用原版 PDFium 从头到尾跑了二十来遍，一遍从 12 秒到 174 秒不等（机器忙闲差得多）。留着输出的 9 遍（两次生成基线，第 7 节里用原版库的四次，量时间留下的三遍）写出的候选基线，除了 `meta`，和入库的两份逐行相同，也就是每一页的判定、差异像素数、最大连通区域、操作符级差异处数都一样；量时间的另外 8 遍输出被后一遍盖掉了，它们的结论都是“和基线相比没有退步”。换一台机器是不是也一样，没有验（上面“和机器有关”一条）。

## 6. 样本、环境和本机结果

- 机器：开发机，AMD Ryzen 7 9800X3D（16 线程），Windows 11 专业版 10.0.26100。不是参考机 R1。
- 命令行工具：`main` @ `ff6b0ac` 的固定副本（发布版，SHA-256 `70da6963…`），配原版预编译的 PDFium `chromium/8138`（159.0.8138.0，`pdfium.dll` 的 SHA-256 `71a3e63e…`）。Python 3.12.0。
- 运行方式：`roundtrip --isolate --jobs 8 --timeout 60`，渲染倍率 2（144 dpi）；判定阈值是命令行工具默认的（通道差大于 24 算差异像素；差异像素少于页面的 0.01%，并且最大连通区域不超过 16 个像素，算无差异）。
- 样本：
  - 自制样本：`tests/corpus/synthetic/`，58 个文件、67 页，来源 `synthetic`。每份针对一种生成器缺陷，所以无差异比例低是预期中的，这个数不代表真实文件。
  - PDFium 公开测试集：`D:\tmp\v03-public\testing\resources`（`chromium/8138`，`core.autocrlf=false` 检出），346 个文件，来源按子目录分成 `public/pdfium/resources`、`pixel`、`javascript`、`xfa`。里面多是回归用例和故意损坏的文件，三分之一的页没有对象。

## 8. 跑一遍要多久

**开发机实测，量的时候有别的任务在跑。** 这台机器不是参考机 R1，同一批的别的任务一直在用它。量了两次，两次机器忙的程度不一样，结果差五倍，所以都列出来：

- 第一次（11:11 到 11:19）：每一遍开始前整机 CPU 占用都是 100%。量完之后看了一眼，占着 CPU 的是别的任务的 `magpdf-cli`、Python 脚本和 PDFium 的测试程序。
- 第二次（11:31 到 11:33）：每一遍开始前整机 CPU 占用在 69% 到 87% 之间，机器仍然不空。

## 9. 流水线和通过线

`.github/workflows/nightly.yml` 做的事：检出；拉 PDFium 预编译库（`scripts/fetch-pdfium-prebuilt.ps1`）；装 Rust 1.99.1，构建发布版 `magpdf-cli`；装 Python 3.12 和 `tests/requirements-test.txt`；跑报告工具的单元测试；取 PDFium 公开测试集（带缓存）；跑 `scripts/nightly-roundtrip.ps1 -RequireBaseline`；不管成败都上传 `tests/out/nightly`（不含保存结果 `saved/`）。逻辑都在脚本里。

**这个文件没有在 GitHub 上跑过。** 本机确认过的只有：它是合法的 YAML；它调用的 `fetch-public-corpus.ps1` 和 `nightly-roundtrip.ps1` 在同样的环境变量下跑得通（第 7 节最后一行）。没有确认的：

- 各个 action 的写法对不对（`actions/cache@v4`、`actions/upload-artifact@v4` 的排除写法、定时触发时 `inputs.fail_on` 为空的处理）。

- 发布版 `magpdf-cli` 在 GitHub 的机器上编译要多久，整个 job 要多久。超时设的是 60 分钟。

## 10. 命令行工具的输出里缺的

这一轮不改 Rust 代码，下面几样都在脚本和报告工具里绕过去了。按用处大小排：

1. **`roundtrip --json` 里看不出用的是哪一份 PDFium。** `tool.pdfium` 只有版本号，修补版和原版都是 159.0.8138.0。现在由入口脚本去算命令行工具旁边那个 `pdfium.dll` 的 SHA-256。建议 JSON 里带上实际加载的库的路径和哈希，或者构建信息。
2. **崩溃、超时的文件没有页数**（`page_count` 是 0，`pages` 是空的）。这次少比了几页，只能从基线里查；没有基线时不知道。建议父进程先读一下页数再交给子进程。
3. **崩溃文件的 `error` 里，工具自己的话后面直接接着子进程标准错误的末尾**（“；stderr：…”）。那一段可能带出文档里的东西，报告工具是按这个分隔符切掉的。建议分成两个字段。
4. **来源名跟着输入目录的名字走。** 直接放在输入目录下的文件，来源是输入目录的名字：同一批文件放在 `resources` 目录里和放在别的名字的目录里，来源不一样。`--source` 只能把全部文件归成一类。报告工具里加了前缀和根目录来源两个参数来固定名字。建议命令行工具加 `--source-prefix`。
5. **JSON 没有格式版本号。** 字段以后改了，报告工具发现不了。建议加一个 `format`。
6. **没有每个文件的内容哈希。** 语料是不是同一批，现在靠另外算的语料指纹；指纹只能说“变了”，说不出是哪个文件变了。
7. **校准轮要单独再跑一遍**，全部文件重新渲染一次，时间差不多翻倍（第 8 节）。可以在同一遍里顺带做。
8. **操作符级比对不在命令行工具里。** `ops_diff.py` 用 qpdf 读文件，和 PDFium 数页数的方式不一样，损坏的文件上页码对不上（这次 5 个文件）；17 个文件 qpdf 打不开（其中 11 个有比对页）。

## 12. 没做的和没验的

1. **流水线没有在 GitHub 上跑过**，没确认的地方见第 9 节。
2. **真实样本没有**。数字都来自自制样本和 PDFium 公开测试集，前者是专门挑缺陷造的，后者多是回归用例，都不代表用户的文件。
3. **真实样本接进来时，产物里会有文档页面的渲染图。** 没通过的页的三张图就是页面本身；《测试样本收集与脱敏规范》要求样本不上传到外部服务。现在跑的两批都是可以公开的文件，没有这个问题。真实样本接进来之前要定：只传报告页面和 JSON、不传图；或者图只留在自己的机器上。入口脚本现在没有“不出图”的开关。
4. **按特征的统计没有做。** 《测试计划》第 11 节写的是“按来源和特征的统计”，现在只有按来源。特征在各目录的 `manifest.json` 里，报告工具没有读。
5. **没有历史曲线。** 只和基线比，不和前几晚比；每晚的结果只在产物里留 30 天。
6. **PR 上没有接。** 《测试计划》要求 PR 子集不能出现主干上没有的失败页；用同一个入口脚本只跑自制样本就能做到（几秒钟），但要改 `ci.yml`，这一轮不能改（第 13 节）。
7. **只有原版 PDFium 的基线。** 默认链接的库换成 `mag/main` 时要重新生成；要同时盯两种库，各用一个 `-BaselineDir`。
8. **耗时是在开发机上、有别的任务在跑的时候量的**，不是参考机，也不是 GitHub 的机器。
9. **机器忙的时候会不会有文件超时，没有专门试。** 单个文件的超时是 60 秒；这一轮最忙的一遍（往返一步 54 秒跑完 346 个文件）也没有文件超时。真实样本里有大文件时要再看。
10. **报告页面没有发布到固定的地址**，要下载产物再打开。
11. **`scripts/*.ps1` 没有自动化测试**。

## 13. 对方案和文档的修改建议

要协调者改的共享文件：

1. `docs/P0技术验证计划.md` V14 的“进展”：改成“自制样本 58 份、清单工具、每晚的入口脚本、分类报告页面、基线和流水线文件都有了（两份 V14 报告）；流水线没有在 GitHub 上跑过，真实样本没有”。
2. `.github/workflows/ci.yml` 的 `rust` 这个 job，在“自制样本校验”后面加两步（这一轮不能改这个文件）：

   ```yaml
   - name: 报告工具的单元测试
     run: python -X dev -m unittest discover -s tests/corpus/tools -p "test_*.py"
   - name: 自制样本往返测试，和基线比（不能出现主干上没有的失败页）
     run: pwsh scripts/nightly-roundtrip.ps1 -Cli target/debug/magpdf-cli.exe -SkipCalibrate -RequireBaseline
   ```

   第二步没有试过调试版的命令行工具，加之前先在本机跑一遍。
3. `docs/工程规范.md` 第 7 节：在“每晚”那一行后面注明流水线文件是 `.github/workflows/nightly.yml`，基线的规则在 `tests/baselines/README.md`。

对文档的建议：

1. 《测试计划》第 7 节的退步判定只有“比例低 0.5 个百分点以上即报警”一句，建议补上第 4 节那张表里另外几种情况，尤其是三条：新的崩溃和超时单独算报警；新变坏的页不到线也要处理；和基线比的比例只算两边都有的文件。
