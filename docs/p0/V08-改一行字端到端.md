## 1. 目标

打通方案 5.2 的三级回退（用原字体、补字形、换字体）：HarfBuzz 塑形，子集化后以 Identity-H 的 Type0 字体加 ToUnicode 写回。计划通过线：

- 样本：中文合同 20 份、英文单证 20 份，每份改 3 处；
- 三级回退各有至少 5 例成功；
- 改后 Acrobat Reader、Chrome、WPS 显示一致，能复制、能搜索，没有乱码；
- 新增 10 个汉字时文件增加不超过 50 KB。

本轮**没有**真实合同/单证 PDF，用的是 `tests/corpus/synthetic-text/generate.py` 按上述份数合成的 20 中文 + 20 英文样本（单据口吻的短句，不是脱敏后的业务原件）。结论只对这批合成样本负责，不外推到真实扫描件或复杂排版。

## 2. 方法

### 2.1 实现

- 引擎：`engine/magpdf-text/src/edit.rs` 的 `edit_line`，按 tier1 `SetText`/`SetCharcodes` → tier2 从嵌入数据或同名系统字体补字形并重新子集 → tier3 换一款能覆盖新字符的系统字体（`font_replaced=true`）。
- 命令行：`magpdf-cli edit-line <in> --page 1 --line N --text ... -o <out> --json`。引擎修复后的正式 36×3 评测使用 release 构建 `target\\release\\magpdf-cli.exe`（约 18.9 秒）；修复前同批 108 次用的是 debug 构建，备份见 `out/v08-eval/results-before-fontfix.json`。
- 保存后由 CLI 填写 `bytes_delta = output_size - input_size`（`EditOutcome::bytes_delta` 在改页阶段仍为 `None`，按注释留给调用方在 `save` 之后计算）。

### 2.2 样本生成

- 生成器：`tests/corpus/synthetic-text/{generate,pdfgen,samples}.py`。页面两行固定原文：中文「合同甲方乙方」/「合同甲方乙方应按时付款」，英文 `Invoice No: ABC-123` / `Total amount payable`。
- 子集只包含**页面原文**用到的字符，不再把「货物验收」等替换字预写进子集（否则第 2 级会全部落成 tier1）。
- `glyph_map` 不再按 GID 去重：等线等字体里「方」(U+65B9) 与康熙部首「⽅」(U+2F45) 共用轮廓，去重后 `gmap['方']` 会 KeyError。这是本轮重修 `generate.py` 时修掉的缺陷；`GOTHIC.TTF`（Century Gothic，西文）已从中文字体表移除。
- 写出 40 份、跳过 0 份；其中 36 份 ≤ 1 MB，写入 `tests/corpus/synthetic-text/samples/`，4 份完整嵌入大文件写入 `out/v08-samples-large/`（新宋体、等线 Bold、幼圆、华文新魏）。

### 2.3 评测脚本

`tests/corpus/synthetic-text/eval_v08.py`：对每份样本从**原文件**出发独立改第 1 行（布局行号 0）三次：

| 意图级别 | 中文新文本 | 英文新文本 |
|---|---|---|
| tier1 | 原文前两字挪到末尾（`合同甲方乙方` → `甲方乙方合同`） | 前三个字母挪到末尾 |
| tier2 | 前四字换成生僻字 `饕餮貔貅`（子集里没有，宋/仿/黑等完整字体里有） | `Invoice No: xyz-987`（原子集通常没有 x/y/z/9/8/7） |
| tier3 | 韩文 `한글테스트행`（中文字体覆盖不了） | 汉字 `货物验收编号`（西文字体覆盖不了） |

成功定义：进程退出码 0 **且** 重开提取的行文本 `contains_new_text`。通过线里「各级至少 5 例」按**实际落入的级别**统计成功次数（同时给出与意图级别一致的对照数字）。

完整嵌入的 4 个大文件在 debug CLI 下单次改写可达数分钟（幼圆约 5 分钟/次），因此不计入 108 次正式改写。这 4 份已另行用 release CLI 做只调序、补 10 个汉字、韩文换字体，全部秒级成功（见 4.7）。正式评测机器结果：`out/v08-eval/results.json`（修复后）；修复前备份：`out/v08-eval/results-before-fontfix.json`。

### 4.5 失败原因（0 次）

本轮 `failures` 为空。上一轮的 14 次提取不符已随样本生成修复：

- 中文调序错序/叠字：子集后误用完整字体旧 GID 查 `/W`，「乙」宽度变成 0。重生样本后 `zh-fang-tier1` 原文抽出「合同甲方乙方」，调序抽出「甲方乙方合同」。
- 西文空格变成 NUL：ToUnicode last-wins 把空格 GID 写成 NBSP（U+00A0），`SetText` 反查 U+0020 失败写成 CID 0。改为优先 ASCII / CJK 统一汉字后，`Invoice No: xyz-987` 含正常空格。

## 6. 遗留问题

1. 官方阅读器：Chrome 里原先三份代表页，以及修复后 6 份 Times / Arial / Courier / Palatino Invoice 产物，显示与复制已验证（见 §4.6、§4.8 与 `out/v08-readers-official/`）。搜索仍未做成：本机这版查看器工具栏/「更多操作」无搜索按钮，Ctrl+F 打不开可读取命中的查找栏。无头 Chrome 仍是空白。Acrobat / WPS 仍未安装（本轮再次核过注册表和常见路径）。
2. 完整嵌入大字体在 debug `edit-line` 下极慢（幼圆单次约 5 分钟，正式 36×3 因此仍跳过 4 份）。release CLI 下这 4 份的只调序、补 10 字、韩文换字体均在 0.5–4.8 秒内成功（见 4.7）。补 10 字因完整字体已含目标字而走 tier1；韩文走 tier3。若把大样本纳入正式 36×3，仍建议用 release 并逐份限时；debug 构建不宜再用来跑这些文件。FontFace 解析与子集缓存仍值得做，以降低 debug / 更大文档上的开销。
3. ~~原文重复汉字导致 tier1 调序错序/叠字~~ **已修复**：根因是子集后仍用完整字体的旧 GID 查 /W，「乙」宽度变成 0，后一个「方」画在「乙」上。重生样本后 `zh-fang-tier1` 原文抽出「合同甲方乙方」，调序抽出「甲方乙方合同」，字形 x 序为 [0,1,2,3,4,5]。
4. ~~西文空格被提取成 NUL~~ **已修复**：ToUnicode 对共享 GID last-wins 把 U+0020 写成 NBSP（U+00A0），SetText 反查空格失败而写成 CID 0。现改为优先 ASCII / CJK 统一汉字（`pdfgen.invert_to_unicode`、`preferred_codepoint`）。烟雾测试中 `Invoice No: xyz-987` 提取含正常空格。
5. ~~未嵌入样本即使用原字符调序也会走 tier2 并重新嵌入子集，文件体积陡降~~ **已修，并已用 release 重跑 108 次正式评测**：未嵌入时若能匹配到同名系统字体，即用其 cmap 做第 1 级。`zh-kai-tier2-system` 只调序现为 tier1、Δ+186 B（修复前正式评测是 tier2、Δ−262396 B）；隶书、华文中宋/宋体以及 Calibri/Verdana/Segoe/Consolas 调序同样留在 tier1。未嵌入中文在补 `饕餮貔貅` 时若系统字体已覆盖，也走 tier1（约 +195–198 B），不再整包子集。编码用页面 `glyph_width` 区分 Identity-H 与简单编码；只为需要的字符建表。产品上若仍要把「重写字体流」提示出来，只应在真正走了第 2/3 级时提示。
6. ~~部分英文字体写入拉丁新字时直接落到 tier3 换字体~~ **已修，并已用 release 重跑 108 次正式评测**：同名匹配补上家族名，并去掉 `PSMT`/`MT`/`PS` 这类 PostScript 后缀，让 PDF 的 `TimesNewRoman`/`CourierNew`/`PalatinoLinotype`/`Arial` 能对上系统字体。写入 `Invoice No: xyz-987` 时 Times/Arial/Courier/Palatino 现为 tier2 且 `font_replaced=false`（例如 Times Δ+17990 B、Arial Δ+15107 B），抽出含正常空格；修复前这些样本落入 tier3 并换字体。
7. 尚未用真实 20+20 合同/单证回归。本轮在工作区 `tests/corpus`（含 v08 工作树与主仓）里仍只有合成样本，没有真实合同/单证 PDF。
8. 合成西文样本遗留：至少 `en-arial-tier2-system` 和 `en-pala-tier2-system` 的原文「Invoice No: ABC-123」与未改行「Total amount payable」字距不均匀；Arial 源文件还多了一页重复内容（两页渲染哈希相同）。编辑行 `Invoice No: xyz-987` 本身显示正常，对照源文件后确认字距问题不是这次 tier2 写入引入的。若要样本更干净，应再查 `generate.py` / `pdfgen.py` 的宽度表。
9. 意图 tier2 在部分样本上会落到 tier1：未嵌入且系统字体已覆盖新字（楷体等补 `饕餮貔貅`），或原字体/完整嵌入字体已含目标字母或汉字（Arial Bold 等写 Invoice、4 份大样本补 10 字）。这是更省事的路径，不是失败；若产品要以「补字形」为提示条件，应按实际级别而不是意图级别判断。

## 7. 对方案的修改建议

1. 方案 5.2 写清：未嵌入且能匹配同名系统字体时，只调序（以及系统字体已覆盖的新字）走第 1 级，不再重做子集；只有真正补字形或换字体才改写字体流。UI 提示应按实际级别，而不是只看 `font_replaced`。
2. 完整嵌入的大字体应避免每次把整份 FontFile 载入后当场子集；优先增量补 GID，或对已解析的 `FontFace` 做进程内缓存。
3. ToUnicode 与空格：西文空格不要写成 CID 对应 U+0000；重复汉字的 CID 与 ToUnicode 必须一对一保持阅读顺序。
4. 样本规范：合成集可以继续用，但 V08 关闭前应补真实合同/提单（按《测试样本收集与脱敏规范》），阅读器目检至少覆盖子集、完整嵌入、未嵌入、换字体各若干份。
5. 评测工具：对 `out/v08-samples-large` 应用 release CLI，并设超时、增量写结果。只调序、补 10 字、韩文换字体在 release 下均已是秒级；若把大样本纳入正式 36×3，仍应逐份限时，并用 release 构建。
