## 1. 目标

原版 PDFium 的内容流生成器（`core/fpdfapi/edit/cpdf_pagecontentgenerator.cpp`）在写回页面对象时丢失信息。按 V02 报告 6.1 的顺序，第一轮修三项：

- **a.** `Tc`（字符间距）、`Tw`（词间距）写出；`TJ` 字距补回归测试（上游已修好）。
- **b.** 颜色空间：灰度、CMYK、ICCBased、Separation、DeviceN、Indexed、Lab、Pattern 写出正确的颜色操作符，不退化为 DeviceRGB 或 Alternate。
- **c.** 文字裁剪模式 `Tr` 4–7：同一 `BT…ET` 的字形合起来作为裁剪区域。

本轮完成 a；d 只完成"不再留下未闭合块"的一半，文字本身仍不保留；b、c 未开始。 b、c 在第二轮完成（见 4.5、4.6）。

## 2. 方法

- **像素比对**：`magpdf-cli roundtrip`（V02 的判定规则：2 倍分辨率，通道差 > 24 算差异像素，差异面积 < 0.01% 且最大连通区域 ≤ 16 像素算无差异）。
- **操作符级比对**（本轮新增，`tests/corpus/tools/ops_diff.py`）：像素比对看不出颜色空间丢失（PDFium 把 CMYK、灰度换算成等价 RGB），也看不出叠印参数丢失。工具把原件和往返结果按页解析内容流，以"绘制事件"（每个路径绘制、文字输出、`Do`、`sh`、内联图像）为对齐单位，比较：
  - 颜色：当前填充/描边颜色及其色彩空间类型（`g/G/rg/RG/k/K/cs/CS/sc/SC/scn/SCN`）；
  - 文字状态：`Tc/Tw/Tz/TL/Ts/Tr` 和所用字体的类型与名称；
  - ExtGState：`ca/CA/BM/SMask/OP/op/OPM`；
  - 事件数量（缺失、多出）。

  输出每页差异摘要和按来源汇总的表。它同时是修复 b 的判定依据：修好后，颜色差异数应降到 0，而不是靠像素比对"看不出来"。

### 4.2 修复项 a：`Tc`、`Tw`

**问题**：`ProcessText()` 只写 `Tm`、`Tf`、`Tr` 和一个 `TJ`，文字状态里的 `Tc`、`Tw` 不写出；解析时它们没有被折算进字形位置，所以写回后字距、词距全部变成 0，后面的字形依次偏移。

**核实**（对照解析器，避免重复修已经折进去的参数）：

- `Tz`：`CPDF_AllStates::mutable_text_state()` 的水平缩放进入文字矩阵，`GetTextMatrix()` 已带上，写回保留。
- `Ts`（rise）：解析时直接加进 `text_pos_.y`（`cpdf_allstates.cpp`），写回保留。
- `TL`：生成器总是写显式 `Tm`，不使用 `T*`、`'`、`"`，leading 不影响显示。
- 所以只有 `Tc`、`Tw` 真的丢。

**改法**：在 `ProcessText()` 的 `BT` 块里、`Tf` 之后写非零的 `Tc`、`Tw`：

```cpp
float char_space = pTextObj->text_state().GetCharSpace();
if (char_space != 0.0f) {
  WriteFloat(*buf, char_space) << " Tc ";
}
float word_space = pTextObj->text_state().GetWordSpace();
if (word_space != 0.0f) {
  WriteFloat(*buf, word_space) << " Tw ";
}
```

安全性依据：文字状态属于图形状态。`ProcessGraphics()` 已经给每个对象套 `q … Q`（`EndProcessGraphics()` 写 `Q`），`q/Q` 保存并恢复文字状态，所以在 `BT…ET` 内写 `Tc`/`Tw` 不会泄漏给后面的对象。只写非默认值，符合方案 2.3 第 1 条"只写状态变化"。

不写 `0 Tc`/`0 Tw` 的正确性：文字对象的状态是解析阶段累加出来的，和脏流起点处的运行时状态一致（前面的流不改动、原样保留），所以"解析值是 0"等价于"运行时也是 0"。

**单元测试**：`CPDFPageContentGeneratorTest.ProcessTextCharAndWordSpace`，覆盖非默认值（断言 ` 10 Tf .5 Tc -1.25 Tw 0 Tr `、仍以 `q` 开头并以 `Q\n` 结尾）和默认值（不写 `Tc`/`Tw`）。

**效果**：

| synthetic 差异页 / 字距文字位置提示 | 29 / 5 | **26 / 2** |

### 4.3 修复项 d（部分）：Type3 字体不再留下未闭合的 `q`、`BT`

**问题**：`ProcessText()` 先写 `q` 和 `BT`，之后才判断字体类型；遇到 Type3 直接 `return`，于是这条流里多出一个未闭合的 `q` 和一个未闭合的 `BT`，同一内容流里后面的对象全部落进这个文字块（方案 2.1 记录的缺陷）。

**改法**：把字体类型判断提到最前，写不出字体字典的字体（Type3）在写出任何操作符之前就返回，对象整体跳过。文字仍然不保留（序列化 Type3 字形的内容流是后续工作），但内容流保持结构完整，后面的对象不受影响。

**验证**（用 `pikepdf` 统计保存后内容流里 `q/Q`、`BT/ET` 的平衡）：

| 样本 | 修前 | 修后 |
|---|---|---|
| `text-type3.pdf` | 未闭合 `q` 1 个、`BT` 1 个 | 0、0 |
| `text-type3-multistream.pdf` | 未闭合 `q` 1 个、`BT` 1 个 | 0、0 |

**说明**：这两个样本的像素结果不变（Type3 文字本来就被丢弃，且位于流的末尾），公开集的 Type3 差异页数量也不变，所以本项在汇总表里体现为"结构修复"而不是"无差异页增加"。缺口：没有单元测试。构造一个能通过 `CPDF_DocPageData::GetFont()` 的最小 Type3 字体字典在测试里直接崩溃（缺少 CharProcs 等必需项），需要专门的测试夹具，留给下一轮。

### 4.5 修复项 b：颜色按自身颜色空间写回

**问题**：`WriteColorToStream()` 只认 RGB/灰度，一律用 `GetRGB()` 换算后写 `rg`/`RG`；CalGray/CalRGB/Lab/ICCBased/Separation/DeviceN/Indexed/Pattern 全部退化为等效 RGB。像素常常不变，但操作符级颜色已变（基线 synthetic 259 处、公开集 1303 处）。

**改法**（`CPDF_PageContentGenerator`，另见提交说明）：

- 设备灰度/RGB/CMYK：按原始分量写 `g/G`、`rg/RG`、`k/K`，不再经过 `GetRGB()`。
- CalGray/CalRGB/Lab/ICCBased：`/Name cs` + 分量 + `sc`/`SC`。
- Separation/DeviceN/Indexed：`/Name cs` + 分量 + `scn`/`SCN`。
- Pattern：`/CSName cs` + 底色分量（仅无色 tiling 图案，分量数取底色空间）+ `/PatternName scn`。
- 资源名：优先复用解析时记录的资源名；设备名（`DeviceGray/DeviceRGB/DeviceCMYK`，有 Default* 时重解析）与 `Pattern` 直接用；否则把颜色空间数组实现为新的 `FXC<n>` 资源、图案为 `FXP<n>`。解析不到或族未知时回退到 RGB（与修前行为一致）。
- 为此解析器侧补了三处：`CPDF_Color::GetColorSpace()/GetComponents()`、`CPDF_ColorSpace::GetArray()/GetMinMax`、`CPDF_ColorState` 记录填充/描边的颜色空间名；并修了 `GetCurrentColorSpaceName()` 把 `CalGray/CalRGB/Lab` 族名写回资源名、导致 `cs` 无法解析的 bug（描边同理），以及把图案资源名传进 `SetFillPattern/SetStrokePattern`。
- Separation `/None`：**如实写出**（`/CSn cs 1 scn`），不是跳过。§8 原文写“/None 不画”是指渲染结果不着墨；实测跳过会在原先空白处画出黑块（像素取样：原文件 `/None` 块白色，跳过写回后变黑），而如实写回后重解析仍是 `/None` 空间、不着墨，ops_diff 为 0。

**单元测试**：`CPDFPageContentGeneratorTest.ProcessColorSpaces`（Lab 复用资源名 `CSlab`、DeviceCMYK 填充/描边、DeviceGray 填充、Separation `/None` 实现为 `/FXC1`）。

**效果**：
| 指标 | 修前（基线） | 修后 |
|---|---|---|
| synthetic 颜色差异 | 259 处 / 62 页 | **0 处 / 0 页** |
| 公开集颜色差异 | 1303 处 / 171 页 | **0 处 / 0 页** |
| synthetic 无差异页 | 38/67 | **54/67（80.6%）** |
| 公开集无差异页 | 373/388 | **384/388（99.0%）** |

其余差异未变：synthetic 文字 0、ExtGState 5、事件缺失 19（渐变 6 为已知缺口）；公开集文字 4、ExtGState 3、事件缺失 6。`pdfium_unittests --gtest_filter=CPDFPageContentGeneratorTest.*` 11/11 通过（含新增测试）。

### 4.6 修复项 c：文字裁剪 Tr 4–7 保持打开

**问题**：`ProcessText()` 给每个文字对象单独套 `q…Q`，`BT…ET` 一结束 `q` 就关上，于是 Tr 4–7 建立的文字裁剪对后续对象失效（形状按未裁剪画出）；同一个 `BT…ET` 里的两个 `Tj` 还被拆成两个 `BT…ET`，渲染器按 `BT…ET` 求交，把本应取并集的字形变成了取交集。

**改法**（`CPDF_PageContentGenerator`）：

- `GenerateModifiedStreams` 改为按下标循环，维护一个打开的裁剪组栈。遇到连续的裁剪模式文字时，收集整段 run，取 run 之后第一个仍在同一流的活动对象，用它的裁剪路径里的文字组与 run 的签名（字体、字号、文字矩阵、位置、对象矩阵、文字状态 CTM、渲染模式、字符码、字距、字符位置、线宽/线帽/线接/虚线）按值匹配；从最长匹配开始，逐个去掉不能成组的前导组（不可写字体、带内容标记、路径裁剪不一致）重试。
- 成组的部分用 `WriteTextClipGroup()` 写出：一个 `q`、首个文字的路径裁剪、每个原 `BT…ET` 一个 `BT…ET`（每文字的图形状态写在 `BT` 内，与原文件一致；第 2 个起的文字强制写 `Tm`），`q` 留待后续对象不再需要该裁剪时再关。成组前的文字逐个照旧写出；没有对象使用该裁剪的 run 照旧单独写出。
- 为此把 `ProcessText()` 拆为 `CanWriteText()` / `WriteTextContent()`（不含 `BT/ET/q/Q`），把 `ProcessGraphics()` 拆为 `WriteGraphicsState()`（不含 `q/Q`，可单独控制是否写路径裁剪）+ `WriteClipPath()`；`ProcessPageObjects()`（单元测试路径）不动。裁剪不能跨内容流，换流时先关掉已打开的组。
- 分组只在解析器记录了裁剪时触发；没有文字裁剪的文件走与修前相同的路径。

**单元测试**：`CPDFPageContentGeneratorTest.ProcessTextClipGroup`（一个 `BT` 含两个文字 → 一个 `BT…ET` 且 `q` 不关；`{1,1}` → 同一个 `q` 下两个 `BT…ET`；两文字共用同一字体资源、第二个文字有自己的 `Tm`）。

**效果**：
| 指标 | 修前 | 修后 |
|---|---|---|
| `text-clip-modes.pdf` 像素差异 | 128469 px（53.5%，整页） | **4370 px（1.8%）** |
| `text-clip-modes.pdf` 像素差异范围 | bbox [0,20,600,370] | **bbox [43,50,232,101]，仅 CLIP4 渐变区** |
| ops_diff 剪裁 text（synthetic） | 4 处（`text-clip-modes`） | **0 处** |
| ops_diff 颜色（synthetic/公开集） | 0 / 0 | **0 / 0（未退化）** |

剩余的 4370 px 全在 CLIP4 渐变区域：该渐变是 shading 对象，生成器仍不写出（已知缺口，不在本项范围）；CLIP5/6/7 与底部紫带的裁剪区像素已与原文件一致。`text-clip-modes` 的 `text_clip` 提示仍在，因为像素提示是粗粒度标签（文件含裁剪文字且仍有像素差异即标出），以像素 bbox 与 ops_diff 剪裁列为准。

**ops_diff.py 的剪裁细分**（§8 第 6 项）：`ops_diff.py` 现跟踪当前裁剪——路径裁剪（`W`/`W*` + 当前路径）与文字裁剪（`BT…ET` 内 Tr 4–7 的文字：字体、字号、Tm、字节、Tr），每事件附快照，逐对比较，单独计 `clip` 列（`path`/`text`）。基线 synthetic 剪裁 1504（文字 4 + 路径 1500）、公开集 331；修后 synthetic 1500、公开集 331（逐页相同）。其中路径 1500 处是**此前已有的缺口**：`struct-many-objects-clip.pdf` 用一个 `q … re W n` 给整页 1500 个小矩形共用裁剪，生成器按对象逐个写 `q…Q` 时没有把该页级裁剪写出（像素无差异，因为矩形本就在裁剪区内）；不在本轮范围，留待后续处理。

`pdfium_unittests --gtest_filter=CPDFPageContentGeneratorTest.*` 12/12 通过（含新增的 `ProcessTextClipGroup` 与 `ProcessColorSpaces`）。

## 5. 新发现

1. **文字对象字体为空时生成器静默换成 Helvetica**。`ProcessText()` 里 `font` 为空就 `CPDF_Font::GetStockFont(document_, "Helvetica")`。`hello_world_2_pages_split_streams.pdf` 第 2 页触发：该页字体在解析阶段就没有建立起来（内联字体字典或资源异常），写回后文字用 Helvetica 显示，且字形编码可能对不上。这属于**解析阶段**的信息缺失，方案 2.1 的退路判定要用到，建议单独建一个缺陷条目跟踪，并确认是解析器丢弃还是该页字体字典本身不规范。
2. **子集字体名在写回时被重命名**（`bug_781804.pdf`）。像素无差异、可搜索性也不受影响（ToUnicode 仍在），但与"未修改的对象原样保留"有出入，V17 的对照里应算作操作符级差异的一类。
3. **颜色空间丢失的量级比像素比对显示的大得多**：synthetic 33 页、公开集 160 页像素一致但颜色操作符已变；这直接支撑修复 b 的必要性和判定方法。
4. 内联图像写回后消失（synthetic `struct-inline-image.pdf`，6 处）——`ProcessImage()` 遇到 `pImage->IsInline()` 直接 `return`，与 V02 4.6 一致。
