# V02 原版 PDFium 往返基线（公开测试集首轮）

状态：草稿（首轮，仅公开测试集）。对应《P0 技术验证计划》3.2 V02、《方案》2.1 / 13.2。

## 1. 目标

在不改动 PDFium 的前提下，量化"解析 → 标记全部对象为已修改 → 重新生成内容流 → 保存 → 重开渲染"这一往返过程造成的画面差异，按来源和缺陷类型统计影响页数，作为 V03 修复顺序的依据；同时交付可在 CI 反复运行的比对工具（V14 的比对部分）。

## 2. 方法

### 2.1 工具

新增 `magpdf-cli roundtrip <文件或目录>`，核心逻辑在 `magpdf-engine::roundtrip`，命令行只负责枚举文件、子进程隔离、落盘和表格输出。每个文件的处理流程：

1. 用原始字节打开文档；逐页加载，统计对象（文字、路径、图像、渐变、Form，透明对象数，Type3 文字数，文字裁剪模式数，字符数）。
2. 对每页的全部顶层对象调用 `FPDFPageObj_TransformF`（单位矩阵，即 `mark_modified()`），再调用 `FPDFPage_GenerateContent`。
3. `FPDF_SaveAsCopy`（`FPDF_NO_INCREMENTAL`）保存到内存。
4. 用一份未被触碰的原始字节副本重新打开 A，用保存结果打开 B；两边都以 scale 2.0（144 dpi）渲染。
5. 用 `magpdf_engine::compare::compare` 比对：任一通道差值大于 24 记为差异像素；差异像素少于页面面积 0.01% 且最大 4 连通差异区不超过 16 像素，判"无差异"（计划原文阈值，校准后未调整）。
6. 有差异的页额外记录：B 的对象统计、字符位置偏移（逐字符比较 A/B 字符框原点，偏移超过 0.1 pt 记为"移动"）、填充/描边颜色变化的对象数，并据此给出自动归因线索（渐变丢失、图像丢失、Type3、对象数变化、文字变化/移动、颜色、透明、文字裁剪、待人工归类）。线索只是人工归类的起点，报告里的归因以人工复核为准。

输出：stdout 按来源分表（文件数、打开失败、保存/重开失败、崩溃、超时、页数、比对页、无差异、比例、其中无对象页、页错误、主要归因）；`--json` 写完整逐页记录；`--diff-dir` 为每个差异页写 A、B 和热力图 PNG（红 = 超阈值差异，黄 = 阈值内差异，灰 = 原图淡化）；`--save-dir` 写保存后的 PDF 供人工查看内容流；`--calibrate` 跳过标记与重生成，只做"打开 → 保存 → 重开 → 渲染比对"，用来校准噪声；`--isolate` 为每个文件启动独立子进程（默认 60 s 超时），崩溃和超时记录为该文件的状态而不是整轮失败，CI 必须带此参数。

### 2.2 `mark_modified()` 是否真的触发重写

公共 API 没有"标记为已修改"的直接入口。`FPDFPageObj_TransformF` 调用 `CPDF_PageObject::Transform`，后者对文字、路径、图像、Form、渐变五类对象都会 `SetDirty(true)`；`FPDFPage_GenerateContent` 只重写含脏对象的内容流（`GenerateModifiedStreams`）。验证分三层：

- 源码：上述调用链在 chromium/8138 源码中逐一确认。
- 单元测试：`pdfium-sys` 的 `mark_modified_rewrites_content_stream` 用手工构造的 PDF 做 A/B——不标记直接 `GenerateContent` + 保存，内容流字节与原文完全一致；标记后保存，内容流变成生成器格式（`q` 开头、`Q` 结尾，含 `rg`/`re`/`f`）。保存时 `CPDF_Creator` 会对无过滤器的流做 Flate 压缩，测试用 `flate2` 解压后比较。
- 真实文件：`--save-dir` 保存的公开测试集文件，内容流均为生成器格式（`q\n0 0 0 RG 0 0 0 rg 1 w 0 J 0 j\n/FXE1 gs q … Q\nQ\n`）。

逐页在运行时证明"这一页确实被重写"做不到：公共 API 读不到内容流字节，保存后又被重新压缩。因此工具只保证调用链正确，不在结果里逐页标注。

### 2.3 噪声校准

同一份文件、同一份 PDFium 库，`--calibrate` 下所有可比对页 100% 无差异（见 4.1），说明打开/保存/重开本身不引入像素差异，阈值无需调整。

`hello_world_2_pages_split_streams.pdf`：两页的 `/Contents` 指向同一个间接数组（两条流）。第一页重生成时，生成器就地改写了这两条共享流，并把新资源名（`/FXF1`、`/FXF2`、`/FXE1`）只写进第一页的资源字典；随后加载第二页时，解析到的已经是改写后的流，`Tf` 找不到字体，PDFium 回退到内置 Helvetica，第二页的重生成又为它新建了一个 Helvetica 字体字典。结果第二页第一行从 Times-Roman 变成 Helvetica（字符位置偏移 ≤ 2.0 pt 是字宽差异的副作用）。第一页渲染一致。这不是字距问题，是"共享内容流在修改前没有去共享（copy-on-write）"：生成器和我们的调用方式各占一半责任，真实文档里多页共用整条内容流不多见，但 Form XObject 被多页引用很常见，P1 做 Form 内部编辑时必须先处理。

### 4.7 性能与体积

- 4 个并发子进程，346 个文件总耗时 4.1 s（校准轮 4.7 s）；逐文件耗时合计 6.85 s，最慢 `bug_1646.pdf` 2.0 s（64×64 pt 的页，A/B 渲染各约 1 s）。
- 各阶段合计：渲染 A 2.05 s、渲染 B 1.93 s、保存 1.07 s、比对 0.43 s、标记+重生成 0.36 s、分析 < 0.01 s。渲染是主要成本；标记与重生成每页中位数 0 ms，最大 10 ms。
- 文件体积：317 个成功保存的文件，原始 2,850,576 字节 → 保存后 2,527,253 字节（`NO_INCREMENTAL` 重写 + 重新压缩）。

## 5. 结论

1. 工具可用：校准轮 100% 无差异，判定阈值按计划原文不变；崩溃、超时、打开失败都能被隔离并单列，CI 可直接用 `--isolate`。
2. 原版 PDFium 的生成器在公开测试集上，有对象的页 94.2% 往返无差异；差异全部能归到已知缺陷，没有"待人工归类"。
3. 缺陷清单与《方案》2.1 基本一致，两处要改：`TJ` 字距在 chromium/8138 已修复（只剩 `Tc`/`Tw`）；内联图像会整个丢失（新增）。另发现两项：文字裁剪模式整体丢失（画面破坏最大）、多页共享内容流被就地改写。
4. 公开测试集不能回答"办公文档 ≥ 98%"这个问题：三分之一的页没有对象，有对象的页大多只有几个对象。办公、设计类真实样本的基线要等 V14 样本到位后再跑一轮，本工具不需要改动。

## 6. 遗留问题

### 6.1 对 V03 修复顺序的建议

按"影响页数 × 画面破坏程度"，结合办公文档的实际用法：

1. `Tc`/`Tw` 写出（办公导出高频；`TJ` 已由上游修复，只需补测试）。
2. 颜色空间：CMYK、ICCBased、Pattern、Separation、Indexed 写出正确操作符（公开集里最多的一类，设计类文档必中；ICCBased 灰/RGB 在办公导出里也常见）。
3. 文字裁剪模式（`Tr` 4–7）：合成样本证实裁剪整体丢失，一旦出现就是整页破坏。
4. Type3：出现即丢字，且留下残缺的 `q`/`BT`。
5. ExtGState 软蒙版、叠印参数。
6. 渐变 `sh` 和内联图像：两者都是"对象整个消失"。
7. 共享内容流 copy-on-write：生成前检查流对象的引用计数或由上层先拆分。
8. 层级（新对象写进末尾新流、跨流调整不生效）：V02 的往返不改层级，覆盖不到，需要 V03 自己的编辑测试（计划 3.2 V13 第 2 条那种"随机修改 5% 对象"的测试同样适用）。

### 6.2 工具问题

- 页加载失败的错误码显示为 `Other(0)`：`FPDF_LoadPage` 失败后 `FPDF_GetLastError` 返回 0，信息量为零，后续可在 `pdfium-sys` 里为"页加载失败"单独定义错误。
- `image_pattern_colorspace.pdf`（仅在 PDFium main 分支存在）在 main 版本上渲染即崩溃；8138 没有该文件，本轮未计入。升级 PDFium 时要重新跑。
- 隔离模式每个文件起一个子进程并各自初始化 PDFium，小文件场景下进程开销大于处理本身（346 个文件 4 jobs 仍只要 4 s，暂可接受）。
- 自动归因只看对象统计、字符位置和填充/描边颜色，分不清 CMYK/ICC/Pattern 三种颜色丢失，也看不出软蒙版、叠印；这些要靠 `--save-dir` 的内容流人工看。
- 没有做对象级"这一页确实被重写"的运行时证明（2.2）。

### 6.3 已知限制（仅记录）

- 公共 API 不能切换 OCG 可见性，含可选内容的页只按默认可见性渲染；`MAG_*` 扩展在 P1 处理。
- Form XObject 内部内容不在本次往返范围内：顶层只重写 `Do`，Form 内部的 CMYK、渐变等缺陷不会被本轮触发（4.6 的 Form 样本因此"无差异"）。
- 本轮没有办公、设计、扫描、货代样本。

## 7. 对方案和计划的修改建议

（本报告不改既有文档，以下由负责人合并。）

- 《方案》2.1 第 4 条：删去"解析 `TJ` 数组时，字距调整值存成占位字符码，写回时被跳过，字距全部丢失"，改为"`TJ` 字距上游已于 2026-03 修复（chromium/8138 已含），`Tc`、`Tw` 仍只存在文字状态里不写出"。
- 《方案》2.1 新增两条：内联图像（`BI … EI`）在重写时被跳过，对象整个丢失；多页共用的内容流会被就地改写，另一页的资源名随之失配。
