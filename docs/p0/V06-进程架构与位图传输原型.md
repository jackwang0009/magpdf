## 1. 目标

《P0 技术验证计划》V06 的三条通过线：

- 从共享内存取一张瓦片小于 5 ms；
- 1000 次小请求的往返 P95 小于 2 ms；
- 强制结束引擎后 5 秒内恢复显示。

另外要给出两个待定项的依据：I1（主进程和引擎之间是否改用 MessagePack）和 I2（共享内存的槽位数量和总大小）。

## 2. 方法

### 2.1 原型结构

```
主进程 magpdf-desktop（目前只有监督端和基准，没有 WebView）
  ├ 启动引擎：命令行传管道名、会话 ID、恢复文件路径、槽位数
  ├ 命名管道客户端：\\.\pipe\magpdf-<主进程 PID>-<8 位随机串>，4 字节小端长度 + UTF-8 JSON
  └ 共享内存只读视图：Local\MagPDF-<会话 ID>-tiles
        │
        ▼
引擎进程 magpdf-engine
  ├ 通信线程（tokio，2 个工作线程）：读帧、解码、派发、编码、写帧
  │   ├ 不等 PDFium 的请求在读循环里直接应答：session.*、render.tiles、render.cancel、tile.fetch
  │   └ 要等 PDFium 的请求交给每条连接一个的工作任务，按到达顺序处理
  ├ PDFium 专用线程：打开和关闭文档、渲染瓦片，任务排队串行执行
  └ 瓦片：渲染完写进共享内存的槽位，再发 render.tileReady
```

| crate | 内容 |
|---|---|
| `engine/magpdf-ipc` | 帧编解码、JSON-RPC 消息、管道、共享内存槽位；主进程和引擎共用。消息类型和常量生成到 `packages/protocol/src/generated/` |
| `engine/magpdf-engine-proc` | 引擎进程：通信循环、PDFium 线程、槽位记账、恢复文件、`bench.engine` |
| `apps/desktop/src-tauri` | 主进程监督端：`magpdf-desktop --bench` |
| `engine/pdfium-sys` | 追加 `tile.rs`：`PageSurface`、`PixelRect`、`render_rect`（按整页像素矩形渲染一块瓦片） |

共享内存的布局：头部 64 字节（魔数、槽位数、槽位大小、版本），之后每个槽位是 64 字节槽头加 512×512×4 字节 BGRA 像素。槽头里的代数按 seqlock 的写法使用：开始写时加 1 变成奇数，写完再加 1 变回偶数；读的一方拷贝前后各读一次代数，两次相等且为偶数才算读到完整瓦片。

恢复文件是一份 JSON，记每份打开的文档的路径、页码、缩放和视口位置，在 `doc.open` 和每次 `render.tiles` 时写盘。引擎启动时按它重新打开文档，并在 `session.hello` 的返回值 `restored` 里告诉主进程。

### 2.2 测量

- `magpdf-desktop --bench` 拉起引擎、打开样本，依次测：1000 次 `session.ping`；引擎内部的分段耗时（`bench.engine`，每项 200 次）；主进程从共享内存读 200 块瓦片；200 次“发 `render.tiles`（一块瓦片）到收到 `render.tileReady`”；最后强制结束引擎，重新拉起到 `session.hello` 应答。结果写到 `tests/out/v06/bench.json`。
- 每组数据跑 5 轮，下面的数字是 5 轮的中位数。测量时系统 CPU 占用 6%–13%。
- 引擎进程另有 7 个端到端用例（`engine/magpdf-engine-proc/tests/e2e.rs`），起真实进程走管道和共享内存，随 `cargo test` 运行。

## 4. 结果数据

### 4.1 三条通过线

| 通过线 | 实测 | 判定 |
|---|---|---|
| 从共享内存取一张瓦片 < 5 ms | 主进程读出一块瓦片：中位数 0.31 ms，P95 0.35 ms | 通过 |
| 1000 次小请求往返 P95 < 2 ms | `session.ping`：中位数 26.6 µs，P95 42.5 µs | 通过 |
| 强制结束引擎后 5 秒内恢复显示 | 结束进程到新引擎应答 `session.hello`、文档已重新打开：62.7 ms | 引擎侧通过，界面侧没测 |

三条都留有两个数量级的余量，但各有一段没测到：

- **取瓦片**测的是主进程从共享内存拷出 1 MB 像素。界面经自定义协议取到这块像素、再上传成纹理的那一段，要等 Tauri 外壳。
- **小请求**只测了不碰 PDFium 的 `session.ping`。任务书要求的“碰 PDFium 的轻量方法”没有单独测。
- **恢复**测的是进程被结束的情况，管道一断主进程立刻知道。引擎挂死时要靠心跳判定，按《接口协议》第 4 节是 5 秒没有响应才算挂死，这种情况下 5 秒内恢复不了；通过线只对“进程被结束”成立。

### 4.2 分段耗时

| 段 | `text-standard14` | `freight-bl-composite` |
|---|---|---|
| PDFium 渲染一块 512×512 瓦片 | 中位数 0.37 ms，P95 0.43 ms | 中位数 0.70 ms，P95 0.81 ms |
| 写入共享内存（1 MB） | 0.22 ms | — |
| 引擎侧读出（1 MB） | 0.11 ms | — |
| 主进程读出（含分配缓冲区和核对代数） | 0.31 ms | 0.31 ms |
| 发 `render.tiles` 到收到 `render.tileReady` | 中位数 0.82 ms，P95 0.98 ms | 中位数 0.95 ms，P95 1.14 ms |
| `session.ping` 往返 | 26.6 µs | 26.6 µs |

`freight-bl-composite` 一列是 3 轮的中位数。

### 4.3 合入时修掉的两个问题

**瓦片事件被定时器拖住。** 读循环原来只在“管道可读”和 500 ms 定时器上醒来。瓦片在后台渲染完，`render.tileReady` 进了待发队列，但没有东西唤醒读循环，要等到下一次定时器。管道空闲时发一块瓦片，实测 503 ms 才收到事件。现在后台任务有消息就唤醒读循环，同样的请求是 0.82 ms。原来的基准没有测“请求到事件”这一段，所以三条通过线都过了而这个问题没暴露。

**PDFium 忙时心跳没有应答。** 读循环原来等每条请求处理完才读下一帧。`doc.open`、`bench.engine` 这类要等 PDFium 线程的请求执行期间，`session.ping` 排在后面得不到应答；`render.tiles` 在记录视图时也会去等 PDFium 线程。打开一个大文件超过 5 秒，主进程就会按心跳超时把引擎误判为挂死。现在这类请求交给每条连接一个的工作任务，读循环不等它们。端到端用例里，`bench.engine` 占着 PDFium 线程时 5 次 `session.ping` 都在 100 ms 内返回。

两个用例都确认过：把修复去掉，对应的用例就失败。

### 4.4 I1：JSON 还是 MessagePack

| 项 | JSON | MessagePack |
|---|---|---|
| 一条小消息的编码 | 0.05 µs | 0.15 µs |
| 一条小消息的解码 | 1.05 µs | 0.60 µs |
| 请求加响应的字节数 | 116 | 82 |

- 一次小请求在引擎侧的编解码合计（请求的编码和解码、响应的编码和解码）是 3.1 µs，占 `session.ping` 往返 26.6 µs 的 12% 左右。这几个数字已经贴近计时器的分辨率，只能看量级。
- 按 I1 的字面标准“占比超过 5% 再换”，12% 超过了。但这个标准是按比例定的，没考虑绝对值：整个往返只有 2 ms 预算的 1.3%，换成 MessagePack 每次省不到 1 µs。
- **建议**：维持 JSON。类型从 Rust 生成、抓包能直接读，这两点比 1 µs 值钱。I1 的标准改成“单条消息的编解码超过 1 ms 再评估”。真正可能超的是 `obj.list` 一次 2000 条这种大响应，P1 做到那里时用真实数据再测。

### 4.5 I2：槽位数量和总大小

| 状态 | 引擎进程 | 主进程 | 系统提交量 |
|---|---|---|---|
| 引擎刚启动，没有文档 | 工作集 9.4 MB，私有 2.2 MB | — | 增加约 220–280 MB |
| 128 个槽位都写过 | 工作集峰值 147 MB，私有峰值 11 MB | 工作集峰值 134 MB | 同上 |

- 一个槽位 1 MB 多一点，128 个槽位写满是 128 MB 物理内存。这部分是两个进程共享的页，在两边的工作集里各算一次，实际只占一份。
- 映射固定按 256 MB 申请，与槽位数无关。申请时没有用 `SEC_RESERVE`，所以 256 MB 在创建时就全部计入系统提交量，物理页才是写到的时候再分配。代码注释里说“没写过的槽位不占内存”，对物理内存成立，对提交量不成立。
- 槽位只是传输用的缓冲：界面取走像素后放进自己的纹理缓存（V12 的上限是 96 MB）。1920×1080、125% 缩放下一屏约 20 块瓦片，加上下各一屏的预取约 60 块，128 个槽位够一次请求用。
- **建议**：默认 128 个槽位不变；映射大小改成按槽位数算（128 个槽位约 128 MB），不再固定 256 MB。

### 4.6 恢复

`magpdf-desktop --bench` 的最后一步：结束引擎进程，用新的管道名和会话 ID 重新拉起，等 `session.hello`。新引擎在启动时已经按恢复文件把文档重新打开，`restored` 里带着新的 `docId`。5 轮都是 1 份文档恢复成功，耗时 60.9–63.5 ms。端到端用例 `a_new_engine_reopens_documents_from_the_recovery_file` 覆盖同一条路径，并确认恢复出来的文档能直接渲染。

这是演示级的实现：恢复文件里只有路径和视图，没有未保存的修改。

## 5. 结论

1. 进程架构可行：主进程和引擎之间的管道往返是几十微秒，瓦片从渲染完成到主进程能读到不到 1 ms，都远低于第 7 节和《接口协议》第 10 节的指标。
2. 三条通过线在开发机上通过，但都只覆盖到主进程为止。界面那一段没有测，因为没有 Tauri 外壳。
3. I1 建议维持 JSON，I2 建议 128 个槽位、映射按槽位数申请。
4. 原型里有两个靠基准发现不了的问题（4.3），已经修掉并补了用例。后面改通信循环时，“请求到事件”的延迟和“忙时心跳”要一直留在测试里。

本机不是参考机 R1，上面的数字都是开发机实测。三条通过线和 4.2 的分段耗时要在 R1 上复测。

## 6. Windows 安全现状与差距

| 项 | 现状 | 差距 |
|---|---|---|
| 管道名 | 主进程 PID 加 8 位随机串（系统随机源） | 无 |
| 管道访问控制 | 用系统默认的安全描述符；拒绝远程客户端；第一个实例带 `first_pipe_instance` | 规范要求只允许当前用户。默认描述符还给 Everyone 读权限，要换成只含当前用户 SID 的显式描述符 |
| 连接方身份 | 不核对 | 引擎应该核对连上来的是不是启动它的主进程 |
| 共享内存命名空间 | 会话本地命名空间，别的登录会话看不到 | 无 |
| 共享内存访问控制 | 认证用户和本地系统都是完全控制 | 要收窄到当前用户。代码注释记录了收窄后别的进程打不开映射的现象，原因没查清 |
| 主进程的视图 | 代码里按只读使用，但向系统申请的是读写权限 | 要改成只读映射 |
| 引擎进程 | 普通权限，没有沙箱 | 方案 2.2 的隔离只做到了“崩溃不影响界面”，没有限制引擎能访问什么 |

这些都留到 P1 和引擎进程的沙箱一起做。

## 7. 遗留问题

1. **Tauri WebView 外壳没有接。** `apps/desktop/src-tauri` 现在是一个命令行程序，没有依赖 Tauri。自定义协议取瓦片、界面的 `TileProvider` 接真实引擎、WebView2 的端到端测试（V12 也在等）都卡在这里。
2. **主进程没有心跳循环。** 引擎侧能应答，主进程侧每 2 秒发一次、5 秒判定挂死的逻辑还没写。
3. **`render.cancel` 是空实现**，`render.tiles` 的 `priority` 没有用上：瓦片按请求顺序渲染。
4. **槽位的缓存命中没有接进渲染路径**，同一块瓦片重复请求会重复渲染。接的时候缓存键里要带文档版本。
5. **每次 `render.tiles` 都同步写一次恢复文件**，在通信线程上。应改成按方案 9.3 定时写。
6. **`engine.restored` 事件还没有发**：引擎已经在 `session.hello` 里报告恢复了哪些文档，主进程转给界面的那一步要等外壳。
7. **没有测碰 PDFium 的轻量请求**，也没有在 R1 上复测。
8. 第 6 节的安全差距。

## 8. 对《接口协议》的修改建议

以下都是建议，文档本身没有改。

**第 3 节**

- 3.3“槽位每复用一次代数加 1”改为“每写入一次代数加 2，奇数表示正在写”，与 seqlock 的实现一致。
- 3.3 的 `fetch("magpdf://tile/<槽位>/<代数>")`：Tauri 2 在 Windows 上把自定义协议映射成 `http://magpdf.localhost/…` 的形式，接外壳时要核实并改写这一句。
- PDFium 渲染到不透明白底上，瓦片的透明度恒为 255，预乘与否没有区别。以后渲染透明图层（拖动预览）时要再确认。

**第 4 节**

- `session.hello` 的参数增加 `sessionId`（共享内存名里要用）和 `recoveryFile`。
- `session.hello` 的返回值增加 `pid` 和 `restored`（按恢复文件重新打开的文档）。主进程靠 `restored` 才能发 `engine.restored`。
- 写明 PDFium 忙的时候 `session.ping` 也必须有应答，否则大文件会被误判成挂死。

**第 6、7 节**

- 原型多了一个 `tile.fetch`（主进程请引擎核对代数）。主进程自己就能从共享内存读代数，建议删掉这个方法。
- `bench.*` 是测量用的方法，正式版本里要放在能力开关后面。
- `render.tileReady` 的参数按第 7 节实现，其中 `version` 目前恒为 0。

**第 8 节**

- 增加“瓦片已被新内容替换”的错误码。原型用的是 3006 `E_TILE_GENERATION_STALE`，主进程转成 HTTP 410。
- 增加“文档不存在”的错误码。原型里 `docId` 无效时借用了 3005 `E_INVALID_ARGUMENT`。
- 增加“文件读不了”（没有权限、被占用）的错误码。2007 `E_WRITE_FAILED` 只管写。

**第 10 节**

- 增加一项：从 `render.tiles` 到 `render.tileReady` 的延迟。4.3 的第一个问题正是因为没有这一项才漏掉的。
- “从共享内存取一张瓦片小于 5 ms”写明测量的起止点：是到主进程读出为止，还是到界面拿到像素为止。

**第 11 节**

- I1、I2 按 4.4、4.5 的建议定稿。
