## 1. 目标

《P0 技术验证计划》V06 的三条通过线：

- 从共享内存取一张瓦片小于 5 ms；
- 1000 次小请求的往返 P95 小于 2 ms；
- 强制结束引擎后 5 秒内恢复显示。

另外要给出两个待定项的依据：I1（主进程和引擎之间是否改用 MessagePack）和 I2（共享内存的槽位数量和总大小）。

## 2. 方法

### 2.1 原型结构

```
主进程 magpdf-desktop（目前只有监督端和基准，没有 WebView）
  ├ 启动引擎：命令行传管道名、会话 ID、恢复文件路径、槽位数
  ├ 命名管道客户端：\\.\pipe\magpdf-<主进程 PID>-<8 位随机串>，4 字节小端长度 + UTF-8 JSON
  └ 共享内存只读视图：Local\MagPDF-<会话 ID>-tiles
        │
        ▼
引擎进程 magpdf-engine
  ├ 通信线程（tokio，2 个工作线程）：读帧、解码、派发、编码、写帧
  │   ├ 不等 PDFium 的请求在读循环里直接应答：session.*、render.tiles、render.cancel、tile.fetch
  │   └ 要等 PDFium 的请求交给每条连接一个的工作任务，按到达顺序处理
  ├ PDFium 专用线程：打开和关闭文档、渲染瓦片，任务排队串行执行
  └ 瓦片：渲染完写进共享内存的槽位，再发 render.tileReady
```

| crate | 内容 |
|---|---|
| `engine/magpdf-ipc` | 帧编解码、JSON-RPC 消息、管道、共享内存槽位；主进程和引擎共用。消息类型和常量生成到 `packages/protocol/src/generated/` |
| `engine/magpdf-engine-proc` | 引擎进程：通信循环、PDFium 线程、槽位记账、恢复文件、`bench.engine` |
| `apps/desktop/src-tauri` | 主进程监督端：`magpdf-desktop --bench` |
| `engine/pdfium-sys` | 追加 `tile.rs`：`PageSurface`、`PixelRect`、`render_rect`（按整页像素矩形渲染一块瓦片） |

共享内存的布局：头部 64 字节（魔数、槽位数、槽位大小、版本），之后每个槽位是 64 字节槽头加 512×512×4 字节 BGRA 像素。槽头里的代数按 seqlock 的写法使用：开始写时加 1 变成奇数，写完再加 1 变回偶数；读的一方拷贝前后各读一次代数，两次相等且为偶数才算读到完整瓦片。

恢复文件是一份 JSON，记每份打开的文档的路径、页码、缩放和视口位置，在 `doc.open` 和每次 `render.tiles` 时写盘。引擎启动时按它重新打开文档，并在 `session.hello` 的返回值 `restored` 里告诉主进程。

### 2.2 测量

- `magpdf-desktop --bench` 拉起引擎、打开样本，依次测：1000 次 `session.ping`；引擎内部的分段耗时（`bench.engine`，每项 200 次）；主进程从共享内存读 200 块瓦片；200 次“发 `render.tiles`（一块瓦片）到收到 `render.tileReady`”；最后强制结束引擎，重新拉起到 `session.hello` 应答。结果写到 `tests/out/v06/bench.json`。
- 每组数据跑 5 轮，下面的数字是 5 轮的中位数。测量时系统 CPU 占用 6%–13%。
- 引擎进程另有 11 个端到端用例（`engine/magpdf-engine-proc/tests/e2e.rs`），起真实进程走管道和共享内存，随 `cargo test` 运行。其中 8 个覆盖本报告的内容（含 11.5 补的一个），3 个覆盖后来接上的 `doc.snapshot` 和编辑命令（见第 10 节）。主进程一侧的监督者另有 4 个用例（`tests/supervisor.rs`，见 11.1）。

## 4. 结果数据

### 4.1 三条通过线

| 通过线 | 实测 | 判定 |
|---|---|---|
| 从共享内存取一张瓦片 < 5 ms | 主进程读出一块瓦片：中位数 0.31 ms，P95 0.35 ms | 通过 |
| 1000 次小请求往返 P95 < 2 ms | `session.ping`：中位数 26.6 µs，P95 42.5 µs | 通过 |
| 强制结束引擎后 5 秒内恢复显示 | 结束进程到新引擎应答 `session.hello`、文档已重新打开：62.7 ms | 引擎侧通过，界面侧没测 |

三条都留有两个数量级的余量，但各有一段没测到：

- **取瓦片**测的是主进程从共享内存拷出 1 MB 像素。界面经自定义协议取到这块像素、再上传成纹理的那一段，要等 Tauri 外壳。
- **小请求**只测了不碰 PDFium 的 `session.ping`。任务书要求的“碰 PDFium 的轻量方法”没有单独测。
- **恢复**测的是进程被结束的情况，管道一断主进程立刻知道。引擎挂死时要靠心跳判定，按《接口协议》第 4 节是 5 秒没有响应才算挂死，这种情况下 5 秒内恢复不了；通过线只对“进程被结束”成立。

### 4.2 分段耗时

| 段 | `text-standard14` | `freight-bl-composite` |
|---|---|---|
| PDFium 渲染一块 512×512 瓦片 | 中位数 0.37 ms，P95 0.43 ms | 中位数 0.70 ms，P95 0.81 ms |
| 写入共享内存（1 MB） | 0.22 ms | — |
| 引擎侧读出（1 MB） | 0.11 ms | — |
| 主进程读出（含分配缓冲区和核对代数） | 0.31 ms | 0.31 ms |
| 发 `render.tiles` 到收到 `render.tileReady` | 中位数 0.81 ms，P95 1.04 ms | 中位数 0.94 ms，P95 1.27 ms |
| `session.ping` 往返 | 26.6 µs | 26.6 µs |

`freight-bl-composite` 一列是 3 轮的中位数。“请求到事件”一行是 2026-11-11 修正瓦片取景之后重测的（11.2）：这一项每次取一块 4 倍缩放的瓦片、位置各不相同，修正前不在左上角的瓦片渲染出来是空白，当时记的是 0.82 / 0.98 ms 和 0.95 / 1.14 ms。其余各行用的都是左上角那块瓦片，不受影响。

### 4.3 合入时修掉的两个问题

**瓦片事件被定时器拖住。** 读循环原来只在“管道可读”和 500 ms 定时器上醒来。瓦片在后台渲染完，`render.tileReady` 进了待发队列，但没有东西唤醒读循环，要等到下一次定时器。管道空闲时发一块瓦片，实测 503 ms 才收到事件。现在后台任务有消息就唤醒读循环，同样的请求不到 1 ms（4.2）。原来的基准没有测“请求到事件”这一段，所以三条通过线都过了而这个问题没暴露。

**PDFium 忙时心跳没有应答。** 读循环原来等每条请求处理完才读下一帧。`doc.open`、`bench.engine` 这类要等 PDFium 线程的请求执行期间，`session.ping` 排在后面得不到应答；`render.tiles` 在记录视图时也会去等 PDFium 线程。打开一个大文件超过 5 秒，主进程就会按心跳超时把引擎误判为挂死。现在这类请求交给每条连接一个的工作任务，读循环不等它们。端到端用例里，`bench.engine` 占着 PDFium 线程时 5 次 `session.ping` 都在 100 ms 内返回。

两个用例都确认过：把修复去掉，对应的用例就失败。

### 4.4 I1：JSON 还是 MessagePack

| 项 | JSON | MessagePack |
|---|---|---|
| 一条小消息的编码 | 0.05 µs | 0.15 µs |
| 一条小消息的解码 | 1.05 µs | 0.60 µs |
| 请求加响应的字节数 | 116 | 82 |

- 一次小请求在引擎侧的编解码合计（请求的编码和解码、响应的编码和解码）是 3.1 µs，占 `session.ping` 往返 26.6 µs 的 12% 左右。这几个数字已经贴近计时器的分辨率，只能看量级。
- 按 I1 的字面标准“占比超过 5% 再换”，12% 超过了。但这个标准是按比例定的，没考虑绝对值：整个往返只有 2 ms 预算的 1.3%，换成 MessagePack 每次省不到 1 µs。
- **建议**：维持 JSON。类型从 Rust 生成、抓包能直接读，这两点比 1 µs 值钱。I1 的标准改成“单条消息的编解码超过 1 ms 再评估”。真正可能超的是 `obj.list` 一次 2000 条这种大响应，P1 做到那里时用真实数据再测。

### 4.5 I2：槽位数量和总大小

| 状态 | 引擎进程 | 主进程 | 系统提交量 |
|---|---|---|---|
| 引擎刚启动，没有文档 | 工作集 9.4 MB，私有 2.2 MB | — | 增加约 220–280 MB |
| 128 个槽位都写过 | 工作集峰值 147 MB，私有峰值 11 MB | 工作集峰值 134 MB | 同上 |

- 一个槽位 1 MB 多一点，128 个槽位写满是 128 MB 物理内存。这部分是两个进程共享的页，在两边的工作集里各算一次，实际只占一份。
- 映射固定按 256 MB 申请，与槽位数无关。申请时没有用 `SEC_RESERVE`，所以 256 MB 在创建时就全部计入系统提交量，物理页才是写到的时候再分配。代码注释里说“没写过的槽位不占内存”，对物理内存成立，对提交量不成立。
- 槽位只是传输用的缓冲：界面取走像素后放进自己的纹理缓存（V12 的上限是 96 MB）。1920×1080、125% 缩放下一屏约 20 块瓦片，加上下各一屏的预取约 60 块，128 个槽位够一次请求用。
- **建议**：默认 128 个槽位不变；映射大小改成按槽位数算（128 个槽位约 128 MB），不再固定 256 MB。

### 4.6 恢复

`magpdf-desktop --bench` 的最后一步：结束引擎进程，用新的管道名和会话 ID 重新拉起，等 `session.hello`。新引擎在启动时已经按恢复文件把文档重新打开，`restored` 里带着新的 `docId`。5 轮都是 1 份文档恢复成功，耗时 60.9–63.5 ms。端到端用例 `a_new_engine_reopens_documents_from_the_recovery_file` 覆盖同一条路径，并确认恢复出来的文档能直接渲染。

这是演示级的实现：恢复文件里只有路径和视图，没有未保存的修改。

## 5. 结论

1. 进程架构可行：主进程和引擎之间的管道往返是几十微秒，瓦片从渲染完成到主进程能读到不到 1 ms，都远低于第 7 节和《接口协议》第 10 节的指标。
2. 三条通过线在开发机上通过，但都只覆盖到主进程为止。界面那一段没有测，因为没有 Tauri 外壳。（外壳接上之后的结果见 11.7：恢复显示通过，小请求贴着线，取瓦片没有达到。）
3. I1 建议维持 JSON，I2 建议 128 个槽位、映射按槽位数申请。
4. 原型里有两个靠基准发现不了的问题（4.3），已经修掉并补了用例。后面改通信循环时，“请求到事件”的延迟和“忙时心跳”要一直留在测试里。

本机不是参考机 R1，上面的数字都是开发机实测。三条通过线和 4.2 的分段耗时要在 R1 上复测。

## 6. Windows 安全现状与差距

| 项 | 现状 | 差距 |
|---|---|---|
| 管道名 | 主进程 PID 加 8 位随机串（系统随机源） | 无 |
| 管道访问控制 | 用系统默认的安全描述符；拒绝远程客户端；第一个实例带 `first_pipe_instance` | 规范要求只允许当前用户。默认描述符还给 Everyone 读权限，要换成只含当前用户 SID 的显式描述符 |
| 连接方身份 | 不核对 | 引擎应该核对连上来的是不是启动它的主进程 |
| 共享内存命名空间 | 会话本地命名空间，别的登录会话看不到 | 无 |
| 共享内存访问控制 | 认证用户和本地系统都是完全控制 | 要收窄到当前用户。代码注释记录了收窄后别的进程打不开映射的现象，原因没查清 |
| 主进程的视图 | 代码里按只读使用，但向系统申请的是读写权限 | 要改成只读映射 |
| 引擎进程 | 普通权限，没有沙箱 | 方案 2.2 的隔离只做到了“崩溃不影响界面”，没有限制引擎能访问什么 |

这些都留到 P1 和引擎进程的沙箱一起做。

## 7. 遗留问题

1. **Tauri WebView 外壳没有接。** `apps/desktop/src-tauri` 现在是一个命令行程序，没有依赖 Tauri。自定义协议取瓦片、界面的 `TileProvider` 接真实引擎、WebView2 的端到端测试（V12 也在等）都卡在这里。（2026-11-11 已接，见 11.6。）
2. **主进程没有心跳循环。** 引擎侧能应答，主进程侧每 2 秒发一次、5 秒判定挂死的逻辑还没写。（2026-11-11 已补，见 11.1。）
3. **`render.cancel` 是空实现**，`render.tiles` 的 `priority` 没有用上：瓦片按请求顺序渲染。
4. **槽位的缓存命中没有接进渲染路径**，同一块瓦片重复请求会重复渲染。接的时候缓存键里要带文档版本。
5. **每次 `render.tiles` 都同步写一次恢复文件**，在通信线程上。应改成按方案 9.3 定时写。
6. **`engine.restored` 事件还没有发**：引擎已经在 `session.hello` 里报告恢复了哪些文档，主进程转给界面的那一步要等外壳。（已发，见 11.6。）
7. **没有测碰 PDFium 的轻量请求**，也没有在 R1 上复测。（从界面发起的轻量请求见 11.7；R1 上仍然没测。）
8. 第 6 节的安全差距。

## 8. 对《接口协议》的修改建议

以下都是建议，文档本身没有改。

**第 3 节**

- 3.3“槽位每复用一次代数加 1”改为“每写入一次代数加 2，奇数表示正在写”，与 seqlock 的实现一致。
- 3.3 的 `fetch("magpdf://tile/<槽位>/<代数>")`：Tauri 2 在 Windows 上把自定义协议映射成 `http://magpdf.localhost/…` 的形式，接外壳时要核实并改写这一句。
- PDFium 渲染到不透明白底上，瓦片的透明度恒为 255，预乘与否没有区别。以后渲染透明图层（拖动预览）时要再确认。

**第 4 节**

- `session.hello` 的参数增加 `sessionId`（共享内存名里要用）和 `recoveryFile`。
- `session.hello` 的返回值增加 `pid` 和 `restored`（按恢复文件重新打开的文档）。主进程靠 `restored` 才能发 `engine.restored`。
- 写明 PDFium 忙的时候 `session.ping` 也必须有应答，否则大文件会被误判成挂死。

**第 6、7 节**

- 原型多了一个 `tile.fetch`（主进程请引擎核对代数）。主进程自己就能从共享内存读代数，建议删掉这个方法。
- `bench.*` 是测量用的方法，正式版本里要放在能力开关后面。
- `render.tileReady` 的参数按第 7 节实现，`version` 是渲染时的文档版本。

**第 8 节**

- 增加“瓦片已被新内容替换”的错误码。原型用的是 3006 `E_TILE_GENERATION_STALE`，主进程转成 HTTP 410。
- 增加“文档不存在”的错误码。原型里 `docId` 无效时借用了 3005 `E_INVALID_ARGUMENT`。
- 增加“文件读不了”（没有权限、被占用）的错误码。2007 `E_WRITE_FAILED` 只管写。

**第 10 节**

- 增加一项：从 `render.tiles` 到 `render.tileReady` 的延迟。4.3 的第一个问题正是因为没有这一项才漏掉的。
- “从共享内存取一张瓦片小于 5 ms”写明测量的起止点：是到主进程读出为止，还是到界面拿到像素为止。

**第 11 节**

- I1、I2 按 4.4、4.5 的建议定稿。

## 10. 补记：编辑命令接入（2026-11-10）

报告写完之后，编辑会话接到了引擎进程的协议上，这样界面以后能经同一条管道改文档。这部分超出 V06 的范围，记在这里是因为它改了本报告描述的消息集合。

| 方法 | 现状 |
|---|---|
| `obj.list` | 按层级从下到上返回对象摘要，支持 `offset`、`limit`，单次最多 2000 条 |
| `obj.hitTest` | `top` 跳过不可见文字、全透明对象和铺满页面的白底；`all` 自上而下返回全部 |
| `edit.transform`、`edit.delete` | 可作用于多个对象，记成一步撤销 |
| `edit.setStyle` | 只支持 RGB 填充色；带了别的样式字段按参数不合法拒绝 |
| `history.undo`、`history.redo` | 撤销删除时对象回到原来的层级，编号不变 |

- 修改类请求带 `baseVersion`，与当前版本不一致返回 3001。成功后推送 `doc.changed`，再应答新版本号。
- 每页第一次修改前先做对象比对（方案 2.3）：在文档副本上重写这一页的内容流，比较前后对象的个数、种类和包围盒。不通过的页拒绝修改，返回 3004。用原版 PDFium 预编译库，58 份自制样本的首页 44 份通过、14 份不通过，不通过的都是方案 2.1 列出的生成器缺陷（渐变、Type3、内联图像、文字裁剪、`Tc`/`Tw` 等）。像素比对和操作符级比对还没有做，颜色空间被换成等价 RGB 的页目前会被放行。（2026-11-11：只做对象比对会放行改了就变色的页，像素比对已补，数字也按页重新统计，见 12.2。）

接入时发现《接口协议》有几处没有写明，实现里先按下面的做法，定稿时要补上：

- `Rect` 的写法：实现用 `[left, bottom, right, top]`。
- 颜色的写法：实现用 `{space, components}`，分量在 0–1 之间。
- `doc.changed` 里 `pagesChanged` 的类型：实现当作布尔值。
- `doc.changed` 和响应的先后：实现先推送事件，再应答。
- 没有可撤销或可重做的操作时用哪个错误码：实现借用了 3005。
- `pageId` 应当在页面重排后不变：实现里它还等于页序号，等有了页面命令再改。

## 11. 补记：接上界面（2026-11-11）

外壳接上之后，页面第一次由引擎渲染进了界面，也第一次有东西去看渲染出来的像素、去走真实的鼠标事件。原来只靠计时的基准和只碰左上角瓦片的用例没发现的问题，这一轮查出来四个（11.2、11.3、11.5，以及 11.6 末尾界面上的一个），都已经修掉；另有一个 PDFium 上游的问题没有修（11.4）。

### 11.1 主进程的监督者

`magpdf_ipc::host::Supervisor` 把第 7 节第 2 条补上了，以后 Tauri 外壳直接用它：

- 启动引擎、连管道、开共享内存、发 `session.hello` 并核对协议版本。
- 请求可以多条同时在途，各自按 `id` 对应答；引擎推送的事件交给调用方；瓦片按槽位和代数从共享内存读。
- 每 2 秒发一次 `session.ping`，5 秒没有应答按挂死处理（《接口协议》第 4 节）。
- 引擎没了就重启：在途请求以 `E_ENGINE_RESTARTED` 结束，新引擎就绪后带着它按恢复文件重新打开的文档通知调用方；连续 3 次拉不起来才报失败。

4 个用例对着真实的引擎进程跑。挂死的情况用引擎的测试开关 `--test-hooks` 造出来：`bench.stall` 把通信循环卡住，进程和管道都还在，只有心跳能发现。用例里心跳调成 100 ms 一次、400 ms 超时，从卡住到新引擎就绪不到 1 秒；按默认的 2 秒和 5 秒，发现挂死本身就要 5–7 秒，4.1 里“挂死时 5 秒内恢复不了”的结论不变。

### 11.2 瓦片取景的平移方向反了（已修）

`render_rect` 把瓦片在整页上的位置 `(x, y)` 原样传给了 `FPDF_RenderPageBitmap` 的 `start_x`、`start_y`。这两个参数的意思是“整页的左上角画在位图的什么位置”，要取整页上从 `(x, y)` 开始的一块，应该传 `(-x, -y)`。结果是只有左上角那块瓦片是对的，其余的要么是空白，要么是错位的内容。

原来的用例只渲染过 `(0, 0)` 和整页之外的瓦片，基准也只计时不看像素，所以一直没暴露。现在的用例把整页按 2 倍渲染后切成格子，每一格都和整页渲染里的同一块比对；引擎进程的端到端用例也多渲染一块不在左上角的瓦片，核对里面有内容。

受影响的数字只有 4.2 的“请求到事件”一行，已重测。

### 11.3 缩放倍数被取整到千分位（已修）

槽位的键把 `scale` 乘 1000 取整，渲染时又用取整后的数。界面的缩放档是 √2 的幂乘 96/72（V12），不是整的千分位，取整后整页的像素尺寸和界面算的不一样，瓦片贴上去会差出零点几个像素。现在键里存的是 `scale` 的二进制表示，渲染和 `render.tileReady` 用的都是请求里的原数；`scale` 不是正数的请求直接按参数不合法拒绝。

### 11.4 PDFium：跨在瓦片左边界上的字形会错位不到 1 像素（未修）

修掉 11.2 之后，逐格比对里还剩两种差异。一种是半透明印章的边缘上个别像素差 1 个色阶，是整页挪动之后浮点误差不同，看不出来，不用管。

另一种看得出来：一个字形跨在瓦片的左边界上时，它在右边那块瓦片里的部分横向错开了不到 1 像素，和左边那块瓦片里的另一半对不齐。2 倍缩放下，样本上是右上角色块里“CMYK”中的“Y”和表头里的一个字母，差异在瓦片左边缘往里 8 像素之内；4 倍缩放下字形大了，最宽到 15 像素。

原因在 PDFium（`core/fxge/cfx_renderdevice.cpp`，`CFX_RenderDevice::DrawNormalText`）。彩色位图上的文字按 1/3 像素定位：整数位置用 `floor(device_origin.x)`，1/3 像素的余数用 `static_cast<int>(device_origin.x * 3) % 3`。字形从位图左边缘之外开始时 `device_origin.x` 是负数，后一个式子向零截断再取余，得到 0、-1、-2，和 `floor` 出来的整数位置对不上，字形就偏了 1/3 或 2/3 像素。整页渲染时只有伸出页面左边的字形会碰到，看不出来；按瓦片渲染时每条竖向的瓦片边界上都可能碰到。

这是上游的问题，原版预编译库和我们的分支都有。可选的处理：

1. 在 PDFium 分支里改那一行（余数也按 `floor` 算）。改动一行，可以提给上游，能算进“P0 至少提交 2 个上游补丁”（C2）。
2. 引擎渲染瓦片时往左多渲染一条边再裁掉，让跨边界的字形原点落在位图之内。不用改 PDFium，但每块瓦片多渲染十分之一左右的像素，而且比这条边还宽的字形仍然会错位。

建议走第 1 条。用例 `every_tile_of_the_grid_matches_its_part_of_the_full_render` 把现状固定下来了：在 2 倍和 1.886 倍（界面实际会用的一档）下，相差超过 2 个色阶的像素每块瓦片不超过 0.5%，只允许出现在左边缘往里 16 像素之内，最左一列的瓦片不允许有；别处出现差异就是新问题。分支修掉之后这条用例仍然能过。

### 11.5 主进程没了，引擎留下来不退出（已修）

引擎原来在连接断开后重建管道实例，继续等下一个连接。管道名里有主进程的 PID 和随机串，主进程每次都是换一个名字重新启动引擎，不会回头再连；主进程崩溃或被结束时，引擎就成了没人管的进程，还占着文档。现在一个引擎只服务一条连接，连接断了就退出。端到端用例里关掉主进程这一头的管道，引擎在 5 秒内正常退出；外壳的冒烟测试里强制结束主进程，引擎 50 ms 左右退出。

引擎自己卡死、同时主进程又被结束的情况，这个办法管不了。要兜住得把引擎放进一个“句柄关闭即结束”的作业对象，和第 6 节的沙箱一起做。

### 11.6 Tauri 外壳和界面接入

第 7 节第 1、6 条做完了：`apps/desktop/src-tauri` 现在是 Tauri 2 的程序，窗口里用系统的 WebView2 跑界面，打开的是真实的 PDF。

```
界面（WebView2）
  ├ EngineSession：把引擎打开的文档放进编辑器的 store；跟着 doc.changed、engine.restored 更新
  ├ EngineTileProvider：画布要 256 像素的瓦片 → 对到盖住它的那块 512 像素引擎瓦片
  │     render.tiles → 等 render.tileReady → 取像素 → 裁出自己的一块，BGRA 换成 RGBA
  └ TauriTransport：命令 engine_request、事件 engine-event、fetch http://magpdf.localhost/tile/…
        │
主进程（magpdf-desktop，Tauri 2）
  ├ 命令 engine_request：文档类请求原样转给引擎；session.*、bench.*、tile.fetch、doc.open 不让界面直接调
  ├ 命令 open_document_dialog：主进程弹“打开”对话框，把选中的文件交给引擎；界面拿不到任意路径
  ├ 命令 open_documents：已经开着的文档（命令行给的，或界面重新加载之前打开的）
  ├ 自定义协议 magpdf：从共享内存读一块瓦片；代数对不上返回 410
  ├ 事件：引擎推送的原样转发；引擎重启时发 engine.restarting、engine.restored、engine.failed
  └ Supervisor（11.1）
```

几处和文档不一样、或者文档没写的地方：

- **取瓦片的地址**。《接口协议》3.3 写的 `fetch("magpdf://tile/…")` 在 WebView2 里不能用，Tauri 把自定义协议映射成 `http://magpdf.localhost/tile/<槽位>/<代数>`，界面用的是这个地址。它和页面（`http://tauri.localhost`）不同源，响应要带 `Access-Control-Allow-Origin`；主进程只对应用自己的页面给这个头，别的来源读不到像素。
- **事件名**。Tauri 的事件名里不能有点号，所以只用一个 Tauri 事件 `engine-event`，协议里的事件名放在载荷的 `method` 里。
- **`engine.restored` 的参数**。协议只写了 `{docIds}`。引擎重启后 `docId` 是重新分配的，界面光有新的 `docId` 对不上手里的文档，实现里多带了每份文档的信息（含路径），界面按路径对。
- **`engine.failed`**。连续 3 次拉不起引擎时发，协议里没有。
- **瓦片大小**。画布用 256 像素的瓦片（V12 的选择），引擎是 512（方案第 7 节）。现在由界面一侧对接：四块画布瓦片共用一块引擎瓦片，取回的像素留一会儿。两边统一成哪个，要在第二轮文档修订里定。
- **权限**。界面只开了“收事件”和上面三个命令；Tauri 的其他接口（文件系统、对话框插件等）没有装，也没有授权。内容安全策略只允许加载应用自己的脚本和样式、连主进程和瓦片地址。
- **数据目录**。恢复文件在 `%LOCALAPPDATA%\MagPDF\recovery\`，按主进程的 PID 分文件，正常退出时删掉。主进程被强制结束时这个文件会留下，下次启动没有人读它；“上次没正常退出，要不要恢复”还没有做。
- **调试端口**。设了环境变量 `MAGPDF_WEBVIEW_DEBUG_PORT` 才打开 WebView2 的远程调试端口，端到端测试靠它连进界面；这时窗口启动也不抢焦点。

验证：

- 界面一侧的单元测试 28 个（瓦片来源 16、会话 9、画布提示层 2、入口页 1），用假的通道。
- 端到端冒烟测试 `apps/desktop/e2e/smoke.mjs`：起发布版的桌面程序，Playwright 经 CDP 连进 WebView2（方案 13.2 第 8 项），走一遍“命令行打开 PDF → 页面渲染出来 → Ctrl + 滚轮放大 → 强制结束引擎后恢复显示 → 关标签页 → 结束主进程后引擎退出”，每一步截图数页面区域里的像素。连跑 5 轮都通过。
- “打开”对话框：在界面里按 Ctrl+O，主进程弹出的对话框归主窗口所有，取消后界面没有变化。从对话框里选文件这一步没有自动化，只用命令行打开的路径验证过同一段打开逻辑。

接入时在界面里另外查出一个问题：画布上“WebGL2 不可用”的提示层一直盖在画布上面。它用 `hidden` 属性隐藏，但样式表给了它 `display: flex`，属性不起作用；结果是提示文字叠在页面中间，鼠标事件全被它接走，滚轮、拖动、选择都到不了画布。V12 的基准是直接调画布的接口，没有经过真实的鼠标事件，所以没发现。现在只有 WebGL2 真的不可用时才放这一层，冒烟测试里用真实的滚轮事件守着。

### 11.7 界面这一段的实测

发布版，开发机，`freight-bl-composite.pdf`。在 WebView2 里用 `performance.now()` 计时，每项 200 次（小请求 1000 次），下面是 2–3 轮的范围。

| 项 | 实测 |
|---|---|
| 小请求往返，界面 → 主进程 → 引擎 → 回来（`render.cancel`，不碰 PDFium） | 中位数 0.9 ms，P95 1.7–1.9 ms |
| 同上，要等 PDFium 线程的轻量请求（`doc.snapshot`） | 中位数 0.9–1.0 ms，P95 1.7–2.0 ms |
| 界面取一块瓦片（`fetch` 加读成 `ArrayBuffer`，1 MB） | 中位数 5.4–5.6 ms，P95 6.4–7.0 ms |
| 其中：同一个地址的空响应（410） | 中位数 0.7 ms |
| 其中：拿到响应头 / 读完响应体 | 5.0–5.3 ms / 0.6 ms |
| 8 块瓦片同时取 | 24–25 ms，合每块 3.0–3.1 ms |
| 发 `render.tiles` 到界面收到 `render.tileReady`（4 倍缩放的瓦片） | 中位数 2.0–2.2 ms，P95 3.2–3.3 ms |
| 发 `render.tiles` 到像素到手 | 中位数 7.8–8.0 ms，P95 9.4–9.8 ms |
| 界面裁出 256×256 并换通道 | 中位数 0.6 ms |
| 启动程序到第一屏瓦片到齐（冒烟测试 5 轮） | 614–664 ms |
| 强制结束引擎到页面重新渲染完（冒烟测试 5 轮） | 191–199 ms |

对照三条通过线，补上 4.1 没测到的那一段：

1. **取瓦片小于 5 ms：到界面为止没有达到。** 主进程从共享内存读出只要 0.31 ms，但按《接口协议》3.3 的办法经自定义协议交给界面，中位数是 5.4–5.6 ms。空响应只要 0.7 ms，说明多出来的 4.5 ms 左右花在 WebView2 接收 1 MB 响应体上，和共享内存、和引擎都没有关系。wry（Tauri 的 WebView 层）是在界面线程上把响应体拷进一个内存流再交给 WebView2 的，WebView2 的文档提醒这种流应当在后台线程上建，否则会拖慢；是不是这个原因没有做剖析确认。
2. **小请求 P95 小于 2 ms：勉强达到。** 管道上的往返是几十微秒，Tauri 的命令通道每次要加 0.9 ms 左右。开发机上 P95 是 1.7–2.0 ms，贴着线。参考机 R1（i5-1240P 一档）的单核性能比开发机低不少，这一项在 R1 上有超线的风险，要复测。
3. **强制结束引擎后 5 秒内恢复显示：达到。** 从结束引擎进程到界面把页面重新渲染完是 0.2 秒。

对第 1 条的建议，按改动从小到大：

- 先不动。一屏瓦片是同时取的，合每块 3 ms，20 块瓦片 60 ms 左右，加上渐进显示，P0 的原型够用。
- 改用 WebView2 的 SharedBuffer。方案 3.1 已经留了这条路：主进程把像素放进 WebView2 建的共享缓冲区，界面直接读，没有响应体这一趟。Tauri 没有包这个接口，要经 `webview2-com` 直接调 COM，主进程里会多一块 `unsafe` 的 Windows 接口代码。
- 4.1 的通过线和《接口协议》第 10 节要写明“取一张瓦片”量到哪里为止。量到主进程是 0.3 ms，量到界面是 5.5 ms，差了一个数量级。

真实文档上平移、缩放的帧时间没有测：手头的自制样本只有 1–3 页，测不出东西，这一项留给 V05。

### 11.9 《接口协议》还要补的

在第 8 节之外，这次又攒下几条：

- 3.3 的取瓦片地址按 11.6 改写；写明响应不带缓存、代数对不上返回 410、槽位越界或地址不对返回 404。
- `render.tiles` 的 `tiles: [{x, y}]` 没写单位。实现里是瓦片左上角在整页像素网格上的位置（512 的倍数），不是瓦片的行列号。
- `render.tiles` 的应答和 `render.tileReady` 走两条路（命令的应答、事件），到界面的先后没有保证。界面要能处理事件先到的情况，协议里应当写明。
- 瓦片渲染失败时界面收不到任何消息：`render.tiles` 已经应答过了，`render.tileReady` 又不会来。现在界面只能靠 30 秒超时。建议加一个 `render.tileFailed` 事件，或者让 `render.tileReady` 能带错误。
- `engine.restored` 的参数、`engine.failed` 事件，见 11.6。
- 第 2 节写“文档类请求，主进程原样转发”。实现里 `doc.open` 不转发界面发来的：路径只能来自主进程自己弹的对话框或命令行，界面传不了路径。这一条比协议严，建议协议照此改。

## 12. 补记：在界面上修改真实文档（2026-11-11）

第 10 节的编辑命令这一轮接到了界面上：在真实的 PDF 上点选、拖动、缩放、删除、撤销、重做，页面随之重画。“打开 → 修改 → 看到结果”第一次走通。界面那一侧的做法见 V12 报告第 11 节，这里记引擎和协议这一侧，以及走通之后才看见的两个问题（12.2、12.4）。

### 12.1 消息集合的变化

| 消息 | 变化 |
|---|---|
| `doc.snapshot` | 接受 `pageIds`：只返回这几页，并带上每页的 `rotate` 和 `cropBox`（CropBox 与 MediaBox 的交集）。界面靠这两样把对象的包围盒从 PDF 用户空间换算到画布上 |
| `PageInfo` | 增加 `fidelity`（`pending`、`ok`、`overlayOnly`）和 `fidelityReason`，照《接口协议》5.3 |
| `ObjectSummary` | 增加 `pickable`：不可见文字、完全透明的对象、铺满页面的白底为 false（方案 4.3） |
| `fidelity.check`、`fidelity.result` | 新实现，照《接口协议》6.9 和第 7 节 |

换算用的矩阵两边各有一份（`pdfium-sys` 的 `PageGeometry::display_matrix`，界面的 `pageSpace.ts`），四种旋转、可见区域不从原点开始都算。对不对是拿渲染结果核的：在旋转页和裁剪框页上把每个对象单独渲染出来，墨迹必须落在按矩阵换算出来的包围盒里；界面那一份的用例数据取自这次渲染的实际结果。

### 12.2 改一个对象，同页别的对象变了颜色（已修）

在界面上把提单样本（`freight-bl-composite.pdf`）里的一行字拖动了一下，页面右上角的 CMYK 色块变成了黑色，专色印章变成了灰色。

原因：改任何一个对象，PDFium 的生成器都要把整页的内容流重写一遍。原版生成器写不出 `k`、`K` 和专色（方案 2.1），没碰过的对象也跟着坏。保真校验（方案 2.3）本该拦住这样的页，但第 10 节实现的只有对象比对——个数、种类、包围盒——颜色变了看不出来。第 10 节末尾写过“像素比对还没有做”，后果比当时估计的重：不是“颜色空间被换成等价 RGB”这种看不出来的变化，而是用户眼前的颜色直接变了，没有任何提示。

现在校验分两步：先比对象；对象没变再比画面——重写前后各渲染一次（2 倍分辨率；大幅面页面降低倍率，最多 1600 万像素），判定规则用往返测试的那一套。不通过的页返回 3004，文档和版本号都不变。

对自制样本的影响（58 个文件，67 页；`magpdf-cli fidelity` 逐页统计）：

| PDFium 构建 | 能修改原有对象 | 只能叠加内容 | 其中：对象个数变了 / 位置变了 / 画面变了 |
|---|---|---|---|
| 原版预编译库（仓库默认） | 38 页（56.7%） | 29 页 | 9 / 5 / 15 |
| V03 修过生成器的构建 | 54 页（80.6%） | 13 页 | 9 / 2 / 2 |

- 只做对象比对时，原版预编译库下有 53 页放行。少掉的 15 页就是以前会被悄悄改坏的：提单、标签两份综合样本，以及 CMYK、ICC（两份）、专色、DeviceN、Indexed、Lab、CalRGB、图案填充（两份）、叠印、线型参数、亮度蒙版。
- V03 的构建下这 15 页里有 13 页能改（剩下线型参数和亮度蒙版两页），另外 `Tc`/`Tw`、文字定位、文字挖空三页也能改了。还不能改的 13 页：渐变 5 页、Type3 两页、内联图像、文字裁剪、标准 14 字体、未嵌入的 CJK 字体、线型参数、亮度蒙版。
- **仓库默认用的是原版预编译库，在它上面最接近真实单证的两份自制样本都只能叠加内容**（它们带 CMYK 色块和专色印章）。真实单证里这样的页占多少，要等真实样本到位才知道。主干默认链接哪个构建，要定。

还拦不住的：

- 颜色空间被换成画面相同的 RGB（灰度写成 `rg`）。对象和像素都一样，要靠操作符级比对（方案 2.3）。
- 默认隐藏的可选内容图层：像素比对时没有把图层全部打开（方案 2.3 要求打开）。
- 和别的页共用内容流的页：重写这一页会连带改掉那一页（方案 2.1），校验只比了这一页。
- 设了打开密码的文档：校验用的那一份文档是不带密码重新打开的，按代码看会打不开，整份文档的页都判成只能叠加内容。样本库里没有加密的文件，这一条没有验证过。现在界面也没有输密码的地方，等做密码的时候一起处理。

### 12.3 校验提前做，结论推给界面

只在第一次修改时校验的话，用户是先把对象拖走、再看着它弹回去、然后才知道这一页不能改。方案 2.3 要求“页面显示后，在引擎空闲时于后台完成校验”，照此做了：

- 一页渲染过瓦片之后排进后台队列；PDFium 线程的任务队列空了就校验一页，做完一页回头看有没有新任务。每页只校验一次。
- 结论经 `fidelity.result` 推送，`doc.snapshot` 的 `PageInfo.fidelity` 里也有（界面重新加载之后靠它接上）。查快照不触发校验。
- 修改命令执行前仍然自己校验：用户赶在后台校验之前动手，命令被拒绝，结论照样推送。
- `fidelity.check` 点名马上校验；已经校验过的页也回一条结论，调用方总能等到答复。页号不对时一页也不校验。

界面拿到结论之后的表现见 V12 报告 11.3：文档顶部出提示条，原有对象可以选中、不能拖动和删除，不弹对话框。

**校验用的那一份文档。** 校验要在另一份文档上试着重写，不能碰正在用的这份。原来的做法是把当前文档完整存一遍再读回来。这在第一次修改时才发生，文件小的时候看不出来；提前到“页面一显示就做”之后，100 MB 的扫描件打开后会卡 1 秒多。现在改成把打开文件时读进来的那块数据再解析一遍，两份文档共用同一块只读数据：要校验的页还没有被改过（改之前必须先过校验），文件原来的样子就是它现在的样子。

发布版引擎，开发机，100 MB 的文件（50 页，每页一张 2 MB 的灰度图，生成的）：

| | 后台校验第一次运行 | 这期间到的瓦片请求等了多久 | 引擎进程私有内存 |
|---|---|---|---|
| 存一遍再读回来 | 1.4 s | 1.4 s | 419 MB |
| 共用文件数据再解析 | 36 ms | 37 ms | 196 MB |

换了做法之后，两种 PDFium 构建下 67 页的结论逐页没有变化。

后台校验占 PDFium 线程的时间（发布版引擎，开发机，从第一块瓦片渲染完到结论发出，含建第二份文档，各 3–4 次）：

| 文件 | 第 1 页 | 之后的页 |
|---|---|---|
| `freight-bl-composite.pdf`（44 个对象） | 13–15 ms | — |
| A4，5000 个路径对象（生成的） | 29–32 ms | — |
| 300 页，每页 500 个对象（生成的） | 12–13 ms | 9–11 ms |
| 100 MB 扫描件（同上） | 28–36 ms | 18–21 ms |

校验一页的过程不能被打断，这期间到达的瓦片请求要等它做完：上面四份文件里是 13–41 ms，平时是 1–10 ms。方案 3.3 把后台保真校验排在最低优先级，这一点做到了；“耗时长的任务可以被高优先级任务打断”没有做到。对象很多、很复杂的真实页面校验一页要多久，手头没有样本，没有量。

### 12.4 修改的延迟

《接口协议》第 10 节有两条和修改有关的线。在端到端测试里量的：发布版，开发机，窗口 1440×900，页面按“适合页面”显示。选中一个对象之后用真实的方向键事件来回微移 30 次，每次等画面重画完再按下一次。计时从 `keydown` 开始；“收到 `doc.changed`”是界面的文档版本号变了的那一刻；“重画完”是视口里的瓦片都换成了新内容、并且画完一帧之后。

| 页面 | 运行次数 | 按键 → 收到 `doc.changed` | 按键 → 重画完 |
|---|---|---|---|
| `color-devicegray.pdf`，8 个对象 | 18 | 中位数 0.8–1.2 ms，P95 1.2–3.5 ms，最大 5.4 ms | 中位数 35–40 ms，P95 43–52 ms |
| A4，5000 个路径对象（生成的） | 25 | 中位数 9.5–12.2 ms，P95 14–25 ms，最大 29 ms | 中位数 68–82 ms，P95 83–103 ms |

对照两条线：

1. **修改命令从发出到收到 `doc.changed`，P95 小于 50 ms：在开发机上达到。** 5000 个对象的页 P95 是 14–25 ms。
2. **修改到受影响瓦片重绘完成小于 150 ms（A4，5000 个对象）：中位数和 P95 达到，个别样本超出。** 25 次运行里各次的最大值是 85–117 ms，但有两次各出现了一个 196 ms 的样本（750 个样本里的 2 个）。8 个对象的页上也有：18 次里一次出现 166 ms，没有留日志的几次里还见过 149 ms 和 201 ms 各一个。这些离群的样本是哪里来的没有查。

这两个数要打的折扣：

- 是开发机，不是参考机 R1。
- 5000 个对象是 5000 个纯色小方块，是最容易渲染的一种页面。有文字、图像、剪切的真实页面会慢。
- 现在每次修改都把这一页在视口里的瓦片全部重画，没有按改动的范围只重画一部分。窗口更大、放得更大的时候瓦片更多。
- “重画完”含等下一帧的时间（开发机的屏幕是 100 Hz）。

### 12.5 端到端测试

`apps/desktop/e2e/smoke.mjs` 在 11.6 的基础上加了修改这一段，用的都是真实的鼠标键盘事件：

1. 命令行打开两份 PDF，页面渲染出来；Ctrl + 滚轮放大；强制结束引擎后恢复显示（同 11.6）。
2. 只能叠加内容的页（提单样本，原版预编译库下）：没有人要求，引擎自己给出结论；提示条出现，文案和《交互设计》9.3 一字不差；对象能选中，拖的时候光标是“不行”、对象不跟着走；Delete、方向键不起作用；文档版本号不变，画面一个像素不变，不弹对话框。样本在 V03 的构建下能改，这时跳过这一段。
3. 能改的页（灰度色块样本）：点选；拖动之后对象到了该去的位置、画面变了；微移 30 次（12.4 的数字）；删除；撤销到头，对象回到原处、画面和修改之前一样；再多按一次撤销什么也不发生。
4. 关标签页；结束主进程后引擎退出。

失败时存一张截图，并把当时打开的文档、选区、提示打印出来。

测试和它查出来的问题都定下来之后一共跑了 50 次（不算故意让它失败的），48 次通过。两次失败：

- 一次是测试脚本向系统要空闲端口时被拒绝（`listen ENOBUFS`），桌面程序还没有启动。开发机上有别的程序占着一万多个 TCP 端口，套接字缓冲区偶尔会用光。现在这一步会重试。
- 一次没有留下完整输出，原因不明。之后才加上失败时留现场的做法。怀疑过是保真校验的结论不稳定，为此在引擎进程这一层把“打开 → 渲染 → 等后台校验”重复了 200 轮、命令行重复了 60 次，结论全部一致，没有找到支持这个怀疑的证据。

各次运行里：启动到第一屏瓦片到齐 0.7–0.9 秒；强制结束引擎到页面重新渲染完 0.20–0.28 秒；结束主进程后引擎退出一般是 50 ms，有一次是 0.86 秒。最后在入库的代码上重新构建，两种页面又各跑了一次，都通过。

这一段测试用真实的按键查出了界面上两个和修改无关的问题（焦点在文档标签页上时按 Delete 会把整份文档关掉；切换工作区会把打开的文档全部关掉），见 V12 报告 11.4。

### 12.6 《接口协议》还要补的

- `doc.snapshot` 不带 `pageIds` 时，实现里的 `PageInfo` 没有 `rotate` 和 `cropBox`：取这两样要加载页面，几百页的文档不能在打开时全做一遍。协议 5.3 把它们写成必有的字段，要改成“按 `pageIds` 请求时才有”，或者另给一个取页面几何信息的方法。
- `PageInfo` 里的宽高：实现给的是按旋转换好的显示宽高（`width`、`height`），协议写的是 `mediaBox`。界面排版只需要显示宽高。
- `ObjectSummary.pickable` 是新加的。界面在本地按包围盒做命中测试（悬停时每帧都要查，不能每次都问引擎），所以“点选时跳过哪些对象”这条规则的结果要引擎一起给出来。`obj.hitTest` 的 `top` 用的是同一个判断。
- `fidelity.check` 的应答是空的；已经校验过的页也回一条 `fidelity.result`；修改命令顺带校验的页也推送。这三点协议没写。
- `fidelity.result` 和修改命令的应答走两条路，先后没有保证（和 11.9 里 `render.tileReady` 的情况一样）。
- `fidelityReason` 现在是给技术支持看的一句话（“重新生成内容流后页面的画面变了”），不是给用户看的；给用户的说法由界面按《交互设计》9.3 统一写。协议第 8 节说 `message` 可以直接显示给用户，这里要区分开。
- 一条修改命令碰到几页时，现在是界面按页拆成几条发（各页的旋转不同，矩阵也就不同）。其中一页被拒绝时，前面几页已经改了，是几步撤销。`edit.transform` 的矩阵如果按页面的显示坐标给、由引擎换算，一条命令就能管几页，要么全做要么全不做。
