## 1. 目标

1. 在 Windows x64 上用上游推荐的流程（depot_tools、gn、ninja）构建我们自己的 PDFium 分支，产出**可动态链接**的 `pdfium.dll`，
   布局与 pdfium-binaries 完全一致，使 `pdfium-sys` 只改 `PDFIUM_PREBUILT_DIR` 就能在原版预编译库与自建库之间切换。
2. 按《工程规范》§6 建立分支布局（`upstream` 镜像上游，`mag/main` 叠加带前缀的独立提交），改动以 gn 参数开关实现，不改上游默认逻辑。
3. 提供可重复的脚本（同步、构建、整理产物）与 CI 草案，给出"CI 全新构建不超过 30 分钟"（P0 计划）和"60 分钟内"（《工程规范》§7）的判断。
4. 验证自建库与原版库行为一致：Rust 测试全部通过、同批样本渲染逐字节相同、bindgen 重新生成无差异。

## 2. 方法

### 2.1 分支与改动

- 上游：`https://pdfium.googlesource.com/pdfium.git`，稳定分支 `chromium/8138`（PDFium 159.0.8138.0，与 `third_party/pdfium-prebuilt` 同版本）。
- 本地 `upstream` 分支跟踪 `origin/chromium/8138`（`5f092b5299`）；`mag/main` 从它创建，叠加一个 `[mag-local]` 提交。
- 共享库改动走 **gn 参数**而不是改目标类型或打头文件补丁（pdfium-binaries 的做法）：
  - `pdfium.gni`：新增 `pdf_is_shared_lib = false`，并断言它与 `is_component_build`、`pdf_is_complete_lib` 互斥；
  - `BUILD.gn`：`pdf_is_shared_lib` 为真时 `pdfium` 目标用 `shared_library`（否则仍是 `component`），`pdfium_public_config` 定义 `FPDF_SHARED_LIBRARY`；
  - `public/fpdfview.h`：`FPDF_EXPORT` 的条件由 `defined(COMPONENT_BUILD)` 扩成 `defined(COMPONENT_BUILD) || defined(FPDF_SHARED_LIBRARY)`。
  - 默认值下三处改动都不生效，上游行为不变；上游 clang-format 风格；3 个文件 +28/−4 行。
- Chromium 的 `build/` 是 DEPS 子仓库，不能放进 PDFium 分支提交，对它的 3 处适配（见第 5 节）保存为主仓库
  `third_party/pdfium/patches/build/0001-win-sdk-26100-without-debugging-tools.patch`，由 `apply-patches.ps1` 幂等应用。

### 2.2 构建参数

以 pdfium-binaries 发布的 `args.gn` 为基础（`pdf_is_standalone=true`、`is_component_build=false`、`pdf_enable_v8/xfa=false`、
`pdf_use_partition_alloc=false`、`treat_warnings_as_errors=false`、x64/win），另加：

```
pdf_is_shared_lib = true          # 本次 [mag-local] 提交
symbol_level = 1                  # Release 带行号级符号，产出 pdfium.dll.pdb
use_siso = false                  # PDFium .gn 默认 use_siso=true，本地与 CI 都用 ninja 直连
use_remoteexec = false
clang_use_chrome_plugins = false
```

工具链：Visual Studio 2022 **Build Tools**（MSVC 14.44.35207，Windows SDK 10.0.26100）+ DEPS 自带的 clang
（llvmorg-24-init-14453-ge063be79-1）、gn 2612、ninja 1.12.1、cpython3；`DEPOT_TOOLS_WIN_TOOLCHAIN=0`。
`.gclient` 用 `checkout_configuration=minimal`、`checkout_v8=False`，并排除 Windows 上无条件下载但用不到的
`third_party/rust-toolchain`（427 MB 下载、2.8 GB 解压）与 `third_party/siso/cipd`（64 MB）。

### 2.3 脚本（`third_party/pdfium/`）

| 文件 | 作用 |
|---|---|
| `sync.ps1` | 从零同步：克隆 depot_tools、写 `.gclient`、克隆 PDFium、建 `upstream`/`mag/main`（远程仓库建好前用 `patches/pdfium/*.patch` `git am` 重放）、`gclient sync`、打 `build/` 补丁；支持 `-Proxy`、`-NoHistory`、`-NoSync`（离线）、`-DepsOnly`（CI）、`-MagRemote` |
| `build.ps1` | 设环境变量 → 打补丁 → 由 `args/<config>.gn` 生成 `args.gn` → `gn gen` → `ninja -j N pdfium pdfium_test pdfium_unittests` → 整理 `dist/` |
| `apply-patches.ps1` | `patches/<子仓库>/` 下补丁的幂等应用/检查（CRLF 检出自动规范为 LF） |
| `args/release.gn`、`args/debug.gn` | 参数模板 |
| `upstream-branch.txt` | 钉住 `chromium/8138`，版本号推导与同步都以它为准 |
| `ci/build-pdfium.yml` | `magpdf-pdfium` 仓库的 GitHub Actions 草案 |

`dist/` 的整理规则：`bin/pdfium.dll(+.pdb)`、`lib/pdfium.dll.lib`、`include/*.h`、`include/cpp/*.h`、`VERSION`、`args.gn`、`LICENSE`、
`licenses/`、`PDFiumConfig.cmake`，另加 `BUILD-INFO.txt`（提交、分支、工具链版本、补丁、构建耗时）。头文件做与 pdfium-binaries 相同的后处理
（`FPDF_EXPORT` 去掉条件编译、`include/cpp` 内的 `#include "public/..."` 改相对路径），`licenses/` 按 ninja 依赖图收集**实际链进** `pdfium.dll`
的第三方组件。`VERSION` 按 pdfium-binaries 格式：`MAJOR`=Chromium 里程碑（在线查 `refs/branch-heads/NNNN/chrome/VERSION`，离线用内置对照表），
`BUILD`=分支号，`MINOR`/`PATCH`=0。

### 2.4 验证方法

1. `$env:PDFIUM_PREBUILT_DIR=<out>\dist`，独立 `CARGO_TARGET_DIR`，跑 `cargo test -p pdfium-sys`、`cargo test --workspace`；核对测试可执行文件旁的 `pdfium.dll` 哈希确为自建版本。
2. 10 个样本分别用预编译库和自建库 `cargo run -q -p magpdf-cli -- render <pdf> --page 1 --dpi 144 [--annots] --output <png>`，Python 逐字节比较 PNG（不同再解码统计像素差）。
3. `engine/pdfium-sys/regen-bindings.ps1 -IncludeDir <dist>\include` 重新生成绑定，与提交的 `src/bindings.rs` 比较后恢复原文件（不提交）。
4. `dumpbin` 对比导出表、依赖 DLL、PE 标志；`gn clean` 后全新构建计时；改一个 `.cpp` 的增量计时；`pdfium_unittests` 全量。
5. 在 worktree 用默认预编译库跑 `cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`。

### 4.4 CI 耗时估算与建议

本机数据：ninja 全新构建墙上 1 分 41 秒、CPU 约 20 分钟（16 线程、高频桌面 CPU）。GitHub `windows-latest` 为 4 vCPU，
单核性能约为本机的一半、磁盘与 Defender 开销更大，估算：

| 阶段 | 冷缓存 | 热缓存（depot_tools + DEPS 命中） |
|---|---|---|
| 检出 PDFium 分支 + 脚本 | 1 分钟 | 1 分钟 |
| depot_tools 克隆与自举 | 1–2 分钟 | 0.5 分钟 |
| `gclient sync --no-history`（排除 rust-toolchain / siso 后约 1 GB：clang 277 MB、cpython3 191 MB、test_fonts 58 MB、git 依赖） | 5–8 分钟 | 1–2 分钟 |
| `gn gen` + ninja（1494 步） | 12–18 分钟 | 同左 |
| `pdfium_unittests` | < 1 分钟 | < 1 分钟 |
| 打包 40 MB、上传 | < 1 分钟 | < 1 分钟 |
| **合计** | **约 20–30 分钟** | **约 15–22 分钟** |

判断：**《工程规范》§7 的 60 分钟内有充足余量；P0 计划的"全新构建不超过 30 分钟"大概率满足但余量小**，需要仓库建立后用 `ci/build-pdfium.yml` 实测一次。
建议：

1. 保持 `actions/cache` 缓存 depot_tools 与 DEPS 管理目录（草案已按 `.gclient_entries` 列出完全由 DEPS 管理的目录，不能整目录缓存 `third_party/`）。
2. 把 `rust-toolchain`、`siso` 从 `.gclient` 排除（已做；仅 rust-toolchain 就省 427 MB 下载、2.8 GB 解压，`gn gen` 已验证不需要它）。
3. 若实测超过 30 分钟：优先接 `sccache`（Chromium 构建支持 `cc_wrapper`，热缓存可把 ninja 阶段压到几分钟），其次用 GitHub 8 核付费 runner（约缩短一半），
   或把引擎组一台开发机注册为自托管 runner（本机全流程不到 5 分钟，但要承担维护与安全隔离）。
4. PDFium 流水线只在 `magpdf-pdfium` 有提交时触发（每季度同步 + 少量修复），不在主仓库 PR 路径上，所以 20–30 分钟对开发节奏影响很小；其他组始终用预编译库。

"其他组成员按说明 30 分钟内跑通示例程序"：其他组走 `scripts/fetch-pdfium-prebuilt.ps1`（或以后下载我们的 Release zip）+ `cargo test --workspace`，
本机从零编译工作区不到 1 分钟，满足。

## 5. 踩过的坑与处理

| 问题 | 原因 | 处理 |
|---|---|---|
| `gn gen`: `No supported Visual Studio can be found` | `build/vs_toolchain.py` 只认环境变量 `vs2022_install`，`GYP_MSVS_VERSION`/`GYP_MSVS_OVERRIDE_PATH` 单独设都不够 | `build.ps1` 用 vswhere 找到 Build Tools 后同时设 `vs2022_install`、`GYP_MSVS_OVERRIDE_PATH`、`WINDOWSSDKDIR` |
| `gn gen`: SDK `10.0.28000.0` 的 Include 目录不存在 | Chromium `build/` 把 SDK 版本写死为 Win11 预览 SDK，Build Tools 装的是 26100 | `build/` 补丁：`SDK_VERSION` 可由 `WINDOWS_SDK_VERSION` 覆盖，脚本默认取本机最新 SDK |
| `gn gen`: 找不到 `dbghelp.dll`（"Debugging Tools for Windows"） | Chromium 要把 SDK Debuggers 的 dbghelp.dll 复制到 out 目录，Build Tools 默认不装该 SDK 组件 | `build/` 补丁：未安装时跳过（PDFium 不用它） |
| 编译 `fileapi.h`: `FILE_INFO_BY_HANDLE_CLASS` 未定义 | `NTDDI_VERSION=NTDDI_WIN11_BR` 只在 SDK 28000+ 定义 | `build/` 补丁：改为 `NTDDI_WIN11_GE` |
| 默认走 siso | PDFium `.gn` 的 `default_args` 有 `use_siso = true` | `args/*.gn` 设 `use_siso=false`、`use_remoteexec=false`；不要用 autoninja |
| `gclient sync` 的 CIPD/hooks 失败 | 本机代理只建立 CONNECT 隧道、TLS 握手失败（github/googlesource/GCS 都不通，百度正常），`cipd` 卡死需手工结束 | 核对 git 依赖已全部在 8138 对应修订，先行构建；CIPD/hooks 与 `pdfium-binaries` 参考克隆留待代理恢复（见第 6 节） |
| `gn clean` 清掉了 out 目录里我放的日志 | `gn clean` 删除 out 下所有非 gn 文件 | 构建日志改放 out 的上一级 |
| **`testing/resources` 中 276/346 个 PDF 被改成 CRLF** | 本机全局 `core.autocrlf=true`；PDFium 没有用 `.gitattributes` 把 `*.pdf` 标成 binary，git 把不含 NUL 的 PDF 当文本 | 取样用 `git cat-file blob`；已在脚本与 README 中要求 PDFium 检出 `core.autocrlf=false`；**需告知 V02 负责人**（他们正在读这个目录） |
| `git am` 丢掉 `[mag-local]` 前缀 | `git am` 默认把方括号前缀当 `[PATCH]` 一起剥掉 | `--keep-non-patch` |
| 相邻 `chromium/NNNN` 分支头同一个提交 | 8138–8141 都指向 `5f092b5299`，按"可达的最大分支号"会推成 8141 | 版本推导优先采用 `upstream-branch.txt` 钉住的分支号 |
| PowerShell `Set-Content` 写 CRLF、`-Encoding ascii` 吞中文 | Windows 默认行为 | 统一用 `WriteLf`（UTF-8 无 BOM、LF），`VERSION`/`PDFiumConfig.cmake` 才能与原版逐字节一致 |
| `.patch` 文件在 autocrlf 检出下变 CRLF，`git apply` 失败 | 主仓库 `text=auto` 未对 `*.patch` 特殊处理 | `apply-patches.ps1` 先规范成 LF 再应用；建议主仓库 `.gitattributes` 加 `*.patch text eol=lf` |
| `third_party/rust-toolchain` 2.8 GB | DEPS 对 Windows 无条件下载，与 `checkout_rust` 无关 | `.gclient` `custom_deps` 置 None，`gn gen` 验证无影响 |

## 6. 结论

- **V01 通过**。PDFium 分支可用上游流程在 Build Tools 环境构建成动态链接的 `pdfium.dll`，产物布局、导出表、头文件与 pdfium-binaries 一致，
  `pdfium-sys` 零改动切换；全新构建 1 分 41 秒（本机），10 样本渲染逐字节一致，Rust 测试与 1154/1158 个 C++ 单元测试通过（4 个为环境问题）。
- 共享库改动只需一个 28 行的 `[mag-local]` 提交和 3 处对 Chromium `build/` 的本地适配，维护负担小；后续季度同步时主要风险在 `build/` 补丁。
- CI 60 分钟目标无风险；30 分钟目标大概率满足，待实测；已给出三级加速方案。

## 8. 对方案的修改建议

1. **《方案》第 12 节 / 《工程规范》§6**：明确 pdfium.dll 用 gn 参数 `pdf_is_shared_lib` 以 `shared_library` + 静态 CRT 构建（非 component build），
   预编译包布局与 pdfium-binaries 相同并额外带 PDB；`VERSION` 沿用 pdfium-binaries 格式，`pdfium-sys` 以此解析版本。
2. **《工程规范》§6** 增加两条：(a) 对 DEPS 子仓库（`build/` 等）的改动以 `third_party/pdfium/patches/<子仓库>/` 补丁保存在主仓库，季度同步时
   必须 `apply-patches.ps1 -Check`；(b) 当前跟踪的上游分支写在 `third_party/pdfium/upstream-branch.txt`，同步上游时先改它。
3. **《工程规范》§1 或开发环境说明**：PDFium 检出必须 `core.autocrlf=false`（或在检出后 `git -c core.autocrlf=false checkout -- testing/resources`）；
   主仓库 `.gitattributes` 增加 `*.patch text eol=lf`。
4. **《P0 技术验证计划》V01 通过线**："CI 全新构建不超过 30 分钟"建议写明测量条件（`windows-latest` 4 vCPU、无缓存、含 `gclient sync`），并补充
   "热缓存 ≤ 20 分钟"的日常目标；真实数据在 `magpdf-pdfium` 建仓后的首次流水线补入本报告。
5. **《工程规范》§7 PDFium 流水线**：产物命名 `pdfium-win-x64-<MAJOR.MINOR.BUILD.PATCH>.zip`，`v*` 标签发 Release；`scripts/fetch-pdfium-prebuilt.ps1`
   在 Release 可用后增加"从我们的 Release 拉取"的开关，让其他组可以在原版与分支预编译库之间切换。
6. **`pdfium-sys`（给引擎组其他成员）**：本次不需要改代码。可选改进：`build.rs` 顺带读取 `dist/BUILD-INFO.txt` 的 `pdfium_commit`，在
   `Library::linked_version()` 或 `magpdf-cli info` 中显示，便于以后核对崩溃转储对应的构建。
