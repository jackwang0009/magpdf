每帧的执行顺序（`CanvasController.render`）：`computeRenderPlan()` → 把缺失瓦片优先队列交给 `TileScheduler` → `GlTileRenderer.draw(plan)`（已就绪的瓦片 + 跨档回退 + 页底色）→ `drawOverlay(...)`。渲染计划里的任何数字都可以在不需要浏览器的情况下断言。

### 1.2 每帧渲染计划（`renderPlan.ts`）

输入：`PageLayout`、视图 `{zoom, x, y}`、视口 CSS 尺寸、`devicePixelRatio`、`has(id)` 缓存查询。
输出：

- `pages`：与视口相交的页（`PageLayout.visiblePages` 二分，300 页是 O(log n)）；
- `targetLevel`：显示比例（zoom × 96/72 × DPR）对应的最小瓦片档（`pickLevel`，13 档，√2 递进，宁可多渲染不放大模糊）；
- `tiles`：目标档已缓存的瓦片四边形（设备像素坐标）；
- `fallback`：目标档缺失时，从更粗档位取已缓存瓦片按原比例拉伸（先粗后细，保证不出现白块）；
- `missing`：需要请求的瓦片，按“离视口中心的距离 / 档位”排队；
- `prefetch`：视口上下各一屏的瓦片，优先级低于缺失。

### 1.3 工具与选区状态机

`selectTool` 的状态：`idle → pressed → (marquee | moving | pressedHandle → scaling | rotating)`，全部转移是纯函数，返回 `ToolEffect[]`（`setSelection`、`moveObjects`、`resizeObjects`、`deleteObjects`、`setView`、`overlay`、`cursor`）。点击、Shift 加选/减选、框选（相交/包含两种模式）、拖动移动、8 控制点缩放、角外侧旋转、方向键微移（0.1 mm，Shift ×10）、Delete、Esc 都由状态机完成。

`ToolManager` 的补充约定：

- 按住 Space 临时切抓手，抬起后恢复；若拖动中抬起按键，等指针抬起再恢复；
- 中键拖动平移，不改当前工具；
- 同一次手势内（`pointerdown` 到 `pointerup`）工具自己改过的选区立刻对后续事件生效（`selectionOverride`），不依赖 store 下一帧渲染；store 里的选区被外部改动（图层面板、删除对象）时调用 `forgetSelectionOverride()` 作废。

## 2. 工作区与布局

内置两个工作区（`workspace/workspaces.ts`），切换在「窗口」菜单，选择会记在 `localStorage`：

| 工作区 | 组件面板 | 右侧 | 用途 |
| --- | --- | --- | --- |
| 货代单证（默认） | 展开 240px（可拖 200–320） | 右上：属性、字符、段落；右下：图层、页面、历史记录、导航器 | 界面图 8.2 |
| 基础 | 折叠成 32px 图标条 | 一个组：属性、图层、页面、历史记录 | 通用文档 |

布局细节：

- 工具栏**不是** dockview 面板，是外壳顶部的一行普通横条（菜单栏下方、与选项栏同一行 36px）：7 个工具横排在左，工具选项跟在后面，填充/描边色块在行尾；它参与外壳布局、不浮动、不盖住组件面板或画布。旧版把它做成 dockview 浮动面板（宽 40，贴左边距 0 / 上边距 40）会盖住东西，已改掉；
- 右侧 32px 图标条是网格里的一个固定宽度组（`maximumWidth = minimumWidth = 32`、隐藏标签头），点图标把对应面板浮到右侧；
- 组件面板折叠时组宽锁 32px、`locked: 'no-drop-target'`，展开时约束 200–320px；右侧组（右上、右下、基础的右侧组）同样约束 200–320px，拖分隔条不能超出这个范围；
- 容器尺寸变化由 `ResizeObserver` 调 `api.layout(w, h)`（`disableAutoResizing`、`proportionalLayout: false`），文档区吸收宽高变化，两侧保持宽度；
- 布局变化 500ms 防抖后 `captureWorkspace()` 回读并写入 `localStorage`（去掉文档面板和图标条；旧版浮动工具栏的残留也会去掉），下次启动恢复；保存时网格里也不留文档面板的视图，视图已空的非结构组在保存和加载时都丢弃（`cleanDockviewLayout()`），只保留组件、文档、右侧这几个结构组；两侧宽度超出 200–320px 的保存值在保存和加载时都收进范围（`clampSideWidths()`），下次加载自动生效；
- 「窗口 → 复位工作区」清掉保存值并回到内置布局；「窗口 → 切换组件面板」等价 Tab 键隐藏/显示整个工作台。

> 说明：切换工作区时 `fromJSON` 之后需要重新登记右侧图标条，`applyWorkspace()` 里用 `ensureStrip()` 保证它一定存在。旧版的 `ensureToolbar()`（浮动工具栏）已删除：工作区布局版本从 1 升到 2，旧版 v1 保存值解析为无效、自动回落到内置布局；`applyWorkspace()` 还会在 `fromJSON` 之后丢弃残留的工具栏面板。加载时 `applyWorkspace()` 先用 `cleanDockviewLayout()` 清掉保存值里残留的文档视图和空组再 `fromJSON`：dockview 8.8.3 在 `fromJSON` 时会跳过面板表里没有的视图、把组留空，`closeEmptyGroups={false}` 时空组不自动消失，只显示“没有打开的文档”水印，旧保存值里的空组会在刷新后复活，所以保存和加载两边都要清。P0 没有做“拖出/合并面板”的自定义布局测试，但 dockview 自身的拖放是开启的，保存的 JSON 会包含浮动组。

## 5. 帧时间：方法与数据

### 5.1 方法

- 构建：`pnpm dev`（Vite 8.3.6，未压缩，React 开发构建），Microsoft Edge 156（`channel: 'msedge'`），窗口 1600×1000，DPR = 1，`--disable-background-timer-throttling`。
- 文档：「文件 → 新建 → 300 页测试文档」（`createMockDocument` 的 `report` 模板，每页约 60 个文字/路径/图像占位对象，A4）。
- 视口：货代单证工作区、1600×1000 窗口下文档区约 380×863 CSS px；读屏缩放 = `zoom × 96/72 ≈ 1.6`（A4 页宽略超出视口）。
- 瓦片：目标档按 `pxPerPt = zoom × 96/72 × DPR` 选取（缩放基准约 2.13 → 档 7，256px 瓦片），DOM 上只有一块 WebGL2 画布 + 一块等大 2D 叠加层。
- 每个阶段连续 240 帧，`requestAnimationFrame` 中先执行操作（平移/缩放/跳页）、`invalidate()` 再等下一帧；`FrameStats` 记录相邻帧间隔与每帧脚本工作时间（`performance.now()` 前后差）。
- 统计：分位数用最近秩法（`percentile()`），长帧阈值 16.7 ms；`intervalMax` 是该阶段最大帧间隔，`workMax` 是最大脚本时间。
- 开关：状态栏右侧按钮 /「视图 → 显示帧时间」，最近 240 帧的 P50/P95/脚本 P95 实时显示；「视图 → 运行性能基准」或控制台 `__magpdf.benchmark(240)` 跑完整 4 阶段并把结果 JSON 打到控制台。基准入口只在开发构建（`import.meta.env.DEV !== false`）挂到 `window.__magpdf`。

阶段定义（`canvas/benchmark.ts`）：

| 阶段 | 操作 |
| --- | --- |
| `pan-slow` | 读屏缩放下，每帧 ±12 px 上下交替滚动（模拟滚轮/触控板） |
| `pan-fast` | 每帧向上 80 px，瓦片持续缺失，考验渐进显示与调度 |
| `zoom` | 以视口中心为锚点，1/4 ↔ 4 倍正弦往返两次（每帧 `zoomAtPoint`） |
| `jump` | 每帧 `scrollToPage` 跳到后 6 页（页面面板点击、拖动滚动条），缩放不变 |

### 5.2 环境与干扰

- CPU：AMD Ryzen 7 9800X3D；测量期间系统总 CPU 占用 31%–44%（另有 agent 在编译，`node` 进程 15 个），GPU 为 Edge 内置软件/硬件混合渲染（`RENDERER = WebKit WebGL`）。
- 浏览器输出：控制台 0 条 error / warning（含 React 嵌套按钮警告与 favicon 404 均已修复）。
- 两次测量（较早一次 CPU 32%–67%，正式一次 31%–44%）各阶段 P50/P95 相差不超过 0.2 ms，下面记录正式一次；本机刷新率 100 Hz（P50 = 10.0 ms 即“每帧都赶上了”）。

### 5.3 结果（300 页，240 帧/阶段）

| 阶段 | 样本 | 帧间隔 P50 | 帧间隔 P95 | 帧间隔最大 | 脚本 P50 | 脚本 P95 | 脚本最大 | 长帧(>16.7ms) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| pan-slow | 239 | 10.0 ms | 10.1 ms | 20.1 ms | 0.3 ms | 1.5 ms | 8.1 ms | 7 |
| pan-fast | 239 | 10.0 ms | 10.1 ms | 30.0 ms | 0.3 ms | 2.6 ms | 10.9 ms | 7 |
| zoom | 239 | 10.0 ms | 10.1 ms | 20.1 ms | 0.3 ms | 1.9 ms | 8.0 ms | 8 |
| jump | 239 | 10.0 ms | 19.9 ms | 40.0 ms | 0.3 ms | 8.7 ms | 12.0 ms | 12 |

瓦片统计：完成 627 次渲染、取消 276 次、过期丢弃 0 次；缓存 598 块 / 96 MB（上限 96 MB，LRU）；MockTileProvider 平均每块 0.06 ms。

解读：

- 平移与缩放：P95 10.1 ms，脚本 P95 ≤ 2.6 ms，远低于 60 fps 的 16.7 ms 预算；长帧 7–8 次集中在阶段切换的第一帧（新一屏瓦片排队）。
- 跳页：每帧换到全新一屏，P95 19.9 ms 说明约 5% 的帧掉到 10 Hz 档；脚本 P95 8.7 ms 是排队的 20–24 块瓦片在 Mock 渲染上的时间，真实引擎（PDFium 单线程、方案 3.3）下这部分会迁移到引擎进程，界面侧应只显示缩略图/白底占位，因此正式接入时以“不阻塞主线程”为准，实测数值不能直接外推。
- 真实 GL 纹理上传在浏览器里无法从 JS 侧计时，故表中“脚本时间”不含 GPU 上传与合成；Mock 的 0.06 ms/块只代表 2D 画位图的开销。

复现：`pnpm dev` → 打开 300 页测试文档 → 控制台执行 `await __magpdf.benchmark(240)`，或「视图 → 运行性能基准」在对话框里看表并「复制 JSON」。

## 6. TileProvider 接口（给 V06 引擎对接）

`packages/editor/src/canvas/tileProvider.ts`。画布**只**通过这个接口取位图，Mock 与真实引擎共用同一套调度与缓存。

```ts
interface TileRequest {
  page: number;            // 页号，从 0 开始
  level: number;           // 缩放档 0..12，pxPerPt = 96/72 × 2^((level-6)/2)。缓冲缓存与纹理都按 (page,level,tx,ty) 索引
  pxPerPt: number;         // 该档的渲染分辨率（设备像素/pt），level 的冗余参数，便于实现直接取 dpi = pxPerPt × 72
  tx: number; ty: number;  // 瓦片在整页位图中的列、行（0 起）
  tileSize: number;        // 瓦片边长，当前 256（设备像素）。边缘瓦片 = 页面剩余部分
  pixelRect: Rect;         // 该瓦片在整页位图中的像素矩形 {x,y,width,height}；= {tx*256, ty*256, ≤256, ≤256}
  pageRect: Rect;          // 同一区域换算到页面坐标（pt），便于引擎直接按 pt 渲染
  documentVersion: number; // 调度器当前的文档版本；与结果返回时版本不一致会被丢弃
  signal: AbortSignal;     // 取消信号
}

interface TileResult {
  width: number;           // 必须等于 pixelRect.width
  height: number;          // 必须等于 pixelRect.height
  pixels: ImageBitmap | { data: Uint8Array | Uint8ClampedArray; width; height }; // 不透明 RGBA，行主序、无行填充
}

interface TileProvider {
  renderTile(request: TileRequest): Promise<TileResult>;
  readonly concurrency?: number; // 建议 1–2（PDFium 串行）；排队放在界面侧，视图移动后能按新优先级重排
  dispose?(): void;
}
```

调用约定（V06 实现时必须遵守）：

1. **代数**：`documentVersion` 在编辑提交后递增（`DocumentSnapshot.version`）。调度器在每个批次（每次 `setWanted`）记录当时的版本，返回时版本已变则直接释放结果、计入 `stale`，不进缓存。实现不需要自己比较版本，但**不要**缓存上次结果冒充新版本。
2. **取消**：`signal` 在三种情况触发——瓦片离开“想要的列表”（视图移走）、该页被 `invalidatePage`（对象修改）、调度器销毁。实现应尽早放弃计算并以 `name === 'AbortError'` 的错误拒绝（`AbortError` / `isAbortError()` 已导出）；即使拒绝得晚，调度器也会丢弃并释放像素。若引擎侧是消息队列，取消消息只需要是“丢弃该 token 的结果”，不必真正中断 PDFium。
3. **尺寸**：结果宽高必须严格等于 `pixelRect` 的宽高，否则渲染器按最近邻缩放会出现接缝；`pixels` 用 `ImageBitmap`（推荐，`createImageBitmap` 后渲染器直接 `texImage2D`，用完 `close()`）或裸 RGBA 都可以。
4. **并发**：界面侧默认并发 = `provider.concurrency ?? 3`；PDFium 单线程时给 1 或 2，把排队留在界面（`TileScheduler` 每次视图变化都会重排队列，慢的旧请求先被取消）。
5. **视口与预取**：`renderPlan` 只请求可见页的缺失瓦片与上下各一屏的预取瓦片；实现可以据此估算内存。缓存上限 96 MB（LRU，按字节），淘汰时释放 GPU 纹理，`ImageBitmap` 需 `close()`（`releasePixels()` 已封装）。
6. **失败**：`renderTile` 抛出非 Abort 错误时调度器记 `failed` 并在控制台输出 `瓦片渲染失败 <id>`，不会让该瓦片永久卡住——下一次 `setWanted` 会重新请求。建议引擎对同一瓦片连续失败 3 次后返回白底位图，避免死循环。
7. **页面尺寸变化**：页面尺寸来自 `DocumentSnapshot.pages[i]`（pt），若编辑改了页尺寸，调用 `invalidatePage(i)` 清缓存，调度器下次会按新 `pixelRect` 重新请求。

替换方式：`CanvasController` 构造时传入 `TileProvider`；当前 `TileCanvas` 用 `MockTileProvider`。V06 只需实现 `renderTile` 并在创建控制器时传入，无需改渲染器、缓存、调度器与叠加层。
