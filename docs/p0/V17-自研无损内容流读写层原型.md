## 1. 目标

验证「PDFium 只负责解析、渲染和命中测试，内容流由自研 Rust 层读写」这条备选路径是否成立：

1. 不修改任何对象直接保存：内容流应与原文件逐字节相同（目标：相同流 ≥ 99%）。
2. 随机修改约 5% 的对象（移动、改色、删除）后保存，与按同一组编辑生成的期望结果做像素比对（判定规则同 V02）；无差异页面比例不低于 V03。
3. 统计操作符与页面对象对不上的页面比例；对不上的页面应退回整条内容流重写再校验（目标：未匹配 / 回退页 ≤ 2%）。
4. 记录读入、映射、保存、渲染耗时，以及修改后文件的字节变化量。

P0 复盘标准（计划第 6 节）：V17 达到目标值且随机修改后的无差异比例高于 V03，才把自研读写层定为 P1 默认做法；否则 P1 继续修补 PDFium 生成器，本原型存档。

## 2. 方法

### 2.1 原型行为（本轮已具备）

- 读入时保留原内容流操作符及其字节位置，并按 PDFium 页面对象规则做顺序对应。
- 保存时只重写改过的对象，其余字节尽量原样保留；改动与新增由自研序列化写出，不经过 PDFium 内容流生成器。
- 删除计划使用 `draw_start`；`Transform` 保持 6 个 double 的矩阵形式。
- 实验驱动 `experiment/run.rs`：在同一 `Page` 句柄上应用编辑后立刻 `mark_all_and_regenerate`。PDFium 若先 `ClosePage` 再生成期望页，编辑会丢失（此前 modify 冒烟因此失败，已从备份恢复并修补）。

### 2.2 对比实验

命令均为 `magpdf-cli content-roundtrip`，输入 `tests/corpus/synthetic`，`--source synthetic`，`--jobs 2`，`--seed 20261109`，`--scale 2.0`。JSON 写到工作树 `tests/out/v17/`：

|---|---|---|---|
| 1 / 3 / 4（恒等往返） | `exp1-roundtrip.json` | `roundtrip`（`modify_ratio=0`） | 不修改即保存；看流是否逐字节相同、未匹配页、耗时与字节 |
| 2（随机修改） | `exp2-modify.json` | `modify`，`modify_ratio=0.05` | 随机改约 5% 对象后保存，与期望渲染像素比对 |
| 2 + 对照 | `exp2-modify-control.json` | `modify` + `--control` | 同上，并跑 PDFium 生成器对照 |
| 对照往返 | `exp-control-roundtrip.json` | `roundtrip` + `--control` | 恒等路径上的 PDFium 生成器对照 |

脚本：`D:\workspace\magpdf\v03r2-tmp\run-v17-corpus.ps1`。日志里 `Tee-Object` 曾把 CLI 的信息流写成 UTF-16，终端表格出现乱码；**结论以 UTF-8 JSON 为准**（Python 汇总）。四次退出码：`EXP1_EXIT=0`、`EXP2_EXIT=0`、`EXP2C_EXIT=0`、`EXPC_EXIT=0`。

像素比对的期望路径与自研保存路径使用同一组随机编辑；对照（`--control`）走 PDFium `GenerateContent` 一类整页重写，作为本轮可得到的生成器基线。本工作树没有已定稿的 V03 报告数字，故「不低于 V03」只能先与这次 `--control` 比较，并注明缺口。

### 4.2 方法 1：不修改即保存，内容流是否逐字节相同

- **56 / 58 = 96.55%，低于目标 99%。**
- 唯一拉低该比例的样本是 `struct-empty-pages.pdf`：4 条内容流中 2 条不一致（`streams_identical=2`，`bytes_original=38`，`bytes_saved=0`）。内容流总字节 52985→52947 的 38 字节差额全部来自这份文件。
- 其余成功打开的文件，保存后的**文件级**字节合计与原文相同（104586，增量 0）。`struct-xref-missing.pdf` 打不开，不参与流比较。
- 恒等模式 `render_us=0`、`pages_passed=0`、`page_records` 为空，本轮**没有**对「不修改保存后的渲染结果」做像素统计；像素数字见方法 2 与对照往返。

### 4.3 方法 2：随机修改 5% 后的像素保真

- 实际改动 129 / 5027 条操作符（2.57%）。比例低于 5%，是因为随机抽的是可映射对象，不是全部操作符；部分操作符不可编辑。
- CLI / `total.pages_passed`：**51 / 58 = 87.93%**（分母为匹配页）。`page_records` 则是 51 个 `pass` + 15 个 `diff`，合计 66，覆盖全部页面。
- 15 个出现 `diff` 的都是**已匹配**的单页文件（`fallback_pages=0`，`pages_matched=1`）：

  `freight-bl-composite.pdf`（改 2 个操作符）、`gs-line-params.pdf`、`gs-smask-luminosity.pdf`、`shading-axial.pdf`、`shading-functions.pdf`、`shading-mesh.pdf`、`shading-radial.pdf`、`shading-stitching-background.pdf`、`struct-cm-nested-transforms.pdf`、`struct-image-xobject-masks.pdf`、`struct-incremental-update.pdf`、`struct-many-objects-clip.pdf`（改 75 个操作符）、`text-cid-cjk-nonembedded.pdf`、`text-standard14.pdf`、`text-type3.pdf`。

- 8 个回退页至少有一部分在 `page_records` 里记为 `pass`（例如 `struct-inline-image.pdf`、`text-clip-modes.pdf`、`text-type3-multistream.pdf`）。它们并未完成对象对应，却可能仍按未改写的原始页面渲染，因此「pass」不能理解为「回退重写后保真通过」。
- 若只数「匹配页里的像素 diff」，则是 15 / 58 失败（通过率 43 / 58 = 74.14%）。报告同时给出 CLI 的 87.93% 与这一口径，避免只看一个百分比。
- **同进程 PDFium 对照**（`--control`，修改模式）：**63 / 66 = 95.45%**。对照失败的 3 页恰为回退样本：`struct-inline-image.pdf`、`text-clip-modes.pdf`、`text-type3-multistream.pdf`。上面 15 个 V17 `diff` 样本在对照里全部 `pages_passed=1`。也就是说，同一组 5% 编辑下，自研保存的像素结果差于 PDFium 生成器对照。
- 本工作树**没有**可引用的 V03 定稿无差异率。就「是否不差于生成器基线」而言，当前合成集上的答案是：**差于本次 `--control`**。
- `verify_failures` 四个 JSON 均为 0，`verify_us` 均为 0；像素对错写在 `page_records`，没有按页列出失败详情，也没有写出 Diff PNG。

### 4.4 方法 3：对不上的页面 / 回退率

- **8 / 66 = 12.12%，高于目标 2%。** `unmatched_files=0`（没有整文件被标成 unmatched），回退发生在页级。
- 原因计数（一份页面可记两条原因，故分项之和 9 ≠ 回退页 8）：

  | 原因 | 次数 | 样本 |
  |---|---:|---|
  | 对象数不一致（PDFium 丢弃或保留的方式不同） | 7 | `struct-inline-image.pdf`、`struct-missing-resources.pdf`、`struct-multi-stream-bt.pdf`、`struct-multi-stream-q.pdf`、`text-clip-modes.pdf`、`text-positioning-ops.pdf`、`text-type3-multistream.pdf` |
  | 流损坏 | 1 | `struct-inline-image.pdf`（该页同时记了对象数不一致） |
  | 页树里的页数少于 PDFium | 1 | `struct-xref-stream-objstm.pdf` |

- 计划要求：对不上的页面应退回整条内容流、用 PDFium 生成器重写再做保真校验。**本轮尚未把回退页经 `GenerateContent` 合并进保存文件**；回退目前主要体现在统计，而不是完整的「回退 + 再校验」闭环。

## 5. 结论

对照 P0 四条目标，本轮**合成语料首轮实验未达标**，也还不能支持「P1 默认改用自研内容流读写层」：

| 目标 | 结果 | 判定 |
|---|---|---|
| 未匹配页 ≤ 2% | 12.12%（8 / 66） | 未达到 |
| 恒等时内容流逐字节相同 ≥ 99% | 96.55%（56 / 58）；缺口集中在空页样本 | 未达到 |
| 随机修改后无差异比例不低于 V03 | CLI 口径 87.93%（51 / 58）；匹配页 diff 口径 74.14%（43 / 58）。同批 PDFium `--control` 为 95.45%（63 / 66）。工作树内无 V03 定稿数字 | **差于本次生成器对照**；与 V03 正式报告的比较仍缺 |
| 记录耗时与字节变化 | 已记录，见 §4.5 | 完成记录 |

与此同时，原型本身是可运行的：库测试与 CLI 此前已通过；单页冒烟（`color-devicegray.pdf`）恒等流相同、修改像素为 `pass` 且增量保存符合 1203+472=1675；合成集上 58 / 66 页能完成对象对应，多数匹配页在 5% 随机修改后像素通过。失败集中在空页流守恒、多内容流 / 内联图像 / Type3 / 缺资源 / 对象流页树的映射，以及渐变、软蒙版、嵌套变换、图像掩膜、增量更新、部分文字对象的改写保真。

按计划第 6 节：当前数字属于「未达到目标值，或不比 V03（此处为 PDFium 对照）好」。**建议复盘时仍把 P1 默认路径放在继续修补 PDFium 生成器**；本原型与本报告存档，补齐回退闭环、单元测试和公开集 / V03 同批数字后再评估是否切换。

## 6. 遗留问题

1. **映射 / 重写单元测试**尚未补齐，回归目前主要靠 CLI 语料实验。
2. **`verify_failures` 始终为空**，`verify_us` 为 0；像素对错只出现在 `page_records`，缺少按页的失败说明。
3. **未匹配页还没有经 PDFium `GenerateContent` 合并进保存文件**，回退 + 再校验闭环未完成。
4. **Diff PNG 未输出**（目录里虽有 `diff/` 占位，本轮语料未写出可供审阅的差异图）。
5. **公开语料在本工作树为空**（仅 `tests/corpus/public/README.md`），没有与 V02/V03 相同的公开集数字。
6. **没有已定稿的 V03 无差异率**可直接对照，「不低于 V03」只能先用 `--control` 近似。
7. 代码仍在 `feat/v17-lossless-content`，**尚未提交**。
8. 恒等模式未做像素统计；空页样本（`struct-empty-pages.pdf`）保存后有的内容流长度为 0。
9. CLI 进度信息经 PowerShell `Tee-Object` 会变成 UTF-16，后续汇总应继续以 JSON + Python UTF-8 为准。

## 7. 对方案的修改建议

1. **P1 路线暂不改为「默认自研读写层」。** 方案 2.1 的备选做法可以保留，但退出标准仍以计划第 6 节为准：先达到未匹配 ≤ 2%、恒等流相同 ≥ 99%，并且修改后无差异率不低于（最好高于）V03 同批数字。
2. **把「回退到 PDFium 整页重写」写成必须交付的行为，而不只是统计口径。** 未匹配页应调用生成器写回保存结果，并纳入与 V02 相同的像素校验；否则 12.12% 的回退页在产品里会直接丢编辑或静默走原文。
3. **对照实验应同时引用 V03 修补后的报告，而不是只跑未修补 / 当前预编译库的 `--control`。** 本次对照在「不修改、只重写」时仅 80.30% 无差异，说明对照本身包含生成器已知缺陷；用它判断 V17 是否「更好」会偏低或偏高，取决于缺陷是否与 V17 失败集重叠。
4. **映射优先补这几类构造**：多内容流（`q` / `BT` 跨流）、内联图像、Type3（含多流）、缺资源、交叉引用流 + 对象流的页树、空页。它们贡献了几乎全部回退页和恒等流失败。
5. **改写保真优先看渐变、SMask、嵌套 `cm`、图像掩膜、增量更新文件、Standard14 / CID / Type3 文字。** 这些页在 PDFium 对照里能过，在自研 modify 里不过，更像是序列化或编辑应用的问题，而不是「生成器本来就会坏」。
6. **补齐 `verify_failures`、Diff PNG、map/rewrite 单元测试和公开集。** 没有这些，复盘会上很难把 15 个 `diff` 归因到具体操作符。
7. 方案正文目前不必改版本号；等补测和 V03 正式数字出来后，再在复盘纪要里写一条「V17 首轮合成集未达标，P1 仍走修补生成器」即可。

## 8. 合入 main 时的复测（2026-11-10）

合入时在 `main` 上用 release 构建重跑了第 4 节的实验：样本同为 `tests/corpus/synthetic` 的 58 份，随机种子不变。同一个 `magpdf-cli.exe` 分别配两份 `pdfium.dll`：一份是 `third_party/pdfium-prebuilt` 里的原版预编译库（`main` 的默认配置），一份是 V03 修补后的构建（`D:\pdfium-src\pdfium\out\Release\dist`，`mag/main` 8477545cb9）。

| 指标 | 原版预编译库 | V03 修补后的构建 |
|---|---:|---:|
| 不修改时内容流逐字节相同 | 56 / 58（96.55%） | 56 / 58（96.55%） |
| 对不上的页面 | 8 / 66（12.12%） | 8 / 66（12.12%） |

1. **三个目标值在三批样本上都达到了，包括一批从来没拿来调试过的。** 首轮是三个都没达到。
2. **随机修改之后，比 V03 第三轮的生成器高**：自制样本高 3 个点，PDFium 公开测试集高 6.5–9 个点，pdf.js 高 2 个点。生成器这一边差在共用内容流（或页对象）的多页文件和 Type3 文字上，都是 V03 没做完的项（9.6）。
3. **“对不上”之外还有一类回退：对应没问题，但改写层写不了这一次修改**（移动不在行首的文字、移动被 PDFium 去掉了剪裁的对象等，9.5）。把这一类也算上，随机修改时全部回退的页是自制样本 1.45%、公开测试集 1.03–1.80%、pdf.js 2.99%。回退的页由生成器重写，所以**生成器还得接着修，两条路不是二选一**。
4. **按计划第 6 节的判定条件，这一轮的数字落在“达到目标值，且随机修改后的无差异比例高于 V03”这一格。** 首轮报告第 5、7 节“P1 继续修补生成器、原型存档”的建议，依据已经变了。P1 用哪种做法是复盘会定的事，定之前这几条要一起看：
   - **样本里没有一份真实单证。** 三批都是测试文件：自制的、PDFium 的、pdf.js 的。办公软件、设计软件导出的真实文件上对应率多少，不知道。

   - **改写层只会三种修改：平移、改填充色、删除。** 缩放、旋转、改描边、改文字内容、加新对象、调层级都没有，遇到就得回退给生成器。“改一行字”（V08）走的也是生成器。
   - **代码是这一轮重写的，一万一千行，时间很短。** 合入时在没见过的样本上查出两处会把文件写坏的情况（9.8）。这类问题多半还有。
   - **回退的那一段是 PDFium 的增量保存写的**，qpdf 对其中三分之一的文件报“交叉引用损坏”（9.7）。不是读写层自己写的那一段的问题，但走这条路的产品要处理它。
5. **建议：P1 把这一层当成“没改过的对象原样保留”的主路径接着做，生成器（带 V03 的补丁）留作回退和新对象的写出；进 P1 之前先用真实样本把对应率和回退率量一遍，再接上第二渲染器。** 这是建议，不是决定。

### 9.2 这一轮做了什么

- **回退闭环**（`616c57f`）。保存结果是三段接起来的：原文件的字节；读写层的增量更新（对得上、也写得了的页）；PDFium 的增量保存（回退的页：做同一组修改，整页标记为已修改，交给生成器重写）。之后重新打开保存结果，逐页比像素，回退的页单独计数。`verify_failures` 按页写出原因，不过的页写出差异图。
- **读写层按 PDFium 的规则重写**（`411d796`，+8562 / −3476 行）。首轮是按规范自己归纳“哪个操作符产生哪个对象”，在 PDFium 和规范不一样的地方对不上（操作数个数不对时忽略操作符、只有一个点的路径、字体找不到时换备用字体、`TJ` 里全是空串、资源缺失的 `Do`……）。这一轮把 PDFium 里决定这些事的代码移植成 Rust：对象层和交叉引用的容错读法、过滤器、页树、内容流的分词、“建不建对象”的解释、资源的加载规则。对齐的版本是 `8477545cb9`。移植了哪些文件、许可的原文在 `engine/magpdf-content/PDFIUM-NOTICE.md`。写回的部分（改写、增量更新）是自己写的。
- **改写**：只动被修改对象的字节，别的原样拼回去。会三种修改：平移（给对象套上 `q 1 0 0 1 dx dy cm … Q`，文字另有改定位的写法）、改填充色、删除（后面还有文字接着写的文字不能直接删，改成不可见）。写不了的情况明确拒绝、交给回退，不硬写（9.5）。
- **保存**：增量更新，交叉引用是表的文件写表，是流的写流。内容流被别的页共用、页对象占着不止一个页号、页字典直接写在 `/Kids` 里，这几种都另起对象，不动别的页（`43e2d46`）。PDFium 公开测试集里因此另起页对象的有 19 页。
- **PDFium 的两处行为专门对齐**：解析完一页之后它会把多余的矩形剪裁从对象上去掉（`66b84a1`；V03 报告 11.4 的那 1500 处剪裁差异就是它）；页树里有类型不对的页时，把文件交给生成器会让进程中止，这种文件的回退页留着原样、对照组不跑（`854d891`）。
- **预期画面的口径改了**：在 PDFium 内存里做完修改，页面不关，直接渲染——这是界面上改完之后用户看到的画面。首轮是改完之后让生成器重写一遍再渲染，预期画面带着生成器自己的损失（9.9）。
- **工具**：`engine/magpdf-content/tools/run-experiments.ps1`（两批样本 × 两份 PDFium × 四种实验，一条命令）、`summarize.py`（汇总成表）、`measure-timing.ps1`（计时）。
- **单元测试**：`magpdf-content` 120 个（首轮 25 个，没有覆盖对应和改写），命令行这部分 12 个。

### 9.6 生成器这一边差在哪

对照组是 V03 第三轮的生成器：同一组修改，整页重写。它不改动时已经很好（公开测试集 385 / 388，pdf.js 97.11%），一修改就掉下来：

- **PDFium 公开测试集，轮流取：23 页不过，全部是做了“移动”的页。** 其中 19 页属于 4 份多页文件（`bug_680376.pdf`、`no_page_count.pdf`、`viewer_ref.pdf`、`bug_1229106.pdf`），这些文件的页树里同一个页对象出现了好几次、占着好几个页号（读写层给这 19 页各另起了页对象）；1 页是两页共用内容流的 `hello_world_2_pages_split_streams.pdf`。生成器把共用的内容流就地改写，改一页，别的页跟着变。这是 V03 没做的“共用内容流的 copy-on-write”一项（V03 报告 11.5）。剩下 3 页是 Type3 文字（`bug_1591.pdf`、`bug_583.pdf`、`bug_642.pdf`）。
- **自制样本：3 页不过**，两份 Type3 的样本和 `shading-mesh.pdf`。
- 也就是说，生成器剩下的差距正好是 V03 第三轮没做完的两项。这两项做完，它在这两批样本上也会接近 100%。读写层不用等：没改的对象它不碰，共用的流和页对象它自己另起。

|---|---|---|---|---|---|
| 自制样本，三种实验 | 59–60 | 59–60 | 0 | 0–1 | 0 |
| PDFium 公开测试集，随机修改 | 216 | 213 | 0 | 3 | 1 |
| pdf.js，随机修改 | 965 | 917 | 0 | 48 | 15 |

- **读写层自己写的增量更新，qpdf 没有报出一处新问题**（一千多份文件），页数都对，内容流都能解析。（公开测试集里 `bug_455199.pdf` 本来就是坏的：交叉引用找不到，`/Contents` 数组里有一项不是流。读写层补上了能用的交叉引用，那一项照原样留着；qpdf 对原件是在修复模式下把它记成警告，对保存结果直接报了错。不算新问题。）
- **PDFium 的增量保存写的那一段，三份里有一份 qpdf 报“交叉引用损坏”**（pdf.js 48 份里 15 份，公开测试集 3 份里 1 份；报的是 `xref not found`、重建交叉引用表、对象个数对不上）。这一段是回退的页用的；有的文件里读写层一个字节都没写，只有这一段，照样报。PDFium 自己读得回来。别的阅读器读不读得了没有试。要么回退的页改用完整保存，要么把生成器写出来的流交给读写层的增量更新去写——都没有做。
- qpdf 不渲染，这只是结构检查，替代不了第二渲染器。

### 9.8 没参与调试的那一批，和合入时查出来的两处错

pdf.js 的测试文件是合入时才取的，读写层的作者没有见过。在它上面三个目标值都达到了（9.1），同时查出两处会把文件写坏的情况，都是 PDFium 的像素比对看不出来、或者只在这批样本里才有的。**已修**（`2e6e53a`，各带单元测试），9.1–9.7 的数是修了之后的。

1. **没解开的过滤器。** 内容流的 `/Filter` 里有 PDFium 不认得的过滤器时（公开测试集里 4 份用 Brotli 压缩的文件，这一版 PDFium 没编进 Brotli），PDFium 拿到的是没解开的数据，当成内容流去解释，页面是空的。读写层照 PDFium 的读法，手里也是这串数据；“不改动也写回”时把它配上 `/FlateDecode` 写了回去，原来的 `/BrotliDecode` 就丢了。PDFium 看前后都是空页，像素无差异；认得 Brotli 的阅读器，原件能显示，保存结果是乱码。是 qpdf 的结构检查发现的。压缩之后解出来是空的流也是同一类（PDFium 这时拿压缩后的原始字节当内容）。现在解码不完整的流一律不写，这一页记成“写不回文件”。
2. **内容流同时是表单 XObject。** `issue18894.pdf` 里，页面的 `/Contents` 和页面资源里的 `/X1` 是同一个对象。移动页面上的一个方块时，读写层原地改写了这条流，表单那一份跟着变了，和预期画面差 1900 个像素。代码的注释里本来就写着这是“没有发现的情况”。现在字典上带 XObject 记号的流一律另建一条。只看字典上的记号，没有去数整份文件里谁引用了它。

另外两件不是错，但要知道：

- **有两页自己就有噪声。** `issue2391-2.pdf`、`pattern_text_non_embedded_font.pdf` 用了系统里没有的基础字体，PDFium 保存再重开之后找的替代字体不一样。`roundtrip --calibrate` 在 pdf.js 那一批的 1935 页里报出的就是这 2 页。上面各表里没有把它们剔掉。
- **进这一类页面的修改，两条路都保不住。** PDFium 解不开内容流的页（上面第 1 条），读写层现在不写；真要改它，只能回退给生成器，生成器按它看到的空页重写，原来的内容就没了。产品里这种页应当整页不让改。保真校验（方案 2.3）用的也是 PDFium，发现不了。

### 9.9 首轮的数为什么换一份 PDFium 就变（第 8 节留的问题）

第 8 节：换成原版预编译库之后，随机修改后无差异的页从 51 降到 37，当时没查出差在哪。

**变的是预期画面，不是保存结果。** 首轮的预期画面是“改完之后让 PDFium 的生成器把整页重写一遍，再重新解析、渲染”得到的，所以带着生成器自己的损失；换一份 PDFium，生成器丢的东西不一样，预期画面跟着变。这一轮每次渲染都记了两张图各自的指纹，按首轮的口径重跑（`--expected regenerated`）：原版和第三轮的修补版之间，预期画面的指纹有 29 页不同，保存结果的画面 0 页不同，结论跟着变的正是这 29 页。

所以首轮那个数量的不是“改完保存有没有走样”，是“读写层的结果和生成器的结果像不像”：按首轮的口径，读写层的无差异页数正好等于那一份生成器不改动时的无差异页数（原版 38 / 69，第三轮 67 / 69）。首轮“读写层不如生成器对照”的结论是这个口径造成的，要作废。

### 9.10 耗时和文件大小

读写层自己的三段：读入（读文件，自研对象层打开文档）、对应（找页、解内容流、照 PDFium 的规则解释，再和 PDFium 的对象逐个核对）、保存（改写内容流，写增量更新；不含回退给生成器的页）。PDFium 那一侧的加载、渲染、比对不算。`measure-timing.ps1`，每种情形 5 遍，每个文件一个进程；表里是**整批样本各文件之和**，ms，中位数（最小–最大）。开发机实测，合入时在机器比较空的时候量的（2026-11-12 17:15–17:18，整机 CPU 占用 4–17%，有一遍开始时 42%）。

| 样本 | 做法 | 文件 / 页 / 字节 | 读入 | 对应 | 保存 |
|---|---|---|---|---|---|
| 自制样本 | 随机修改 | 60 / 69 / 109 KB | 7.1（6.4–7.8） | 4.2（4.0–4.8） | 10.8（10.2–11.9） |
| 自制样本 | 不改动，每页都写回 | 同上 | 6.4（6.1–6.8） | 4.1（4.0–4.2） | 10.7（10.4–10.9） |
| PDFium 公开测试集 | 随机修改 | 346 / 389 / 2.82 MB | 39.0（38.3–41.0） | 18.8（18.4–20.3） | 42.2（42.1–44.1） |
| PDFium 公开测试集 | 不改动，每页都写回 | 同上 | 39.7（38.9–41.0） | 19.2（18.8–19.7） | 47.2（45.8–47.8） |

- 公开测试集 389 页，三段合起来约 0.1 秒，平均每页 0.26–0.27 ms。这两批样本的页都很小。
- pdf.js 那一批大得多（1092 份、156 MB、237 万个操作符、33 万个对象），没有用计时脚本量，只有跑实验时顺带记的数（8 个进程同时跑，不能当耗时用）：整批读入 0.3 秒，对应 0.7 秒，保存 1.4–1.5 秒，平均每页 1.2–1.3 ms。
- 和渲染比，这三段可以忽略：同一次实验里 PDFium 渲染、比对花的时间是它的几十倍。真实的大文件（几百页、每页上万个对象）上要多久没有量。

文件大小（配第三轮，随机修改，三批样本各自的合计）：

| 样本 | 原文件 | 读写层追加 | PDFium 增量保存追加（回退的页） | 作为对比：整份完整重写 |
|---|---|---|---|---|
| 自制样本 | 109 KB | 30 KB（27.1%） | 6 KB（5.9%） | 116 KB |
| PDFium 公开测试集 | 2.82 MB | 94 KB（3.3%） | 141 KB（5.0%） | 2.76 MB |
| pdf.js 测试文件 | 155.9 MB | 9.33 MB（6.0%） | 6.82 MB（4.4%） | 168.0 MB |

- 增量更新只追加改过的内容流（整条重新压缩）和必要的页字典。自制样本的文件小，内容流占的比例大，所以追加的比例高。
- 回退的页占 1–3%，追加的字节却和读写层那一段差不多：生成器是整页重写。

### 9.12 没做的和遗留

1. **真实样本没有跑**，一份都没有。
2. **第二渲染器没有接**（方案 13.2 第 3 项）。只做了 qpdf 的结构检查。
3. **改写层会的修改只有三种**（平移、改填充色、删除）。缩放、旋转、描边色、文字内容、新对象、层级都要回退。
4. **回退的那一段用 PDFium 的增量保存**，qpdf 对三分之一的文件报交叉引用损坏（9.7）。
5. **加密的文件不支持**（自研对象层不解密），整份回退。pdf.js 那一批里 13 页。
6. **内联图像用 `DCTDecode`、`CCITTFaxDecode` 时定不了界**，整页回退。5 页。
7. **内容流被别处引用而字典上看不出来**（没有 `/Type`、`/Subtype`）时，原地改写仍然会连带改到那里（9.8 第 2 条只堵了看得出来的）。
8. **Flate 数据损坏的流**：PDFium 用解出来的那一部分，读写层照做，写回时就按这一部分写了。算不算“写坏”没有定。
9. **`shading-mesh.pdf` 移动网格渐变之后差 240 个像素**，读写层和生成器差得一样，原因没查。
10. **解不开内容流的页应当整页不让改**（9.8），产品里还没有这条规则；保真校验发现不了。
11. **对齐的 PDFium 版本是写死的**（`8477545cb9`）。PDFium 升级、改了解析规则，这一层要跟着改；怎么发现“对不齐了”，现在靠的是每一页都和 PDFium 的对象逐个核对个数和类别，核对不上就回退。
12. 没有接进引擎（`magpdf-engine` 的编辑会话还是走生成器）。这是原型，只有命令行的实验。

### 9.14 对方案和计划的修改建议

1. **方案 2.1 的备选做法**（内容流自己读写）：从“备选”改成和修补生成器并列的做法，写明分工——没改的对象原样保留、简单的修改由读写层写；读写层写不了的修改和对不上的页回退给生成器。P1 用哪种由复盘会定（9.1）。
2. **方案 2.3 的保真校验**补一条规则：内容流没能完整解码的页（过滤器 PDFium 不认得等）整页不让改（9.8）。
3. **方案 13.2**：第二渲染器要尽早接上。这一轮的两处错里有一处只有别的阅读器看得出来；在接上之前，qpdf 的结构检查可以先放进每晚的测试。
4. **《P0 技术验证计划》V17 的目标值**把两类回退分开写：“操作符和对象对不上的页”和“对得上但这一次修改写不了的页”。现在只有前一个有目标值。
5. **每晚的往返测试把 pdf.js 的测试文件加进去**（规范第 2 节本来就列了它）。这一轮是手工取、手工跑的：`scripts/fetch-public-corpus.ps1` 还只会取 PDFium 那一批。
6. **V03 没做完的两项**（共用内容流的 copy-on-write、Type3 文字）不因为这一轮的结果就不做了：回退的页和新对象还是生成器写。
