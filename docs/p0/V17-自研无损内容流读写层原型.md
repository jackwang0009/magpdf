## 1. 目标

验证「PDFium 只负责解析、渲染和命中测试，内容流由自研 Rust 层读写」这条备选路径是否成立：

1. 不修改任何对象直接保存：内容流应与原文件逐字节相同（目标：相同流 ≥ 99%）。
2. 随机修改约 5% 的对象（移动、改色、删除）后保存，与按同一组编辑生成的期望结果做像素比对（判定规则同 V02）；无差异页面比例不低于 V03。
3. 统计操作符与页面对象对不上的页面比例；对不上的页面应退回整条内容流重写再校验（目标：未匹配 / 回退页 ≤ 2%）。
4. 记录读入、映射、保存、渲染耗时，以及修改后文件的字节变化量。

P0 复盘标准（计划第 6 节）：V17 达到目标值且随机修改后的无差异比例高于 V03，才把自研读写层定为 P1 默认做法；否则 P1 继续修补 PDFium 生成器，本原型存档。

## 2. 方法

### 2.1 原型行为（本轮已具备）

- 读入时保留原内容流操作符及其字节位置，并按 PDFium 页面对象规则做顺序对应。
- 保存时只重写改过的对象，其余字节尽量原样保留；改动与新增由自研序列化写出，不经过 PDFium 内容流生成器。
- 删除计划使用 `draw_start`；`Transform` 保持 6 个 double 的矩阵形式。
- 实验驱动 `experiment/run.rs`：在同一 `Page` 句柄上应用编辑后立刻 `mark_all_and_regenerate`。PDFium 若先 `ClosePage` 再生成期望页，编辑会丢失（此前 modify 冒烟因此失败，已从备份恢复并修补）。

### 2.2 对比实验

命令均为 `magpdf-cli content-roundtrip`，输入 `tests/corpus/synthetic`，`--source synthetic`，`--jobs 2`，`--seed 20261109`，`--scale 2.0`。JSON 写到工作树 `tests/out/v17/`：

| 实验 | 文件 | 模式 | 说明 |
|---|---|---|---|
| 1 / 3 / 4（恒等往返） | `exp1-roundtrip.json` | `roundtrip`（`modify_ratio=0`） | 不修改即保存；看流是否逐字节相同、未匹配页、耗时与字节 |
| 2（随机修改） | `exp2-modify.json` | `modify`，`modify_ratio=0.05` | 随机改约 5% 对象后保存，与期望渲染像素比对 |
| 2 + 对照 | `exp2-modify-control.json` | `modify` + `--control` | 同上，并跑 PDFium 生成器对照 |
| 对照往返 | `exp-control-roundtrip.json` | `roundtrip` + `--control` | 恒等路径上的 PDFium 生成器对照 |

脚本：`D:\workspace\magpdf\v03r2-tmp\run-v17-corpus.ps1`。日志里 `Tee-Object` 曾把 CLI 的信息流写成 UTF-16，终端表格出现乱码；**结论以 UTF-8 JSON 为准**（Python 汇总）。四次退出码：`EXP1_EXIT=0`、`EXP2_EXIT=0`、`EXP2C_EXIT=0`、`EXPC_EXIT=0`。

像素比对的期望路径与自研保存路径使用同一组随机编辑；对照（`--control`）走 PDFium `GenerateContent` 一类整页重写，作为本轮可得到的生成器基线。本工作树没有已定稿的 V03 报告数字，故「不低于 V03」只能先与这次 `--control` 比较，并注明缺口。

### 4.2 方法 1：不修改即保存，内容流是否逐字节相同

- **56 / 58 = 96.55%，低于目标 99%。**
- 唯一拉低该比例的样本是 `struct-empty-pages.pdf`：4 条内容流中 2 条不一致（`streams_identical=2`，`bytes_original=38`，`bytes_saved=0`）。内容流总字节 52985→52947 的 38 字节差额全部来自这份文件。
- 其余成功打开的文件，保存后的**文件级**字节合计与原文相同（104586，增量 0）。`struct-xref-missing.pdf` 打不开，不参与流比较。
- 恒等模式 `render_us=0`、`pages_passed=0`、`page_records` 为空，本轮**没有**对「不修改保存后的渲染结果」做像素统计；像素数字见方法 2 与对照往返。

### 4.3 方法 2：随机修改 5% 后的像素保真

- 实际改动 129 / 5027 条操作符（2.57%）。比例低于 5%，是因为随机抽的是可映射对象，不是全部操作符；部分操作符不可编辑。
- CLI / `total.pages_passed`：**51 / 58 = 87.93%**（分母为匹配页）。`page_records` 则是 51 个 `pass` + 15 个 `diff`，合计 66，覆盖全部页面。
- 15 个出现 `diff` 的都是**已匹配**的单页文件（`fallback_pages=0`，`pages_matched=1`）：

  `freight-bl-composite.pdf`（改 2 个操作符）、`gs-line-params.pdf`、`gs-smask-luminosity.pdf`、`shading-axial.pdf`、`shading-functions.pdf`、`shading-mesh.pdf`、`shading-radial.pdf`、`shading-stitching-background.pdf`、`struct-cm-nested-transforms.pdf`、`struct-image-xobject-masks.pdf`、`struct-incremental-update.pdf`、`struct-many-objects-clip.pdf`（改 75 个操作符）、`text-cid-cjk-nonembedded.pdf`、`text-standard14.pdf`、`text-type3.pdf`。

- 8 个回退页至少有一部分在 `page_records` 里记为 `pass`（例如 `struct-inline-image.pdf`、`text-clip-modes.pdf`、`text-type3-multistream.pdf`）。它们并未完成对象对应，却可能仍按未改写的原始页面渲染，因此「pass」不能理解为「回退重写后保真通过」。
- 若只数「匹配页里的像素 diff」，则是 15 / 58 失败（通过率 43 / 58 = 74.14%）。报告同时给出 CLI 的 87.93% 与这一口径，避免只看一个百分比。
- **同进程 PDFium 对照**（`--control`，修改模式）：**63 / 66 = 95.45%**。对照失败的 3 页恰为回退样本：`struct-inline-image.pdf`、`text-clip-modes.pdf`、`text-type3-multistream.pdf`。上面 15 个 V17 `diff` 样本在对照里全部 `pages_passed=1`。也就是说，同一组 5% 编辑下，自研保存的像素结果差于 PDFium 生成器对照。
- 本工作树**没有**可引用的 V03 定稿无差异率。就「是否不差于生成器基线」而言，当前合成集上的答案是：**差于本次 `--control`**。
- `verify_failures` 四个 JSON 均为 0，`verify_us` 均为 0；像素对错写在 `page_records`，没有按页列出失败详情，也没有写出 Diff PNG。

### 4.4 方法 3：对不上的页面 / 回退率

- **8 / 66 = 12.12%，高于目标 2%。** `unmatched_files=0`（没有整文件被标成 unmatched），回退发生在页级。
- 原因计数（一份页面可记两条原因，故分项之和 9 ≠ 回退页 8）：

  | 原因 | 次数 | 样本 |
  |---|---:|---|
  | 对象数不一致（PDFium 丢弃或保留的方式不同） | 7 | `struct-inline-image.pdf`、`struct-missing-resources.pdf`、`struct-multi-stream-bt.pdf`、`struct-multi-stream-q.pdf`、`text-clip-modes.pdf`、`text-positioning-ops.pdf`、`text-type3-multistream.pdf` |
  | 流损坏 | 1 | `struct-inline-image.pdf`（该页同时记了对象数不一致） |
  | 页树里的页数少于 PDFium | 1 | `struct-xref-stream-objstm.pdf` |

- 计划要求：对不上的页面应退回整条内容流、用 PDFium 生成器重写再做保真校验。**本轮尚未把回退页经 `GenerateContent` 合并进保存文件**；回退目前主要体现在统计，而不是完整的「回退 + 再校验」闭环。

## 5. 结论

对照 P0 四条目标，本轮**合成语料首轮实验未达标**，也还不能支持「P1 默认改用自研内容流读写层」：

| 目标 | 结果 | 判定 |
|---|---|---|
| 未匹配页 ≤ 2% | 12.12%（8 / 66） | 未达到 |
| 恒等时内容流逐字节相同 ≥ 99% | 96.55%（56 / 58）；缺口集中在空页样本 | 未达到 |
| 随机修改后无差异比例不低于 V03 | CLI 口径 87.93%（51 / 58）；匹配页 diff 口径 74.14%（43 / 58）。同批 PDFium `--control` 为 95.45%（63 / 66）。工作树内无 V03 定稿数字 | **差于本次生成器对照**；与 V03 正式报告的比较仍缺 |
| 记录耗时与字节变化 | 已记录，见 §4.5 | 完成记录 |

与此同时，原型本身是可运行的：库测试与 CLI 此前已通过；单页冒烟（`color-devicegray.pdf`）恒等流相同、修改像素为 `pass` 且增量保存符合 1203+472=1675；合成集上 58 / 66 页能完成对象对应，多数匹配页在 5% 随机修改后像素通过。失败集中在空页流守恒、多内容流 / 内联图像 / Type3 / 缺资源 / 对象流页树的映射，以及渐变、软蒙版、嵌套变换、图像掩膜、增量更新、部分文字对象的改写保真。

按计划第 6 节：当前数字属于「未达到目标值，或不比 V03（此处为 PDFium 对照）好」。**建议复盘时仍把 P1 默认路径放在继续修补 PDFium 生成器**；本原型与本报告存档，补齐回退闭环、单元测试和公开集 / V03 同批数字后再评估是否切换。

## 6. 遗留问题

1. **映射 / 重写单元测试**尚未补齐，回归目前主要靠 CLI 语料实验。
2. **`verify_failures` 始终为空**，`verify_us` 为 0；像素对错只出现在 `page_records`，缺少按页的失败说明。
3. **未匹配页还没有经 PDFium `GenerateContent` 合并进保存文件**，回退 + 再校验闭环未完成。
4. **Diff PNG 未输出**（目录里虽有 `diff/` 占位，本轮语料未写出可供审阅的差异图）。
5. **公开语料在本工作树为空**（仅 `tests/corpus/public/README.md`），没有与 V02/V03 相同的公开集数字。
6. **没有已定稿的 V03 无差异率**可直接对照，「不低于 V03」只能先用 `--control` 近似。
7. 代码仍在 `feat/v17-lossless-content`，**尚未提交**。
8. 恒等模式未做像素统计；空页样本（`struct-empty-pages.pdf`）保存后有的内容流长度为 0。
9. CLI 进度信息经 PowerShell `Tee-Object` 会变成 UTF-16，后续汇总应继续以 JSON + Python UTF-8 为准。

## 7. 对方案的修改建议

1. **P1 路线暂不改为「默认自研读写层」。** 方案 2.1 的备选做法可以保留，但退出标准仍以计划第 6 节为准：先达到未匹配 ≤ 2%、恒等流相同 ≥ 99%，并且修改后无差异率不低于（最好高于）V03 同批数字。
2. **把「回退到 PDFium 整页重写」写成必须交付的行为，而不只是统计口径。** 未匹配页应调用生成器写回保存结果，并纳入与 V02 相同的像素校验；否则 12.12% 的回退页在产品里会直接丢编辑或静默走原文。
3. **对照实验应同时引用 V03 修补后的报告，而不是只跑未修补 / 当前预编译库的 `--control`。** 本次对照在「不修改、只重写」时仅 80.30% 无差异，说明对照本身包含生成器已知缺陷；用它判断 V17 是否「更好」会偏低或偏高，取决于缺陷是否与 V17 失败集重叠。
4. **映射优先补这几类构造**：多内容流（`q` / `BT` 跨流）、内联图像、Type3（含多流）、缺资源、交叉引用流 + 对象流的页树、空页。它们贡献了几乎全部回退页和恒等流失败。
5. **改写保真优先看渐变、SMask、嵌套 `cm`、图像掩膜、增量更新文件、Standard14 / CID / Type3 文字。** 这些页在 PDFium 对照里能过，在自研 modify 里不过，更像是序列化或编辑应用的问题，而不是「生成器本来就会坏」。
6. **补齐 `verify_failures`、Diff PNG、map/rewrite 单元测试和公开集。** 没有这些，复盘会上很难把 15 个 `diff` 归因到具体操作符。
7. 方案正文目前不必改版本号；等补测和 V03 正式数字出来后，再在复盘纪要里写一条「V17 首轮合成集未达标，P1 仍走修补生成器」即可。

## 8. 合入 main 时的复测（2026-11-10）

合入时在 `main` 上用 release 构建重跑了第 4 节的实验：样本同为 `tests/corpus/synthetic` 的 58 份，随机种子不变。同一个 `magpdf-cli.exe` 分别配两份 `pdfium.dll`：一份是 `third_party/pdfium-prebuilt` 里的原版预编译库（`main` 的默认配置），一份是 V03 修补后的构建（`D:\pdfium-src\pdfium\out\Release\dist`，`mag/main` 8477545cb9）。

| 指标 | 原版预编译库 | V03 修补后的构建 |
|---|---:|---:|
| 不修改时内容流逐字节相同 | 56 / 58（96.55%） | 56 / 58（96.55%） |
| 对不上的页面 | 8 / 66（12.12%） | 8 / 66（12.12%） |
| 随机修改 5% 后无差异（匹配页） | 37 / 58（63.79%） | 51 / 58（87.93%） |
| 同一批修改，PDFium 生成器对照 | 62 / 66（93.94%） | 63 / 66（95.45%） |
| 不修改，PDFium 生成器整页重写对照 | 37 / 66（56.06%） | 53 / 66（80.30%） |

- 第 4 节的数字与右列逐项相同，说明当时工作树链接的是 V03 修补后的 `pdfium.dll`，不是原版预编译库。4.5、第 6 节第 6 条和第 7 节第 3 条把 `--control` 当成未修补的生成器，这一点要更正：95.45% 和 80.30% 已经是 V03 第二轮修补（`Tc/Tw`、Type3 未闭合块、颜色空间、文字裁剪）之后的结果。
- 换成原版预编译库后，随机修改后的无差异页从 51 降到 37，恒等保存和对应率不变。多出来的 14 页差在哪里还没有查。下一轮先分清是"预期画面"（在 PDFium 内存里改完直接渲染）随 PDFium 版本变了，还是保存结果重新打开后的渲染变了。
- 结论不变：两种配置下，自研读写层随机修改后的无差异率都低于 PDFium 生成器对照。
