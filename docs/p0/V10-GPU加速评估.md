# V10 GPU 加速评估 —— 验证报告（开发机上的参考数据）

- 分支：`feat/v10-gpu-eval`（从 `main` @ `ff6b0ac` 分出）。合入时逐个摘到 `main` 上，脚本是 `f25b6a7` → `cd34fa8` 这 6 个提交，加合入时的两处改动（第 12 节）
- 日期：2026-11-12
- 对应方案：《方案》2.2（默认 CPU 推理；有显卡时 Windows 11 24H2 起用 Windows ML，更早的系统回退 DirectML）、6.5、12.1（安装包估算）、第 15 节“GPU 推理接口变动”；《P0 技术验证计划》V10
- 结论：
  1. **计划要的三组数一组也没有，“GPU 加速是否默认开启”定不了。** R3（RTX 4050，Windows ML 和强制回退的 DirectML）、R2（Windows 10，集成显卡，DirectML）上都没有量。这份报告只有开发机上的参考数据：同一批模型、同一批输入，CPU 对 DirectML。开发机的独立显卡 GTX 1070 在设备管理器里是出错状态（代码 43），DirectML 用不了它，只量了集成显卡。
  2. **在这台机器的集成显卡上，DirectML 比 CPU 慢。** 每页推理耗时，移动版是 CPU 的 6.3 倍（2097 对 330 ms），服务器版是 3.2 倍（5704 对 1763 ms）；从装载运行时到第一页出结果，移动版 3.2 秒对 0.66 秒；进程内存多 336 MB，另占 1.3 GB 共享显存（第 3–5 节）。不是算子回退到 CPU 造成的，也不是输入形状变来变去造成的（3.3、第 8 节）。这台机器的 CPU 很强、集成显卡很弱，这个倍数不能搬到参考机上。
  3. **稳定性和输出没有问题。** 连续 1000 页两边都没有报错，内存、显存不涨，耗时不漂（第 6 节）；DirectML 和 CPU 的输出数值上差 1e-3 量级，解码出来的文字一行不差（第 7 节）。
  4. **机器忙的时候两边差不多（3.4）。** CPU 被别的任务占满时，CPU 推理慢到 7.8 倍，DirectML 只慢到 1.5 倍。显卡推理不抢 CPU、也不怕 CPU 被抢，这是它实在的好处；不过建 DirectML 会话这一步吃 CPU，忙的时候要十几秒。
  5. **安装包（第 9 节）**：带 DirectML 多 18.6 MB（LZMA 压过之后多 8.6 MB）；Windows ML 的运行时随包带多 26.0 MB（压过之后多 10.1 MB）。
  6. **查实的三件事，方案 2.2 要补（第 10、11 节）。** Windows ML 自带的执行提供程序只有 CPU 和 DirectML；各家显卡专用的要联网下载、装进系统，只管比较新的显卡，集成显卡和老显卡在 Windows 11 24H2 上用的仍然是 DirectML。带 DirectML 的 ONNX Runtime，官方单独发布的停在 1.24.4；产品用的 1.31.1 里没有 DirectML，要用显卡就得换运行时。`DirectML.dll` 的许可是微软的专有条款，里面有“可能收集信息发给微软”“可能自动检查并安装更新”两条，要有人对一下。
  7. **建议：v1.0 只带 CPU 版运行时，不做 GPU 加速；参考机上量过之后再定要不要做成可选项。** 现有的数据里没有一条支持默认开启：默认开不开，受影响最大的是只有集成显卡的机器，这一类机器上唯一的一组数是“更慢”。真要做的话怎么接、什么情况回退到 CPU，办法写在第 11 节，用仓库外面的一个小程序核对过，产品代码一行没动。

## 2. 环境、样本、量法

### 2.1 机器

- 开发机：AMD Ryzen 7 9800X3D（8 核 16 线程）、47.2 GB 内存、Windows 11 24H2（内部版本 26100）。
- 集成显卡 AMD Radeon(TM) Graphics（`PCI\VEN_1002&DEV_13C0`，驱动 32.0.21045.9003，2026-08-27）。专用显存 486 MB，另可用 24.1 GB 共享内存。按公开资料，这是 Ryzen 9000 桌面处理器自带的集成显卡，RDNA 2 架构、2 个计算单元，是集成显卡里很弱的一档。DXGI 里有三个同名的适配器（序号 0、1、2），多出来的两个应该是远程桌面和安卓模拟器的虚拟显示适配器（设备管理器里的 Todesk、MuMu 两项）挂在它上面的，没有逐个核对；只量了序号 0。
- 独立显卡 NVIDIA GeForce GTX 1070（驱动 32.0.15.7602，2025-04-12）**这一轮用不了**：设备管理器里是错误状态，代码 43（设备启动之后报告了故障），从 11 月 4 日这次开机起就是这样；DXGI 枚举不到它，`nvidia-smi` 报“连不上 NVIDIA 驱动”。DirectML 只能用 DXGI 里看得到的显卡。修它要重装驱动或重启，机器上别的任务正在用屏幕和显卡，没有动。
- 这台机器的 CPU 很强、集成显卡很弱，两者的力量对比和 R1、R2、R3 都不一样。**下面“DirectML 是 CPU 的几倍”只对这台机器成立，不能搬到参考机上。**

### 2.3 样本和工作量

- V09 最初的那套合成样本：18 页 300 dpi 的 A4 打印体单证（2480×3508），内容全部虚构；英文、中文、中英混排各 6 页，每种有干净的、加噪声的、转 ±1.5° 的、又加噪声又转的。生成脚本是 `tests/perf/gpu/gen_samples.py`：`tests/corpus/synthetic-ocr/gen_synthetic.py` 在 V09 这一轮重写了，出的不再是这 18 页，所以把旧的留了一份在这里，重量时用的还是同一套（合入时核对过，18 张图逐字节相同）。
- 文字行的框用固定的命令行工具跑一遍 OCR 得到（`magpdf-cli ocr`），移动版、服务器版各跑一遍。Python 这边把 `engine/magpdf-scan/src/ocr/` 的预处理逐步移植到 numpy（`workload.py`）：检测输入长边缩到 1600、宽高取 32 的倍数；按四点框裁出各行；方向分类 160×80、每 6 行一批；识别高 48、按长宽比排序后每 6 行一批、批宽向上取 32 的倍数（320–3200）。
- 所以一页的工作量和产品一样：检测 1 次，全部文字行各做 1 次方向分类和识别。移动版 18 页共 548 行（每页 21–37 行，中位数 34），方向分类和识别各 100 批（每页 4–7 批），识别批次的形状有 45 种（宽 320–2176）；服务器版 543 行、各 99 批、47 种形状（宽 320–2336）。18 页的检测输入都是 1120×1600。
- 和产品差的一点：命令行工具识别之后因为置信度太低丢掉的行不在它的输出里（两套模型各 2 行），这边就没有这几行，比产品少做约 0.4% 的分类和识别。
- 服务器版慢，只用了 18 页里均匀挑的 6 页（英文、中文、混排各 2 页，共 180 行）；宽度分档那一项用 9 页。
- 移植对不对，用结果核对：把识别模型的输出解码成文字，和命令行工具（Rust 写的流水线）给出的文字逐行比。移动版 18 页 548 行、服务器版 6 页 180 行，CPU 和 DirectML 两边都没有一行不同（第 7 节）。

### 2.4 量法

- 只量模型推理（`InferenceSession.run`，含把输入送进去、把输出取回来）。输入事先算好存成缓存，前后处理不在计时里。会话的设置和 `runtime.rs` 一样：图优化开到最高一级，线程数交给 ONNX Runtime；DirectML 另按它的要求关掉内存模式优化、用顺序执行。
- 每种配置每次起一个新进程，配置之间轮流跑，各 5 次。进程里整套页面过 3 遍（服务器版 6 页过 2 遍）：第 1 遍单独记，第 2 遍起算稳定值。表里“中位数（最小–最大）”的意思：先在一个进程里取各页的中位数，再对 5 个进程取中位数、最小、最大。
- 初始化分三段：装载 ONNX Runtime、建三个会话、第一页的推理。
- 内存是进程的峰值工作集。显存读性能计数器 `GPU Process Memory`（任务管理器“专用 GPU 内存”“共享 GPU 内存”两列的来源），每 0.5 秒采一次取峰值；集成显卡没有独立显存，主要看“共享”。
- 要的执行提供程序没有起来就算失败（Python 接口默认会悄悄回退到 CPU）；另外记下本进程在这块显卡上的占用，确认是显卡在算。
- 全部测量一条命令重跑：`D:\workspace\magpdf-wt\venvs\v10\Scripts\python.exe tests/perf/gpu/run_all.py`，结果在 `tests/out/v10/`（`summary.md`、`summary.json`、`runs/*.json`）。说明见 `tests/perf/gpu/README.md`。

### 2.5 机器上别的任务，和“优先级调高一档”的那一份

量的这一天，机器先后是两种情况，下面分开写：

- **忙的时候**（上午到 13:34）：另外五个验证项在同一台机器上编译、跑测试，整机 CPU 基本占满（量的那一段里别的进程占 59–98%）。移动版每页耗时的第一遍是这时候量的。为了在这种情况下也看得出 CPU 推理本来有多快，每种配置另量了一份“测量进程的优先级调高一档（高于正常）”的，和正常优先级的轮流跑：推理线程能排到别的任务前面，接近机器空闲时的数（不完全等于：同一个物理核上的另一个线程、内存带宽还是被占着）。
- **比较空的时候**（14:10 以后）：别的验证项停了，别的进程占 CPU 的中位数是 4–10%，个别进程量的时候到 25%（用户自己的程序照常开着）。服务器版每页耗时、输出一致性、节点分配、换宽度、宽度分档、连续处理都是这时候量的；移动版每页耗时在 15:49–16:13 按正常优先级重量了一遍，服务器版里忙的时候量的那一轮（5 个进程）也在 16:14–16:18 补量了。
- 第 3–5 节用的是比较空的时候的数。忙的时候那一遍放在 3.4，它说明的是另一件事：CPU 被别的任务占满时，CPU 推理慢多少，显卡推理慢多少。那一遍的结果文件留在 `tests/out/v10/runs-loaded/`，汇总是 `summary-loaded.md`。
- 换宽度的代价、宽度分档、连续处理（第 6、8 节）看的是同一个配置自己前后比，只量了优先级调高一档的那一份。

### 3.2 服务器版（6 页，平均每页 30.0 行）

| 配置 | 每页 | 是第一行的几倍 | 检测 | 方向分类 | 识别 | 识别每行 | 别的进程占的 CPU |
|---|---|---|---|---|---|---|---|
| CPU，1.31.1 | 1763（1637–1911） | 1.00 | 876 | 5 | 883 | 29.4 | 6% |
| CPU，1.24.4 | 1751（1636–1758） | 0.99 | 877 | 9 | 862 | 28.7 | 8% |

- **在这台机器上，DirectML（集成显卡）比 CPU 慢：移动版的耗时是 CPU 的 6.3 倍，服务器版是 3.2 倍。** 三段都慢：移动版检测 83 → 298 ms，方向分类 5 → 57 ms，识别 243 → 1737 ms。
- 慢不是因为算子回退到了 CPU（3.3），也不是因为输入的形状变来变去（第 8 节）。量的时候显卡在满负荷地算（本进程占显卡 92–95%），本进程只占 6% 的 CPU。就是这块集成显卡比这颗 CPU 慢。
- **ONNX Runtime 的版本不是原因**：同是 CPU，1.31.1 和 1.24.4 只差 1%。
- **Windows ML 那份运行时和官方的 DirectML 包没有差别**（移动版 2100 对 2097 ms，服务器版 5679 对 5704 ms）：它自带的就是同一个 DirectML 1.15.4。
- 这里只量了模型推理。整条流水线（含前后处理）每页多久见 V09 第 5 节，两边用的页不一样，不能直接比。

### 3.3 节点落在哪个执行提供程序上

| 模型 | 输入形状 | CPU 配置 | DirectML 配置 | 没落在 DirectML 上的算子 |
|---|---|---|---|---|
| 移动版检测 | 1×3×1600×1120 | CPU 352 个 | DirectML 258 个 | — |
| 移动版方向分类 | 6×3×80×160 | CPU 53 个 | DirectML 98 个，CPU 2 个 | `Slice`、`Concat` 各 1 个 |
| 移动版识别 | 6×3×48×640 | CPU 357 个 | DirectML 298 个，CPU 2 个 | `Slice`、`Concat` 各 1 个 |

| 服务器版识别 | 6×3×48×608 | CPU 187 个 | DirectML 184 个，CPU 2 个 | `Slice`、`Concat` 各 1 个 |

### 3.4 机器忙的时候（移动版，上午那一遍）

| 配置 | 正常优先级：每页 | 别的进程占的 CPU | 优先级调高一档：每页 | 别的进程占的 CPU |
|---|---|---|---|---|
| CPU，1.31.1 | 2589（617–4332） | 78% | 390（386–476） | 45% |
| CPU，1.24.4 | 2432（568–3432） | 81% | 没有量 | |
| DirectML @ 集成显卡 | 3075（2777–4614） | 97% | 2698（2543–4228） | 94% |
| Windows ML 的运行时 ＋ DirectML | 2797（2505–4504） | 96% | 没有量 | |

- **CPU 被别的任务占满时，CPU 推理慢到 7.8 倍（330 → 2589 ms），而且抖得厉害（617–4332 ms）；DirectML 只慢到 1.5 倍（2097 → 3075 ms）。** 这时候两边差不多。
- 把测量进程的优先级调高一档，CPU 推理回到 390 ms，接近空的时候的数。
- 这和产品有关：识别是打开文档之后在后台做的（方案 6.2），机器忙不忙看用户自己在干什么。“显卡推理不抢 CPU、也不怕 CPU 被抢”是它实在的好处；但在这块显卡上，要等 CPU 推理被拖慢 6 倍以上它才追得上。V09 报告 5.5 说的是同一件事的另一面：线程数用默认值时，机器一忙 CPU 推理吃亏很大。

- 建 DirectML 的会话本身不慢（三个会话 0.28–0.41 秒，CPU 是 0.12–0.29 秒）。多出来的在第一页：它比稳定之后的一页多 0.8 秒（移动版）到 1.6 秒（服务器版），是各个模型头一次推理时的准备，具体花在哪没有查。

## 6. 连续处理 1000 页

移动版模型，18 页轮着用，一个进程从头跑到尾，测量进程的优先级调高一档。量的时候别的任务已经停了（别的进程占 CPU 4–6%）。

| 配置 | 页数 | 报错 | 重建会话 | 用时 | 每页中位数（P95） | 每 108 页一个窗口：第 2 个 → 第 8 个 → 最后一个（中位数） | 工作集每 100 页涨 | 共享显存每 100 页涨 | 峰值工作集 |
|---|---|---|---|---|---|---|---|---|---|
| CPU（1.31.1） | 1000 / 1000 | 0 | 0 | 6 分 | 330 ms（464） | 333 → 329 → 329 | +0.14 MB（1388 → 1387 MB） | — | 1435 MB |
| DirectML @ 集成显卡 | 1000 / 1000 | 0 | 0 | 36 分 | 2181 ms（2850） | 2127 → 2184 → 2413 | −1.11 MB（1495 → 1484 MB） | 0（一直是 1289 MB） | 1750 MB |

- **两边都跑完了 1000 页，没有报错，没有重建过会话。**
- **内存、显存不涨。** CPU 的工作集全程在 1381–1396 MB 之间；DirectML 的工作集在 1472–1502 MB 之间，共享显存从第 10 页起一直是 1289 MB，专用显存 140 MB。

| 服务器版 | 6 页、180 行 | 1.2e-4 | 0 / 10,752,000 | 0 | 3.2e-4 | 0 | 0 / 0 | 0 |

## 8. 识别模型的输入宽度

识别模型的输入宽度跟着文字行的长短变（320–3200，32 的倍数），18 页里有 45 种形状。在显卡上，换形状有可能要重新编译、重新分配，所以单独量了三样。都是移动版的识别模型，测量进程的优先级调高一档。

**换宽度的代价**（一批 6 行；ms，中位数）：

| 配置 | 宽度 | 连着跑，一次 | 这种宽度头一次多花 | 和另一种宽度轮着跑，一次多花 |
|---|---|---|---|---|
| CPU | 320 | 12.0 | 3.5 | 1.0 |
| CPU | 960 | 37.2 | 1.3 | −1.1 |
| DirectML | 320 | 140.3 | 12.2 | 1.8 |
| DirectML | 960 | 397.9 | 6.4 | 0.2 |

八种宽度（352–1408）轮着跑，和每种连着跑比，多花的时间 CPU 是 −10.4 ms（一次 43.3 ms），DirectML 是 −1.4 ms（一次 359.1 ms），都在噪声里。整页流程里顺带看的也一样（第 3 节那一遍，正常优先级）：45 种形状各自头一次出现时，比之后多花的时间中位数是 CPU −2.2 ms、DirectML 0.2 ms，一遍 18 页下来 DirectML 合计多花 0.12 秒。

**宽度怎么分档**（只跑识别这一段，9 页；每页 ms，中位数）：

| 分法 | 形状种数 | CPU：稳定后每页 | 峰值工作集 | DirectML：稳定后每页 | 峰值工作集 | 共享显存 |
|---|---|---|---|---|---|---|
| 产品现在的分法（按长宽比排序，6 行一批，批宽取 32 的倍数） | 31 | 165 | 907 MB | 1751 | 1212 MB | 758 MB |
| 宽度按 320 一档，每批补满 6 行 | 7 | 381 | 925 MB | 2515 | 1294 MB | 738 MB |
| 同上，每一档建一个形状固定的会话 | 7 | 351 | 2382 MB | 2325 | 4164 MB | 3659 MB |

- **换形状几乎没有代价**，在这一版 DirectML（1.15.4）和这块显卡上，头一次出现的形状最多多花十来毫秒，轮着换不多花。所以“把宽度归成几档、少几种形状”这条路没有收益。
- **归档反而慢**：宽度按 320 一档并把批补满，要算的像素多了，CPU 慢到 2.3 倍，DirectML 慢到 1.4 倍。
- **形状固定的会话**在 DirectML 上只快 8%（2515 → 2325 ms），七个会话的内存到 4.2 GB、共享显存到 3.7 GB，建这七个会话要 1.0 秒。不值得。
- 也就是说，DirectML 在这块集成显卡上慢，不是形状变来变去造成的，换分法救不回来。

## 10. Windows ML

### 10.1 它现在是什么（微软文档，2026-11-12 查）

- Windows ML 是微软分发的一份 ONNX Runtime，加一套“执行提供程序目录”的接口。**它自带的执行提供程序只有两个：CPU 和 DirectML**（文档里 DirectML 后面标着 legacy）。
- 各家硬件专用的执行提供程序不在包里，在 Windows 11 24H2（内部版本 26100）及以上的机器上，按硬件和驱动从目录里**按需下载、装进系统**：`NvTensorRtRtxExecutionProvider`（NVIDIA，要 GeForce RTX 30 系及以上、驱动不低于 32.0.15.5585）、`AMDGPUExecutionProvider`（AMD，要 RDNA 3 及以上、驱动不低于 25.10.13.09）、`OpenVINOExecutionProvider`（Intel）、`QNNExecutionProvider`（高通 NPU）、`VitisAIExecutionProvider`（AMD NPU）。
- 两种部署方式：运行时随应用带（三个 DLL，文档说约 41 MB；C#、C++/WinRT、C/C++ 都行，NuGet 包 `Microsoft.Windows.AI.MachineLearning` 面向 Windows 10 内部版本 18362 及以上）；或者依赖系统里装的 Windows App SDK 运行时（C/C++ 不支持这种）。
- ONNX Runtime 文档的 DirectML 一页，开头现在写着：DirectML 处于维持性维护，仍然支持，新功能开发转到了 Windows ML。

### 10.2 在这台机器上落到哪个执行提供程序（实测）

- `winml_probe.py`（Windows ML 的 Python 绑定；系统里已经装着 Windows App Runtime 2.6.5，没有另装东西）：目录的 `FindAllProviders()` 对这台机器**一个执行提供程序也没有列出来**。它自带的 ONNX Runtime 1.25.2 里只有 `DmlExecutionProvider` 和 `CPUExecutionProvider`，看到的设备是 CPU 和集成显卡。
- 所以在这台机器上用 Windows ML，显卡这一条只能落到它自带的 DirectML（和第 3 节量的是同一个 DirectML 1.15.4），不然就是 CPU。
- 这和文档对得上：集成显卡是 RDNA 2，不够 AMD 那个执行提供程序要的 RDNA 3；GTX 1070 就算是好的，也不在 NvTensorRtRtx 的支持范围里（要 RTX 30 系及以上）。GTX 1070 这一句是按文档说的，显卡坏着，没有实测。
- 结论：任务书问的“在这台机器（GTX 1070）上会落到哪个执行提供程序”——DirectML。在 R3（RTX 4050，Windows 11 24H2）上按文档会拿到 NvTensorRtRtx，**那是另一个执行提供程序，这台机器上量不了，也推不出来。**

### 10.3 量了什么，没量什么

- 量了：Windows ML 那份 ONNX Runtime（1.25.2）加它自带的 DirectML，跑在集成显卡上，见第 3–5 节表里“Windows ML 的运行时 ＋ DirectML”一行。每页耗时、初始化、内存都和官方的 DirectML 包（1.24.4）一样（移动版 2100 对 2097 ms，服务器版 5679 对 5704 ms），节点的分配也一样（3.3）。
- 没有量：目录里的任何一个执行提供程序（这台机器上没有可用的）；`--ensure-ready`（会从微软商店下载并往系统里装东西）没有跑。

### 10.4 要走这条路的话，随包带什么

- 运行时随包带：`Microsoft.Windows.AI.MachineLearning.dll`、`onnxruntime.dll`、`DirectML.dll`，共 43.3 MB（第 9 节）。只用它的 ONNX Runtime 和 DirectML、不用目录的话，前一个可以不带（11.4 的小程序这样跑通了），42.3 MB。
- 硬件专用的执行提供程序不随包带，由目录接口联网下载、装进系统，各有各的许可条款（NVIDIA、AMD、Intel 的）。产品的定位是“安装后断网可用”“引擎进程不联网”（方案 1.1、13.3），这一步只能做成用户同意之后、由主进程触发的可选项；断网的机器上只剩 DirectML 和 CPU。
- Windows 11 24H2 以下的系统（R2 是 Windows 10 22H2）拿不到目录里的执行提供程序，只有自带的 DirectML 和 CPU。也就是说：**不管走不走 Windows ML，旧系统、集成显卡、老独立显卡最后用的都是 DirectML。**

## 11. 产品里怎么接（只写办法，没有实现）

### 11.1 先要定用哪一份 `onnxruntime.dll`

产品现在：`ort` `=2.0.0-rc.15`，特性 `std, load-dynamic, tracing, api-31`，运行时装载 CPU 版 `onnxruntime.dll` 1.31.1。**这一份里没有 DirectML**，要用显卡就得换运行时：

| 路 | 运行时 | 版本 | 随包带 | `ort` 的特性 | 核对到哪一步 |
|---|---|---|---|---|---|
| A | NuGet `Microsoft.ML.OnnxRuntime.DirectML` | 1.24.4（官方最后一版） | `onnxruntime.dll` ＋ `DirectML.dll`，35.9 MB | 加 `directml`；`api-31` 换成 `api-24` | 小程序跑通（11.4） |
| B | Windows ML 包里的那一份 | 1.28.3（包 2.5.96） | `onnxruntime.dll` ＋ `DirectML.dll`，42.3 MB；要用目录再加 1 MB | 加 `directml`；`api-28` 或更低 | `api-24` 的小程序装载它跑通；`api-28` 只做了编译检查 |
| C | 自己用 `--use_dml` 编 1.31.1，或者 `ort` 作者（pyke）预编译的 1.31 带 DirectML 的静态库 | 1.31.x | 同 A | 加 `directml`，`api-31` 不动 | 没有验证 |

为什么要动 `api-31`：`ort` 用 `load-dynamic` 时，装载的 DLL 版本低于编译时选的 `api-N` 就拒绝（小程序实测：`api-31` 的构建装载 1.24.4 和 1.28.3 都报 `ort 2.0.0-rc.15 is not compatible with the ONNX Runtime binary …; expected version >= '1.31.x'`）。反过来没问题：`api-24` 的构建装载 1.24.4、1.28.3、1.31.1 都正常。`engine/magpdf-scan` 现在的代码在 `api-24 + directml`、`api-28 + directml` 下都能通过 `cargo check`（拿一份不改动的副本在仓库外面试的）。

### 11.2 建会话

改的地方是 `runtime.rs` 的 `load_session`。开了 GPU 时：

```rust
use ort::ep;

let dml = ep::DirectML::default()
    .with_device_id(adapter_index)   // 或者 .with_performance_preference(ep::directml::PerformancePreference::HighPerformance)
    .build()
    .error_on_failure();             // 一定要：默认是注册失败只记一条日志，会话照样建出来，跑在 CPU 上
builder = builder
    .with_memory_pattern(false)?     // DirectML 的要求
    .with_parallel_execution(false)? // DirectML 的要求
    .with_execution_providers([dml])?;
```

- `error_on_failure()` 不能省。小程序实测：不加它，给一个不存在的显卡序号，或者装载的是 CPU 版的 DLL，会话都能建出来，推理照常，实际跑在 CPU 上，没有任何报错；加了它，前一种在建会话时报 DXGI 的错（887A0002），后一种报 `DirectML is not supported in this build of ONNX Runtime`。
- 先问一句 `ep::DirectML::default().is_available()`：装载的 DLL 里没有 DirectML 时返回 `false`，界面上就不该出现 GPU 选项。
- DirectML 的会话同一时刻只能有一个线程调 `run`（ONNX Runtime 文档）。
- 选显卡：`with_device_id` 的序号是 DXGI `EnumAdapters1` 的顺序。这台机器上三个序号是同一块集成显卡，可见不能只看名字；要跳过软件适配器，同一块显卡出现多次时只留一个。不想自己枚举就不给序号，改用 `PerformancePreference::HighPerformance`，由 DirectML 自己挑高性能的那一块（小程序试过不给序号能跑；“挑的是不是独立显卡”要在有两块好显卡的机器上验证）。
- 形状固定的会话更快一些（第 8 节）：`with_dimension_override("DynamicDimension.0", 批大小)` 等把输入的维度定死。代价是每种形状一个会话，内存和显存成倍涨。

### 11.3 什么情况下回退到 CPU

| 情况 | 怎么发现 | 核对过吗 |
|---|---|---|
| 运行时里没有 DirectML（装的是 CPU 版） | `is_available()` 为 `false` | 小程序实测 |
| 没有能用的显卡：显卡序号无效、驱动坏了（这台机器的 GTX 1070 就是，DXGI 里根本没有它）、只有软件适配器（远程桌面、虚拟机） | 建会话报错（要 `error_on_failure()`） | 序号无效实测；其余没有试 |
| `DirectML.dll` 没带或者版本太旧 | 旁边没有时会去装载系统自带的那一份。Windows 11 24H2 上系统自带 1.15.5，能跑；更早的系统自带的更旧，会怎样没有验证。**所以一定要把 `DirectML.dll` 放在 `onnxruntime.dll` 旁边**（实测装载的是旁边这一份，不是程序目录也不是系统目录的） | 小程序实测（只在这台机器上） |
| 推理中途出错：显卡驱动重置或更新、睡眠唤醒、切换远程桌面、显存不够 | `run` 返回错误：换成 CPU 会话把这一页重跑，这次运行里不再用显卡，记日志 | 没有试 |
| 显卡比 CPU 慢（这台机器的集成显卡就是） | 第一次开启时用一张内置的小图各跑一遍，显卡不比 CPU 快就不用；结果按“显卡型号 + 驱动版本”记下来 | 建议，没有做 |
| 输出对不上 | 同一次自检里比两边的输出（第 7 节的差别是 1e-3 量级，文字完全一样），差得多就不用 | 建议，没有做 |

另外两件事：建 DirectML 会话比 CPU 慢得多（第 4 节），要放在后台做，不要卡住第一页；会话和显存在不用的时候要能放掉（第 5 节）。

### 11.4 核对用的小程序

为了确认上面说的不是照着文档猜的，写了一个一次性的 Rust 小程序（`ort` `=2.0.0-rc.15`，`load-dynamic` ＋ `directml`，分别按 `api-24`、`api-31` 编），用移动版检测模型跑了 13 种“DLL × 编译时的 API 版本 × 注册方式”的组合。它放在仓库外面（`D:\workspace\magpdf-wt\tmp\v10\ort-probe`，结果在同目录的 `cases.log`），**没有入库**：任务书要求不动 Rust 代码，往仓库里加一个 Cargo 工程也可能碰到工作区和 CI。合入时也没有放进来（它是一次性的试验，脚本里写死了本机的路径）；源码 134 行和 13 组的记录还留在开发机的那个目录里，以后真要接显卡时照 11.1–11.3 重做一遍比留着它更可靠。

### 11.5 走 Windows ML 的目录的话

没有做，只查了办法：NuGet 包里有 C 头文件 `include/WinMLEpCatalog.h`（`WinMLEpCatalogCreate`、`WinMLEpCatalogEnumProviders`、`WinMLEpEnsureReady`、`WinMLEpGetLibraryPath` 等）和导入库，Rust 里可以直接声明外部函数来调；拿到执行提供程序的库路径之后用 `ort` 的 `Environment::register_ep_library` 注册，再用 `SessionBuilder::with_devices` 或 `with_auto_device` 选设备（这几个接口 `api-22` 起就有）。`WinMLEpEnsureReady` 会联网下载并往系统里装东西，见 10.4。

### 11.6 许可

- 带 DirectML 的 `onnxruntime.dll`：MIT，和现在一样。
- `DirectML.dll`（`Microsoft.AI.DirectML`）：**微软的专有许可条款**（包里的 `LICENSE.txt`：MICROSOFT SOFTWARE LICENSE TERMS — MICROSOFT DIRECTX MACHINE LEARNING），不是开源许可证，不在仓库的白名单里。第 1 条允许随自己开发的应用分发、只能用在 Windows 和 Xbox 上；第 2 条写着软件可能收集信息发给微软；第 6 条写着可能自动检查并安装更新；第 3 条禁止反向工程。《开源许可与合规清单》里已经有 DirectML 一行（“微软可再分发许可，按微软条款随安装包分发”），第 2、第 6 条和产品“文档不离开本机”“日志不自动上传”（方案 1.1、13.4；`runtime.rs` 里也因此关掉了 ONNX Runtime 的遥测）的说法要有人对一下：这个 DLL 实际上发不发数据，**没有验证**。
- Windows ML 的运行时：同样是微软的专有条款（`license.txt`：MICROSOFT SOFTWARE LICENSE TERMS — Microsoft Windows ML Runtime）。目录里各家的执行提供程序另有各自的条款。

做这一项的子任务在量到一半时停了，没有回来。合入时做了这些：

## 13. 没做的和没验的

- **计划 V10 要的三组数一组也没有量。** R3（RTX 4050，Windows 11 24H2）上的 Windows ML 和强制回退的 DirectML、R2（Windows 10 22H2，集成显卡）上的 DirectML 都没有；R1 上也没有。机器到了之后，建好虚拟环境、放好模型和命令行工具，同一条命令可以直接量 CPU 和 DirectML。Windows ML 目录里的执行提供程序（R3 上按文档是 NvTensorRtRtx）脚本还不会量：`winml_probe.py --ensure-ready` 能把它装上并给出库路径，`bench.py` 里注册它、选设备的那一段没有写，因为这台机器上没法试。
- **GTX 1070 没有量。** 设备管理器里是代码 43，没有修（2.1）。修好之后重跑同一条命令，脚本会自己多量一种配置。
- **样本不是计划要的那一批。** 计划写的是和 V09 同一批样本（标注过的真实单证）；这里用的是 V09 的 18 页合成样本，都是 A4 打印体，检测模型的输入只有 1120×1600 一种形状。真实单证大小不一时，检测模型换形状的代价没有量（识别模型换宽度的量了，第 8 节）。
- **产品里没有接。** Rust 代码一行没动。第 11 节的办法只用仓库外面的小程序核对过，小程序没有入库。
- **显卡中途出事没有试**：驱动重置或更新、睡眠唤醒、切换远程桌面、显存不够时 `run` 返回什么、会话还能不能接着用。
- **Windows 10 上没有验。** 随包带的 `DirectML.dll` 1.15.4 在 Windows 10 22H2 上能不能用、那里系统自带的是哪一版，都没有实测。
- **`DirectML.dll` 发不发数据没有验证**（许可条款第 2 条，11.6），没有抓包。
- **专用英文识别模型 `en_PP-OCRv5_mobile_rec` 没有量。** 量的是移动版、服务器版各自的检测、方向分类和多语言识别。
- **11.1 的路 C 没有验证**：自己编带 DirectML 的 1.31.1，或者用 pyke 预编译的库。
- **DirectML 的开关没有逐个量。** `ep.dml.enable_graph_capture` 试了一下：打开之后识别模型的 `run` 返回的输出是空的，没有再查。`disable_metacommands`、`ep.dml.disable_memory_arena` 等没有试。
- **几个会话同时跑没有量**（比如几页并行识别）。DirectML 的会话同一时刻只能有一个线程调 `run`。
- **`PerformancePreference::HighPerformance` 挑的是不是独立显卡**没有验，要有两块好显卡的机器。
- **DXGI 序号 1、2 没有量**，应该和序号 0 是同一块集成显卡（`--all-adapters` 可以都量）。
- **耗电、发热没有量。** 笔记本上要不要默认用显卡，这两样也得看。
- **机器不是完全空闲。** 第 3–8 节的数是别的验证项停了之后量的，但用户自己的程序照常开着（别的进程占 CPU 的中位数 4–10%，安卓模拟器偶尔用一下显卡）（2.5）。

## 14. 对方案和计划的修改建议

下面这些文件是共用的，这个分支没有改，请协调者定了之后改。

1. **《方案》2.2**“有显卡时可用 GPU 加速：Windows 11 24H2 起用 Windows ML，更早的系统回退到 DirectML”，补上三件查实的事：
   - Windows ML 自带的执行提供程序只有 CPU 和 DirectML。各家显卡专用的要联网从目录下载、装进系统，只在 Windows 11 24H2 及以上有，而且只管比较新的显卡（NVIDIA 要 RTX 30 系及以上，AMD 要 RDNA 3 及以上）。集成显卡和老显卡即使在 Windows 11 24H2 上，用的仍然是 DirectML。
   - 带 DirectML 的 ONNX Runtime，官方单独发布的停在 1.24.4。产品现在用 1.31.1（CPU 版，里面没有 DirectML）；要用显卡，运行时得换成 1.24.4，或者 Windows ML 包里的 1.28.3，或者自己编。
   - 建议写明：v1.0 只带 CPU 版运行时，不做 GPU 加速；R3、R2、R1 上量过之后再定要不要做成可选项（理由见结论）。
2. **《方案》12.1** “ONNX Runtime（含 DirectML 回退）约 30–40 MB”按实测改：只带 CPU 版 17.3 MB；带 DirectML 35.9 MB；Windows ML 的运行时随包带 43.3 MB（第 9 节）。v1.0 只带 CPU 版的话，这一行是 17.3 MB，基础安装合计少 13–23 MB。
3. **《方案》第 15 节**：
   - “低配电脑 OCR 慢”的对策里有“有显卡时用 GPU 加速（2.2）”。低配机多半只有集成显卡，这条对策在集成显卡上成不成立没有数据；这台开发机的集成显卡上 DirectML 比 CPU 慢（第 3 节）。建议在参考机上量过之前，不把它当对策写。
   - “GPU 推理接口变动”一行补上：带 DirectML 的 ONNX Runtime 已经停在 1.24.4；Windows ML 的硬件专用执行提供程序要联网下载并装进系统，和“安装后断网可用”“引擎进程不联网”（1.1、13.3）有出入。
4. **《P0 技术验证计划》V10**：
   - 进展写成：开发机上有 CPU 对 DirectML（集成显卡）的参考数据；R3、R2 没有量，“GPU 加速是否默认开启”没有定。
   - 内容里加上 R1。默认开不开，受影响最大的是只有集成显卡的机器，计划里只有 R2 一台。
   - V10 现在只有指标、没有通过线。建议补一条，比如“稳定之后每页推理耗时不到 CPU 的一半，输出的文字和 CPU 一致，连续 1000 页不出错”才考虑默认开启。具体的数请评审时定。
   - 样本写明用哪一批：计划写的是和 V09 同一批；真实样本没到之前只能用合成样本。
5. **《开源许可与合规清单》**：
   - DirectML 一行：许可是微软的专有条款（`Microsoft.AI.DirectML` 包里的 `LICENSE.txt`），不是开源许可证；条款里有“可能收集信息发给微软”“可能自动检查并安装更新”两条，要法务或负责人对一下。
   - Windows ML 一行的“是否随安装包分发在 P0 定”：建议定为 v1.0 不随包分发。
6. **以后真要接显卡时才需要改的**（现在不用动）：工作区 `Cargo.toml` 里 `ort` 的特性（加 `directml`，`api-31` 降到 `api-24` 或 `api-28`）；`models/manifest.json`、`models/README.md` 里的运行时（换成带 DirectML 的包，多一个 `DirectML.dll`）。
7. **开发机的 GTX 1070** 要修一下（重装驱动或者重启），修好之后重跑同一条命令，把“DirectML @ 独立显卡”这一行补上。
8. **核对用的 Rust 小程序**（11.4）合入时没有入库。
