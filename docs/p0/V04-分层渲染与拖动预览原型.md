# V04 分层渲染与拖动预览原型 —— 验证报告

- 分支：`main`（这一项直接在主干上做，没有另开分支）
- 基线：`main` @ `41c26c7`
- 日期：2026-11-11
- 对应方案：《方案》3.2 拖动预览、3.3 渲染调度；《接口协议》6.3 `render.layered`、9.2–9.3 `MAG_RenderPageFiltered`；《P0 技术验证计划》V04
- 结论：
  1. **拖动对象时，对象本身跟着鼠标走了**（原来是一个虚线框），做法和方案 3.2 一致：拖动开始时引擎把页面渲染成两层，拖动过程中界面只用 WebGL 挪对象层，不向引擎发任何请求。缩放（拖控制点）走的是同一条路。
  2. **通过线（R1 上，5000 个对象的页和 300 dpi 整页扫描件，拖动时帧时间 P95 不超过 16.7 ms）：R1 上没有量，不能说达到。** 开发机上（100 Hz 的屏，画布跑在集成显卡上，同一块显卡上还开着别的程序）：四种窗口大小（1440×900 到 3440×1400）、两种页面各拖 40 秒，8 次里 6 次没有一帧超过 16.7 ms，另外两次是 3998 帧里 1 帧、3987 帧里 10 帧。但在这之前，机器上一个安卓模拟器每隔 5 秒占一下显卡的那段时间里，3440×1400 下拖 40 秒有 3.2% 的帧超过 16.7 ms，一簇一簇地掉；端到端测试默认只量两秒，碰上一簇时 P95 是 20 ms。详见第 3 节。
  3. 拖动中每帧的工作量和页面有多复杂没有关系：每帧脚本时间的中位数，5000 个对象的页是 0.3–0.6 ms，8 个对象的页是 0.2–0.3 ms；占显卡的份额和“每帧把画布重画一遍”一样。
  4. **`MAG_RenderPageFiltered` 没有做，PDFium 分支没有改。** 用公开接口 `FPDFPageObj_SetIsActive` 在渲染前后临时隐藏对象，效果相同。这样做成立的前提是引擎每渲染一块瓦片都重新打开页面；以后要是让页面一直开着，就得做那个扩展接口了（第 2 节）。
  5. **预览和松手之后的画面有差别，比方案 3.2 第 4 条说的多、也大**：带混合模式的对象在拖动中是另一个样子（不是“细微差别”）；被别的对象压着的对象，拖动中会浮到上面来；视图缩放不是 100%、200% 这样的整档时，文字松手的一瞬间边缘会变一下。都是松手后恢复准确显示。要不要处理、怎么处理，需要评审时定（第 4 节）。
  6. 顺带量到一件 V05 的事：**窗口大的时候，修改到重画完超过了 150 ms**（2560×1400 以上，中位数 135–144 ms，P95 149–186 ms）。原因和出路见 3.6。

## 1. 做法

```
按住对象开始拖
  └ 画布控制器：向瓦片来源要两层
      ├ 底图：这一页在视口里的瓦片，去掉被拖的对象           render.tiles + layer {mode: "without", objectIds}
      └ 对象层：被拖对象所在位置的瓦片，只有被拖的对象、别处透明  render.tiles + layer {mode: "only", objectIds}
两层的第一批瓦片到齐之前：照旧画虚线框
到齐之后的每一帧：平常的瓦片 → 底图盖在这一页上 → 对象层按鼠标的位移挪过去画（不向引擎发请求）
松手：提交修改命令，预览留着；这一页重画好的瓦片到齐了才撤
```

### 1.1 引擎：渲染时去掉或只留一部分对象

- `pdfium-sys` 加了 `render_rect_filtered(page, surface, rect, flags, background, filter)`，`filter` 是 `LayerFilter::Without(序号)` 或 `LayerFilter::Only(序号)`，序号是对象在页内的层级。
- 做法：渲染前把不要的对象设成“不活动”（`FPDFPageObj_SetIsActive(obj, false)`，PDFium 渲染时跳过不活动的对象），渲染完设回来，中途出错也会设回来。本来就不活动的对象不去动。只管页面顶层的对象；Form XObject 里面的对象跟着它所在的那个顶层对象走。
- 编辑会话把对象编号换成当前的层级序号（`EditSession::z_indices`），所以改过层级、删过对象之后要的还是对的那些对象。编号不在这一页上时报错，这一批瓦片不渲染。
- 对象层渲染在全透明的背景上。位图是**没有预乘**的 BGRA：一半透明的红色是 `[0, 0, 255, 128]`，不是 `[0, 0, 128, 128]`。这一点有用例守着，界面合成前自己预乘。

### 1.2 协议：`render.tiles` 多一个 `layer`

```jsonc
// render.tiles 的参数，其余不变
{ "docId": 1, "pageId": 0, "scale": 1.0, "tiles": [{ "x": 0, "y": 0 }], "priority": "visible",
  "layer": { "mode": "without" | "only", "objectIds": [12, 13] } }   // 不带就是平常的整页
```

- 各层的瓦片和平常的瓦片走同一条路：立即应答 `requestIds`，渲染完发 `render.tileReady`，像素在共享内存槽位里。
- 槽位表的键里多了“哪一层”，同一个位置上整页的瓦片和各层的瓦片互不覆盖。
- 带 `layer` 的请求不记进恢复文件的视图：它是拖动预览要的，不是用户换了地方看。
- 和《接口协议》6.3 的 `render.layered` 不一样，理由见第 5 节。

### 1.3 界面

- `TileProvider` 多了一个能力标记 `layers` 和请求里的 `layer`。`EngineTileProvider` 把它带给引擎，裁瓦片时给对象层做预乘（`(c × a + 127) / 255`）；缓存的键里带着层和文档版本，文档一变全部作废。模拟文档的瓦片来源不会按层渲染，拖动时照旧是虚线框。
- `DragLayers`（`canvas/dragLayers.ts`）只管要瓦片、记住纹理：两层的第一批都到了才算就绪；有一块渲染不出来，整个不用。
- 画布控制器（`canvasController.ts`）：
  - **要哪些瓦片。** 底图要这一页在视口里的全部瓦片。对象层要被拖对象的外框（四周多留 4 个像素）盖住的瓦片，最多伸到视口周围各一个视口那么远——整页的图被拖的时候，对象层就是视口里的全部瓦片。
  - **怎么画。** 只是挪动时，对象层整体平移，位移取整到设备像素；缩放时，按“原来的外框 → 现在的外框”把对象层拉伸，相邻瓦片共用一条边。
  - **选框**跟着预览走；有了分层预览就不再画虚线框，也不画控制点。
  - **拖动中换了缩放档**（Ctrl + 滚轮）：按新的档位重新要两层。**拖动中视口挪了**（滚轮）：新露出来的部分补要底图——这种情况下拖动中是有请求的。

### 1.4 松手之后

修改命令发出去之后，这一页的瓦片要几十毫秒才能重画好。这期间如果撤掉预览，对象会闪回原处再跳到新位置。所以预览留着，直到下面任何一条成立：

- 这一页的修订号变了，并且视口里它的瓦片都换成了新的（正常的结局）；
- 对象不在松手的位置上（偏差超过 0.5 pt）：修改被拒绝了，或者引擎给的结果不一样；
- 过了 1.5 秒；
- 又开始拖别的，或者又来了一次修改。

两层还没到齐就松手的话不留预览（之后到的瓦片可能是修改之后渲染的，位置对不上），和原来一样会看到对象从原处跳过去。

### 1.5 不做分层预览、照旧画虚线框的情况

- 选区跨页（两层是按页渲染的）；
- 选区超过 500 个对象；
- 对象层超过 128 块瓦片；
- 瓦片来源不会按层渲染（模拟文档）；
- 有瓦片没渲染出来，或者 WebGL 上下文丢了：这一次拖动不再重试。

## 2. 为什么没有做 `MAG_RenderPageFiltered`

方案 3.2 对这个接口的要求是“只在渲染时过滤对象，不改变对象状态”。`FPDFPageObj_SetIsActive` 是 PDFium 现成的公开接口（标着 Experimental），它**会**改对象的状态：除了活动标记，还会把对象标成“已修改”。这个“已修改”的标记如果留到重新生成内容流的时候，对象所在的那条内容流会被重写，哪怕对象根本没动过——这正是保真校验要防的事。

现在的引擎里它留不到那个时候：

- “已修改”的标记记在页面句柄里的对象上，不在文档里；
- 引擎每渲染一块瓦片都是“打开页面 → 渲染 → 关掉页面”，修改也是各自打开、关掉；页面句柄一关，标记就没有了。

有用例直接验证这一点（`pdfium-sys/tests/layers.rs` 的 `a_layer_render_leaves_no_trace_once_the_page_is_closed`）：渲染两层、关掉页面，再打开重新生成内容流、保存，内容流和原来逐字节相同；反过来，在同一个页面句柄上渲染完接着重新生成，内容流就被重写了——后一半是对照，没有它就分不出前一半是不是真的没有痕迹。引擎进程一层也有用例：分层渲染之后整页的瓦片逐字节不变，文档版本号不变，照常能改。两种 PDFium 构建（原版预编译库、V03 修过生成器的）下都通过。

所以在现在的引擎结构下，公开接口够用，不用改分支。什么时候不够：

- **引擎让页面一直开着的时候。** 现在每块瓦片都重新打开一遍页面：对象多的页要重新解析，扫描页要重新解码图像（这部分占瓦片耗时的多少没有单独量）。要省掉它，页面句柄就得留着，渲染和修改共用，这时“已修改”的标记会漏进下一次重新生成。到那一步有两条路：做 `MAG_RenderPageFiltered`；或者渲染另用一个只读的页面句柄。
- **上游改了这个接口的时候。** 它标着 Experimental。

没有量的：只留一个对象时，引擎要把页上其余的对象逐个设成不活动再设回来，5000 个对象就是近一万次调用。从预览就绪的时间看（3.3，5000 个对象的页不比扫描页慢）它不是问题，但没有单独量过。

## 3. 实测

### 3.1 环境、样本、量法

- **机器：开发机，不是参考机 R1。** 屏幕 3440×1440、100 Hz、缩放 100%。画布的 WebGL 经 ANGLE（Direct3D 11）跑在处理器自带的集成显卡上（AMD Radeon Graphics），屏幕也接在它上面；机器上另有一块独立显卡，在系统里是出错的状态，没有参与。
- **这不是一台干净的测量机。** 同一块显卡上还有开发用的编辑器（一直占着 4–18%）、一个安卓模拟器、聊天软件。3.4 的掉帧就是这么来的。
- 发布版构建；PDFium 是仓库默认的原版预编译库。
- **样本都是画出来的**，由 `tests/corpus/perf/generate.py` 生成到 `tests/out/perf/`（不入库）：

| 叫法 | 文件 | 内容 | 拖的是什么 |
|---|---|---|---|
| 5000 个对象的页 | `a4-5000-objects.pdf` | A4，4999 个小色块加一个 140×70 pt 的深色块 | 那个深色块（最上面的对象） |
| 扫描页 | `scan-300dpi.pdf` | A4，一张 2480×3508 的灰度 JPEG 铺满整页 | 整页的图（页上唯一的对象） |
| 扫描页加章 | `scan-300dpi-stamp.pdf` | 同上，上面再放一个 140×70 pt 的色块 | 那个色块 |
| 灰度色块样本 | `tests/corpus/synthetic/color-devicegray.pdf` | 300×200 pt，8 个对象 | 标题文字 |

  色块没有文字、剪切、透明，是最容易渲染的一类页面；“扫描件”是纸的底色加噪声和一行行深色的条。**真实的图纸和扫描件上，预览就绪的时间和修改到重画完的时间会更长；拖动中的帧间隔不受影响**（那时不渲染页面）。
- **量法**：界面端到端测试 `apps/desktop/e2e/smoke.mjs`。真实的鼠标事件（经 CDP 注入，走浏览器正常的事件分发）：按住对象，不停地绕圈挪，一条接一条地发。页面里用 `requestAnimationFrame` 记下每一帧的时刻，算帧间隔；同时取画布自己记的每帧脚本时间。测试断言拖动过程中分层预览一直在用、没有向引擎要过瓦片。最后回到原处松手，文档不变。
  - 默认拖 2 秒（约 200 帧）。`MAGPDF_E2E_DRAG_MS` 可以改长，`MAGPDF_E2E_WINDOW` 可以改窗口大小，例如：

    ```powershell
    python tests/corpus/perf/generate.py
    $env:MAGPDF_E2E_EDIT_PDF = (Resolve-Path tests/out/perf/a4-5000-objects.pdf)
    $env:MAGPDF_E2E_WINDOW = '3440x1400'; $env:MAGPDF_E2E_DRAG_MS = '40000'
    pnpm --filter @magpdf/desktop e2e      # 结果的 drag 一项里有帧数、超过 16.7 ms 的帧数和它们落在第几秒
    ```
  - **屏幕是 100 Hz，这比通过线严。** 一帧只要晚了一次刷新，间隔就是 20 ms，超过 16.7 ms；同样的一帧在 60 Hz 的屏上只要 16.7 ms 之内画完就不算掉。
- “预览就绪”从画布开始要两层瓦片算起，到两层的第一批都变成了纹理为止。不含从按下鼠标到认出这是拖动的时间，也不含之后等下一帧的时间。

### 3.2 默认窗口（1440×900，画布 748×763 像素），每次拖 2 秒

每种页面 5 次运行。页面按“适合页面”显示：A4 的三种是 63.7%，灰度色块样本是 175%。

|---|---|---|---|---|---|
| 5000 个对象的页 | 12 / 2 | 37–47 ms | 10 / 10.1–20 / 10.1–20.1 ms | 12、0、0、0、0 | 0.3–0.6 / 0.5–3 ms |
| 扫描页 | 12 / 12 | 55–65 ms | 10 / 10.1 / 10.1–11.1 ms | 0、0、0、0、0 | 0.3–0.5 / 0.5–0.6 ms |
| 扫描页加章 | 12 / 1 | 51–71 ms | 10 / 10.1 / 10.1–20 ms | 0、0、0、2、0 | 0.2–0.6 / 0.4–1 ms |
| 灰度色块样本 | 12 / 3 | 24–26 ms | 10 / 10.1 / 10.1–10.2 ms | 0、0、0、0、0 | 0.2–0.3 / 0.5–0.6 ms |

- 20 次里 18 次没有一帧超过 16.7 ms。有掉帧的两次（12 帧、2 帧）当时机器上在发生什么没有记录。
- 在这之前的构建上（界面代码相同，引擎少一处和拖动无关的改动）还跑过两批各 20 次，一批期间不做别的，一批期间照常在编辑器里干活：40 次没有一帧超过 16.7 ms，两批没有差别。
- **默认窗口也不是不会掉。** 更早的一批（那时还没有开始记显卡占用）里，扫描页 5 次运行每次都有 5–20 帧超过 16.7 ms，5000 个对象的页 5 次里有 1 次（16 帧）。当时是什么在抢显卡没有记录；之后默认窗口下只在上面那两次里又见到。
- 预览就绪之前的这几十毫秒里，用户看到的是虚线框，然后对象跳到鼠标的位置开始跟着走。

- 每一格整段的帧间隔 P95 都是 10.1 ms，每帧脚本时间 P95 0.4–0.7 ms。

- **预览就绪的时间随窗口变大而变长**：窗口大，页面放得大，要渲染的瓦片多。2560×1400 以上是 95–165 ms（含上面那一次和 3.4 的几次），这段时间里用户看到的还是虚线框。它没有通过线，但 100 ms 上下已经是看得出来的停顿。

### 3.4 别的程序抢显卡的时候

在跑上面这一批之前几分钟，同样是 3440×1400、5000 个对象的页、拖 40 秒：**3871 帧里 122 帧超过 16.7 ms（3.2%）**，最大间隔 30 ms，整段的 P95 仍是 10.1 ms。掉帧是一簇一簇的，40 秒里落在第 2、7–8、12–13、18、23–24、28、33–34、38–39 秒，每簇 10–19 帧，大约每 5 秒一簇。端到端测试默认只拖 2 秒，碰上一簇的那一次是 185 帧里 14 帧，P95 20 ms；碰不上就是 0。

查下来，这一簇一簇的掉帧来自机器上的一个安卓模拟器（进程名 `MuMuNxDevice`）：

- 它每隔约 5.1 秒占用这块显卡 24%–40%，持续一秒左右。让画布连续每帧重画 40 秒，同时每秒记一次各进程的显卡占用：7 簇掉帧每一簇都和模拟器占显卡的那一秒对得上（两边都是一秒一个数，对齐的精度也就是一秒）；模拟器占了显卡而没有掉帧的有 1 次；没有哪一簇掉帧出在模拟器空闲的时候。
- 模拟器不占显卡之后（3.3 里 3440×1400 的两次和之后那一次），同样的窗口、同样的操作，一共 11997 帧里 1 帧。
- 画布越大掉得越多。让画布连续每帧重画 40 秒（不拖动），模拟器照常每 5 秒占一次：

| 窗口 | 画布（像素） | 帧数 | 超过 16.7 ms |
|---|---|---|---|
| 1440×900 | 748×763 | 4008 | 0 |
| 1920×1040 | 1212×864 | 4005 | 9（0.2%） |
| 2560×1400 | 1852×1224 | 3972 | 47（1.2%） |
| 3440×1400（两次） | 2732×1224 | 3952、3919 | 62、90（1.6%、2.3%） |

- **不是拖动预览特有的**：每帧重画不涉及分层，照样掉。拖动时画布的 GPU 进程占这块显卡的份额和每帧重画时一样——默认窗口约 20%，1920×1040 约 20%，3440×1400 约 35%（5 秒平均）。
- **不是 2D 叠加层（选框、标尺）的开销**：把叠加层藏起来再量，3440×1400 下 45 秒、4404 帧里照样掉了 109 帧（2.5%）。
- 不是输入注入的问题：每帧重画时没有任何输入。也不是脚本慢：掉帧的那些秒里，每帧脚本时间的 P95 大多在 1.2 ms 以内，个别是 5–8 ms，都不到一帧的时间。

这一小节里除了第一段，数字是用临时脚本量的，没有入库：起发布版程序、用 Win32 改窗口大小、经 CDP 每帧调一次画布的 `invalidate()` 并记 `requestAnimationFrame` 的间隔，显卡占用取 Windows 性能计数器 `\GPU Engine(*)\Utilization Percentage`。第一段用入库的端到端测试能重现，前提是机器上有别的程序在抢显卡。

**怎么看这件事。** 拖动预览自己的开销小而且稳定。记了显卡占用的那几次，掉帧都出在别的程序占显卡的时候，窗口越大越容易掉；没有记的那几次（3.2）不知道是什么原因。这是这台开发机的情况，R1 是什么情况不知道：R1 的屏如果是 60 Hz，每帧的时间多出三分之二；R1 的显卡如果更弱，或者用户机器上也开着吃显卡的程序，就可能更糟。**所以这一项要在 R1 上量过才能下结论，量的时候要用最大化的窗口、拖得足够久（至少几十秒），并且记下同时在跑的程序。**

### 3.5 对着通过线

| 通过线 | 结果 |
|---|---|
| 在 R1 上，5000 个对象的页面和 300 dpi 整页扫描件，拖动时帧时间 P95 不超过 16.7 ms | **R1 上没有量。** 开发机上：拖 40 秒，整段的 P95 在所有情况下都是 10.1 ms；按 2 秒一段看，有的段 P95 是 20 ms（大窗口下别的程序抢显卡的时候；默认窗口下也见过几次，原因没有记录） |
| 带混合模式、透明度组的对象，预览与最终效果有细微差别，可以接受 | 透明度组、半透明：没有差别。混合模式：差别不细微（4.1） |

样本上的折扣：5000 个对象是色块，不是图纸；扫描件是画的。这两样对拖动中的帧间隔没有影响，对预览就绪的时间有影响。

### 3.6 顺带量到的：修改到重画完（V05 的指标）

同一批运行里，选中对象后用方向键来回微移 30 次，从按键到视口里的瓦片都换成新内容并画完一帧（量法同 V06 报告 12.4）：

| 窗口 | 缩放 | 这一页在视口里的瓦片 | 5000 个对象的页：中位数 / P95 / 最大 | 扫描页：中位数 / P95 / 最大 |
|---|---|---|---|---|
| 1440×900 | 63.7% | 12 | 67 / 80 / 91 ms | 56 / 72 / 79 ms |
| 1920×1040 | 72.7% | 20 | 85 / 107 / 107 ms | 84 / 94 / 96 ms |
| 2560×1400 | 104.8% | 35 | 144 / 168 / 182 ms | 135 / 149 / 151 ms |
| 3440×1400 | 104.8% | 35 | 137 / 186 / 192 ms | 135 / 159 / 161 ms |

- **150 ms 的线（《接口协议》第 10 节、方案第 7 节）在默认窗口下达到，窗口到 2560×1400 以上就超了。** V06 报告 12.4 写过“窗口更大、放得更大的时候瓦片更多”，这里是具体的数。
- 时间跟着瓦片数走（两种页面都是）。已知的原因有两个：每次修改把这一页在视口里的瓦片全部重画，不管改的是哪一小块；每块瓦片都重新打开一遍页面。各占多少没有拆开量。
- 能试的也是两条：`doc.changed` 带上改动的范围，界面只重画碰到的瓦片（挪一个小对象只碰一两块）；引擎让页面开着，不重复打开（这就碰到第 2 节说的事）。留给 V05，效果要量了才知道。
- 表里每格是一次运行、30 个样本。
- 默认窗口下各页的结果和 V06 报告 12.4 一致。离群的样本仍然有：3.2 那三批 60 次默认窗口的运行（1800 个样本）里，3 次各出现一个 182、313、385 ms 的样本，原因仍然没有查。

## 4. 预览和松手之后的画面差在哪里

方案 3.2 第 4 条只说了一种差别（混合模式、透明度组，“细微”）。实际有四种，下面按看得出来的程度排。前三种都在真实程序里拖过，截了拖动中和松手后的两张图比过，比的是对象落下去的那块区域里有多少像素不一样（任一通道差 8 级以上才算）；用的是临时脚本，没有入库，括号里是手工重现的办法。

### 4.1 带混合模式的对象：拖动中是另一个样子

对象层是把对象单独画在透明背景上，混合模式要混的底下那些内容不在这一层里，所以拖动中它是按“正常”模式叠上去的。

- 样本 `tests/corpus/synthetic/gs-blend-modes.pdf`，拖第二根竖条（Screen 模式；打开文件拖标着 `Scrn` 的那根就能看到）：页面上它本来是把底下的色带提亮，压在白纸上的部分看不见；一开始拖，它变成一根不透明的蓝紫色条；松手后变回去。对象区域里 **100% 的像素不一样，平均差 69 级**（共 255 级）。
- 这不是“细微差别”。《P0 技术验证计划》的通过线写的是“可以接受”，所以不算没达到，但方案 3.2 第 4 条的说法要改。
- 透明度组（`gs-transparency-group.pdf` 里的 Form XObject）和半透明对象（`gs-alpha.pdf` 里最上面的方块）没有差别：100% 缩放下，整个画布上两张图不一样的地方只有松手后才出现的 8 个控制点。这也说明对象层的透明度合成（1.1 的预乘）和位置在真实程序里是对的。

要不要处理，有三个选择，需要评审时定：照现在这样（方案原来的意思）；带混合模式的对象退回虚线框（引擎要在对象摘要里告诉界面哪些对象带混合模式）；底图不去掉这类对象、让引擎每帧重画（那就不是分层预览了）。

### 4.2 被别的对象压着的对象：拖动中浮到上面来

对象层总是画在底图上面。被拖的对象上面如果还压着别的对象，拖动中它会盖住它们，松手后回到原来的层级。

- 样本 `gs-alpha.pdf`，拖中间那个蓝色的半透明方块（它上面压着绿色的方块；按在它没被压住的地方拖）：两个方块重叠的地方，拖动中是蓝压绿，松手后是绿压蓝。对象区域里 49.7% 的像素不一样，平均差 53 级。
- 方案没有提到这一种。要做对，得再分一层：压在被拖对象上面的那些对象单独一层，画在对象层上面。瓦片多要一批，预览就绪更慢。没有做。

### 4.3 缩放不在整档上时：松手的一瞬间文字的边缘会变

瓦片是按固定的缩放档渲染的（每档差 √2 倍），视图的缩放不在档上时，画的时候再缩放一下。拖动中对象层挪的是整数个屏幕像素；松手后重画的瓦片里，对象挪的不是整数个瓦片像素，抗锯齿出来的边缘就和挪过去的那张位图不完全一样。

- 灰度色块样本的标题文字，拖 (40, 24) 像素：

| 视图缩放 | 是不是整档 | 对象区域里不一样的像素 | 这些像素平均差多少 |
|---|---|---|---|
| 100% | 是 | 0.0% | — |
| 200% | 是 | 1.2% | — |
| 150% | 不是 | 20.8% | 17 级 |
| 175%（“适合页面”） | 不是 | 51.2% | 31 级 |

- 把后一张图上下左右各挪 1–2 个像素再比，都不会更接近：位置没有错，差的是边缘的深浅。放大了看，两张图上的字在同一个位置，一张略粗一点。
- 纯色块没有这个差别（0%）；扫描页的图有（端到端测试里 24.5%，图里的噪声对重采样很敏感）。
- “适合页面”“适合宽度”几乎总是不在整档上，所以平常都会碰到。看上去是松手时文字轻微地闪一下。要消掉它，得让瓦片按视图实际的缩放渲染（不在画的时候再缩放），那是瓦片画布的事，不在这一项里。

### 4.4 其他

- **拖出页面的部分**：预览里对象拖到页面外面的部分照样画出来；松手后页面外面什么也没有（瓦片只管页面之内）。
- **缩放（拖控制点）的预览是把位图拉伸**，放大时发虚，松手后重画才清楚。
- **两层还没到齐就松手**：没有预览，对象从原处跳到新位置（和原来一样）。

## 5. 和《接口协议》的出入

协议 6.3 的 `render.layered` 是“一次请求，返回两层位图”，参数 `{docId, pageId, objectIds, scale, viewport}`。实现里没有这个方法，是给 `render.tiles` 加了 `layer`。理由：

- 位图在协议里只有一种传法——瓦片进共享内存槽位、`render.tileReady` 通知。`render.layered` “返回两层位图”，得为它另定一种传法，或者拆成瓦片，那就和 `render.tiles` 是一回事了。
- 两层要的范围不一样：底图是整个视口，对象层只是对象周围。一个 `viewport` 参数表达不了。
- 拖动中视口挪了要补底图，补的也是瓦片。

建议协议按实现改：去掉 `render.layered`，在 `render.tiles` 的参数里加 `layer`。同时要写明的几点：

- 对象层的像素是没有预乘的 BGRA，背景全透明；底图和平常的瓦片一样是不透明的。
- `objectIds` 里有不在这一页上的对象：现在是应答照给、瓦片不渲染、也没有任何通知，界面只能等超时（30 秒）。这是“渲染失败时引擎不发消息”的老问题（V06 报告 11.9），协议要补一个失败的通知。
- 带 `layer` 的请求不算视图变化，不记进恢复文件。
- `layer` 的优先级：方案 3.3 的队列里“拖动分层”排在可见瓦片之后、预取之前。引擎现在没有优先级队列，各类请求先来先渲染。
- 9.2 的清单里 `MAG_RenderPageFiltered` 标着“P0 原型，P1 定稿”，按第 2 节改成“页面常开时才需要”。

按《工程规范》，协议文档要先评审再改，这里只记建议，文档本身没有动。

## 7. 没做的、没验的

- **R1 上没有量。**
- 样本是画的：5000 个色块，不是图纸；“扫描件”不是真的扫描件。
- 高分屏（缩放 150%、200%）没有试，画布的像素数会是现在的 2–4 倍。
- 拖动中滚轮平移、缩放：有单元测试，真实程序里没有专门试。
- 旋转过的页、可见区域不从原点开始的页：坐标换算是现成的（V12 报告 11.1），拖动预览在这样的页上没有专门试。
- 多选拖动：实现支持（一页之内、500 个对象以内），真实程序里只试过单个对象。
- 压在被拖对象上面的对象单独一层（4.2）、带混合模式的对象怎么办（4.1）：没有做，等评审。
- 引擎的渲染优先级和可打断的渲染（方案 3.3）：没有做。拖动开始时如果引擎正忙着别的（后台保真校验一页是 13–41 ms，V06 报告 12.3），两层瓦片要等。
- 预览就绪的时间在大窗口下是 95–165 ms。可能缩短它的办法（底图先用已有的整页瓦片顶着、只等对象周围的几块；页面常开）没有做，也没有试。
- 3.4 的测量脚本没有入库。V05 要量平移、缩放的帧间隔时，应该把它整理成入库的工具。
