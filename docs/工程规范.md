## 1. 仓库

| 仓库 | 内容 |
|---|---|
| `magpdf` | 主仓库，目录结构见方案第 12 节 |
| `magpdf-pdfium` | PDFium 分支，以子模块挂在 `third_party/pdfium`（第 6 节） |
| `magpdf-corpus` | 测试文件库，用 Git LFS 或企业网盘，访问受控（《测试样本收集与脱敏规范》第 5 节） |
| Zint、ZXing-C++ | 以子模块挂在 `third_party/`，指向官方仓库，锁定到发布标签 |

- 代码托管平台按公司现有条件选，要求支持 PR 评审、CI 和大文件存储。
- 主仓库根目录放 `CODEOWNERS`，按目录指定负责的组，PR 自动请对应的人评审。

## 2. 分支与提交

- **主干开发**：`main` 始终能构建、测试全部通过。功能分支命名 `feat/…`、`fix/…`，尽量 3 天内合入，通过 PR 以压缩合并（squash）方式合入。
- **发布分支**：发布准备开始时从 `main` 拉出 `release/1.0`，只接收缺陷修复；修复先合入 `main`，再拣选（cherry-pick）到发布分支。
- **提交信息**：类型前缀加描述，中英文均可，例如 `fix(engine): 修复 TJ 字距写回丢失`，并关联缺陷或任务编号。类型用 `feat`、`fix`、`perf`、`refactor`、`test`、`docs`、`build`、`chore`。
- **功能开关**：没做完的功能在主干上用编译开关（Rust feature 或构建变量）隐藏，不长期维护功能分支。

## 3. 代码评审

- 每个 PR 至少 1 人评审。以下内容要由对应负责人评审：

| 内容 | 评审人 |
|---|---|
| PDFium 分支、`MAG_*` 接口、文件私有数据格式 | 引擎组组长 |
| 接口协议 | 引擎组、界面组各 1 人 |
| 安装、签名、自动更新、授权校验 | 测试与工程组，加引擎组组长 |
| 界面外观和交互 | 界面组设计人员 |

- PR 描述写清：改了什么、为什么改、怎么测的；界面改动附截图；是否影响文件格式或协议。
- 工作日 24 小时内给出评审意见。
- 单个 PR 的实质改动建议不超过 400 行，生成的代码和测试数据不算。

## 4. 编码规范

| 语言 | 规范与工具 |
|---|---|
| Rust | edition 2024；`rustfmt` 默认配置；`clippy` 开启 `-D warnings`。库代码用 `thiserror` 定义错误，应用层用 `anyhow`；库代码里不用 `unwrap`、`expect`（测试除外）。`unsafe` 只允许出现在 `pdfium-sys` 和调用 Windows 接口的模块，每处写 `// SAFETY:` 说明成立的前提 |
| TypeScript | 开启 `strict`；ESLint + Prettier；React 函数组件；状态用 Zustand（方案 3.4）；不用 `any`，确实需要时注明原因 |
| C++（PDFium 分支） | 遵循上游代码风格，`clang-format` 用上游配置；新代码放独立文件；修上游缺陷时按上游要求带测试 |
| 着色器 | GLSL ES 3.0（WebGL2） |

通用要求：
- **日志**：Rust 用 `tracing` 输出结构化日志。日志里不得出现文档内容：不记录文档文字、图片、文件名和路径，需要区分文件时记录文件路径的哈希（方案 13.4）。
- **用户可见的错误**：文案统一在一处定义，与《接口协议》第 8 节的错误码对应。
- **界面文字**：集中放在资源文件里。v1.0 只有简体中文，但不在代码里写死，以后好加其他语言。
- **注释**：只写代码本身表达不了的约束和原因。

## 5. 依赖管理

- 新增第三方依赖要在 PR 里写明用途和许可证，由第 3 节的评审人确认。
- **许可证白名单**：MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、Zlib、FreeType License、OFL-1.1、Unicode License；MPL-2.0 只允许以未修改的独立文件形式使用。
- **禁止**进入安装包：GPL、LGPL、AGPL、SSPL，以及没有许可证的代码。只在测试中使用、不随产品分发的工具不受此限（如 MuPDF，见《开源许可与合规清单》）。
- **工具**：Rust 依赖用 `cargo-deny` 检查许可证、重复版本和安全公告；npm 依赖用许可证扫描工具；CI 检查不通过即不能合入。
- **锁定版本**：`Cargo.lock`、`pnpm-lock.yaml` 提交入库；C/C++ 依赖按标签锁定子模块。
- **升级**：每月集中升级一次依赖；安全修复随时升级。

## 6. PDFium 分支维护

- **分支**：`magpdf-pdfium` 仓库里，`upstream` 分支镜像上游，`mag/main` 是我们的分支。
- **补丁组织**：每个修复或扩展是一个独立提交，提交信息前加标记：
  - `[upstream-candidate]`：可以提交给上游的缺陷修复，如生成器修复；
  - `[mag-ext]`：`MAG_*` 扩展接口；
  - `[mag-local]`：只有我们需要的改动，尽量少。
- **扩展接口**：声明放 `public/mag_*.h`，实现放独立源文件，不改上游现有逻辑（方案 15）。
- **提交上游**：`[upstream-candidate]` 的修复按上游流程，经 Gerrit 代码评审提交。提交前公司要先签 Google 的企业贡献者许可协议。上游合入后，下次同步时删掉本地版本。
- **同步上游**：每季度一次，把 `mag/main` 变基到上游最新的 `chromium/NNNN` 稳定分支。同步后跑一周全量往返测试和模糊测试，没有退步再更新主仓库的子模块。
- **安全修复**：上游有涉及 PDFium 的安全修复时，两周内单独合入，不等季度同步。
- **构建**：引擎组维护构建脚本，CI 产出预编译库（含调试符号）供其他组使用（方案 12）。

## 7. CI/CD

| 流水线 | 触发 | 内容 | 时长目标 |
|---|---|---|---|
| PR | 每次推送 | 构建（用 PDFium 预编译库）、代码检查、单元测试、契约测试、往返和编辑测试子集、许可证检查 | 20 分钟内 |
| PDFium | `magpdf-pdfium` 有新提交 | 全量构建、C++ 测试、产出预编译库 | 60 分钟内 |
| 每晚 | 每天 | 往返和编辑测试全量、第二渲染器比对、性能基准（R1）、端到端测试、打印比对、模糊测试结果汇总 | 当晚跑完 |
| 发布 | 打版本标签 | 构建安装包、签名、生成第三方许可声明、上传（《发布手册》） | — |

- 构建产物：主干每日构建保留 30 天，发布版本永久保留。
- 调试符号：每个发布版本的 PDB 文件归档，用于分析用户发来的崩溃转储，不随安装包分发。

## 8. 版本号

| 对象 | 规则 |
|---|---|
| 软件 | 语义化版本 `主.次.修订`，如 `1.0.0`；Beta 为 `1.0.0-beta.1` |
| 接口协议 | 整数，不兼容修改时加 1（《接口协议》第 4 节） |
| 文件私有数据 | 文档级 `/Fmt`、组件级 `/Ver`（《文件私有数据格式规范》第 8 节） |
| OCR 模型 | 记录模型名称和版本，写进 OCR 缓存（《文件私有数据格式规范》9.5） |

## 9. 文档

- 方案和配套文档放在 `docs/`，用 Markdown 写，改动走 PR，和代码一样评审。
- **修改协议、格式、组件参数**：先改《接口协议》《文件私有数据格式规范》《组件参数定义》并评审，再改代码。
- **架构决策记录（ADR）**：重要的技术决定（技术选型变更、协议或格式的重大修改、P0 复盘结论）各写一页，放 `docs/adr/`，按编号递增，内容包括背景、决定、理由和后果。

## 10. 完成的定义

一个功能或修复要满足以下全部条件才算完成：
1. 代码已合入 `main`，CI 全部通过。
2. 有对应的自动化测试；修复缺陷的有回归测试。
3. 涉及界面的，符合《交互设计》和方案 8.3 的视觉规范，设计人员确认过。
4. 涉及协议、格式、组件参数的，相关文档已更新。
5. 用户可见的变化已写进《用户手册》，或记入用户手册的待办。
6. 没有新增许可证问题。

## 11. 安全与保密

- 代码签名证书、授权文件签名私钥、更新包签名私钥都不进代码仓库，保管和使用见《发布手册》和《授权与定价方案》。
- 开发机开启全盘加密。
- 测试样本和真实单证不得上传到任何外部服务，包括 AI 工具；代码只在公司批准的开发工具中使用。

## 12. 工作节奏

- 两周一个迭代：迭代计划会（1 小时）、每日站会（15 分钟）、迭代评审和回顾（1 小时）。
- 每个阶段（P0–P3）结束时开阶段评审，对照方案 14.3 的退出标准逐条判定。
- 任务和缺陷管理工具按公司现有条件选定，要求支持看板、自定义缺陷字段，并能和代码仓库关联。
