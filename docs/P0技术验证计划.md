## 1. P0 要回答的问题

1. PDFium 分支修复内容流生成器后，往返测试能否达标（办公类文档 ≥ 98%，设计软件导出 ≥ 90%）？达不到时走哪条退路（方案 2.1、2.4）？
2. 原生进程架构（Tauri 主进程 + 引擎进程 + 共享内存）能否达到第 7 节的性能指标？
3. 中文"改一行字"能否端到端跑通：塑形、子集化、嵌入，改后可复制、可搜索？
4. PP-OCRv5 在自有样本上的准确率和速度是否达标？英文单证用哪个模型？GPU 加速值不值得做？
5. 背景修补（v1.1 功能）原型是否可行？
6. 用户访谈的结论是否支持第 11 节的高频工作和组件优先级，包括套打？
7. 与 Foxit SDK 对比，PDFium 分支是否仍是更好的选择？
8. 内容流的读写改由我们自己实现（PDFium 仍负责解析和渲染），能否做到没改过的对象原样保留？效果是否优于修补 PDFium 的生成器？

P0 复盘会根据这些答案决定能否按原方案进入 P1，并把方案和配套文档定稿（第 6 节）。

### 3.2 各项内容

**V01 原生构建与预编译库**
- 内容：在 Windows x64 上用上游推荐的流程（depot_tools、gn、ninja）构建 PDFium 分支；Rust 绑定 `pdfium-sys` 能调用；CI 每次提交产出预编译库，非引擎组的人下载即可编译运行（方案 12）。
- 通过线：**在 CI 上**全新构建不超过 30 分钟（测量条件：`windows-latest` 4 vCPU、无缓存、含 `gclient sync`；热缓存 ≤ 20 分钟作为日常目标）；其他组成员按说明 30 分钟内跑通示例程序。
- 进展：本机全新构建 1 分 41 秒，10 个样本渲染与预编译库逐字节相同（V01 报告）；`magpdf-pdfium` 建仓后补 CI 实测数据。

**V02 原版 PDFium 往返测试基线**
- 方法：对测试文件库的每一页，解析后把所有对象标记为已修改，重新生成内容流并保存，再与原文件分别按 2 倍分辨率（144 dpi）渲染比对（方案 2.1、13.2）。
- 判定"无差异"：任一颜色通道差值大于 24（0–255）的像素算差异像素；差异像素少于页面面积的 0.01%，且最大的连通差异区域不超过 16 个像素，算无差异。W1 先用"生成器不做任何改动"的页面校准噪声，必要时调整阈值，调整后全程不再改。
- 产出：基线报告，按来源分类统计无差异比例，并扣除没有页面对象的页另报一列；按缺陷类型（颜色、渐变、扩展图形状态、文字字距、Type3、层级、其他）统计影响页数，作为 V03 的修复顺序依据。
- 判定方法补充：像素比对看不出"颜色空间被换算成等价 RGB"、叠印和文字状态丢失，还要用 qpdf 或 pikepdf，或用操作符级比对工具，比较往返前后的颜色、状态操作符和绘制事件；这类页面计入差异页（V14 4.4、V02）。
- 自制样本（`tests/corpus/synthetic/`）作为往返测试的烟雾子集，每次 PR 必跑（V14）。

**V03 修复内容流生成器**
- 修复项（方案 2.1），顺序按 V02 报告 6.1（影响页数 × 画面破坏程度）：
  1. `Tc`、`Tw` 写出（`TJ` 上游已修，补回归测试）；办公软件导出的文字大量使用，最优先。（2026-11-09 已修复，见 V03 报告）
  2. 颜色空间：灰度、CMYK、ICCBased、Separation、DeviceN、Indexed、Lab、Pattern 写出正确的颜色操作符，ICCBased 不得退化为 Alternate 或 DeviceRGB，专色 `/None` 保持不画。（2026-11-09 已修复，见 V03 报告）
  3. 文字裁剪模式（`Tr` 4–7）：合成样本证实裁剪整体丢失，一旦出现就是整页破坏，优先级高于 Type3 和 ExtGState。（2026-11-09 已修复，见 V03 报告）
  4. Type3 字体的文字原样保留，不再留下未闭合的 `q`、`BT`。（2026-11-09 修了后一半：不再留下未闭合块；文字本身仍被跳过）
  5. 扩展图形状态写全：软蒙版、叠印（`OP/op/OPM`）、文字挖空。
  6. 渐变（`sh`）和内联图像不再被跳过。
  7. 共享内容流的 copy-on-write：生成前检查流对象的引用计数，或由上层先拆分（Form XObject 被多页引用时同样需要）。
  8. 新对象和调整层级后的对象写进正确的内容流，必要时合并内容流。
- 同时落实方案 2.3 的生成规则：只写状态变化、共用剪切路径的对象合组、文字裁剪块整体保留、标记内容嵌套不乱。
- 方法：每修完一项重跑 V02 全量，补单元测试和模糊测试目标。
- 通过线：办公类文档 ≥ 98%，设计软件导出 ≥ 90%（方案 14.3）；剩下的差异页逐页分类说明原因。
- 上游：每项修复整理成可提交上游的补丁，P0 内至少提交 2 个。
- 未达标时：差异来自生成器的，继续修，P1 前两周作缓冲；差异来自解析阶段已经丢失的信息（对象模型里没有），按方案 2.1 的退路，结合 V13 评估自研解析层或商用 SDK。

**V04 分层渲染与拖动预览原型**
- 内容：实现 `MAG_RenderPageFiltered`（《接口协议》9.3）；界面用 WebGL2 把对象层叠在底图上做变换，拖动过程不发请求（方案 3.2）。
- 通过线：在 R1 上，5000 个对象的页面和 300 dpi 整页扫描件，拖动时帧时间 P95 不超过 16.7 ms（60 fps）。带混合模式、透明度组的对象，预览与最终效果有细微差别，可以接受（方案 3.2 第 4 条）。

**V05 渲染与编辑性能**
- 指标（方案第 7 节）：

| 指标 | 目标 | 样本 |
|---|---|---|
| 300 页文档出首屏 | < 1.5 s | 300 页的报表系统导出文件 |
| 选中、拖动 | 60 fps | 同 V04 |
| 单对象修改到重绘完成 | < 150 ms | A4、5000 个对象的图纸 |
| 扫描页 OCR（移动版模型，CPU） | < 2 s/页 | 见 V09 |

- 批量生成 1000 张标签的指标在 P2 实测，P0 不测。
- 未达标时：给出优化方案和预计收益，方案 14.3 允许"有明确的优化方案"时进入 P1。

**V06 进程架构与位图传输原型**
- 内容：主进程启动引擎进程；命名管道传 JSON-RPC 消息，共享内存传瓦片（《接口协议》第 3 节）；结束引擎进程后界面保持打开，自动重启并从恢复文件恢复（方案 9.3，演示级实现）。
- 通过线：从共享内存取一张瓦片小于 5 ms；1000 次小请求的往返 P95 小于 2 ms；强制结束引擎后 5 秒内恢复显示。
- 同时测 JSON 编解码在总耗时中的占比，作为《接口协议》待定项 I1 的依据。
- 进展：开发机上取瓦片 P95 0.35 ms、`session.ping` 往返 P95 42.5 µs、结束引擎到新引擎恢复文档 62.7 ms（V06 报告）。三项都只测到主进程为止，界面一段和参考机 R1 上的复测要等 Tauri 外壳。

**V07 文字块识别原型**
- 内容：把字符按基线、字体、间距聚成行和段落，推断对齐方式和行距（方案 5.1）。
- 样本：Word、WPS 导出的 100 页，货代单证 50 页，按《V07-标注格式》标注行和段落（以 PDFium 字符索引为单位）。
- 目标值：按字符一致率计，行的聚类正确率 ≥ 98%，段落 ≥ 90%。

**V08 "改一行字"端到端**

- 样本：中文合同 20 份、英文单证 20 份，每份改 3 处。
- 通过线：三级回退各有至少 5 例成功；修改后在 Acrobat Reader、Chrome、WPS 中显示一致，能复制、能搜索，没有乱码；新增 10 个汉字时文件增加不超过 50 KB。

**V17 自研无损内容流读写层原型（与 V03 对比）**
- 思路（方案 2.1 的备选做法）：PDFium 仍负责解析、渲染和命中测试，是唯一的几何来源；内容流的读写由我们用 Rust 实现。读入时保留原内容流里每个操作符及其字节位置，并按 PDFium 建立页面对象的规则，把操作符和页面对象按顺序一一对应（每个路径绘制、`Do`、`sh`、内联图像、文字输出指令对应一个对象）。保存时只重写改过的对象，其余字节原样保留；改过的和新增的对象由自己的序列化代码写出，不经过 PDFium 的生成器。
- 参考代码：可以参考、移植 PDFium（BSD-3 / Apache-2.0）和 pdf.js（Apache-2.0）的代码，保留原版权声明；MuPDF 是 AGPL 许可，不参考它的源码。
- 对比方法，与 V03 用同一批样本：
  1. 不修改任何对象直接保存：内容流应与原文件逐字节相同。
  2. 随机修改 5% 的对象（移动、改色、删除）后保存，与原文件渲染比对，判定规则同 V02。
  3. 统计操作符和对象对不上的页面比例；对不上的页面退回整条内容流重写，再做保真校验。
  4. 记录读入和保存的耗时，以及修改后文件的字节变化量。
- 目标值：对不上的页面不超过 2%；不修改时逐字节相同的内容流 ≥ 99%；随机修改后的无差异页面比例不低于 V03。
- 人手：引擎组 1 人负责，文字组协助文字类操作符的对应。
- 产出：与 V03 的对比报告，P0 复盘时据此决定 P1 用哪种做法（第 6 节）。

## 6. P0 复盘会

- 时间：W6 最后两天。参加：全体成员和方案评审人。
- 议程：各验证项结果（每项 10 分钟）→ 对照方案 14.3 的 P0 退出标准逐条判定 → 复核方案第 15 节的风险 → 按实测重估附录 A1 的工作量 → 作出决定。

| 结果 | 决定 |
|---|---|
| 全部达标 | 按原计划进入 P1 |
| 往返测试未达标，但差异都在生成器内，且有修复计划 | 进入 P1；修复排进 P1 前两周，P1 结束时再验 |
| 往返测试未达标，且有信息在解析阶段就已丢失 | 暂不进入 P1；按方案 2.1 的退路，结合 V13 评估自研解析层或商用 SDK，一周内给出方案修订 |
| V17 达到目标值，且随机修改后的无差异比例高于 V03 | P1 采用自研内容流读写层：PDFium 只负责解析、渲染和命中测试，`MAG_*` 扩展照常；V03 的修复中只保留整条重写时仍需要的部分 |
| V17 未达到目标值，或不比 V03 好 | P1 继续修补 PDFium 的生成器；V17 的原型代码和报告存档，v1.0 之后再评估 |
| 性能未达标，但有明确的优化方案 | 进入 P1，优化项列入 P1 计划 |
| OCR 未达标 | 调整模型策略，例如把服务器版模型改为推荐下载；不影响进入 P1 |
| 访谈结论改变了优先级 | 调整 P1–P3 的范围（方案 14.2） |

产出：复盘纪要；方案 v1.0 定稿；配套文档按结论修订后定稿；P1 详细计划。
