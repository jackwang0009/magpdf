P1 起引擎组和界面组并行开发，双方以本协议为准。协议的类型定义写在 Rust 里，由构建生成 TypeScript 类型（`packages/protocol`，方案 3.1）；本文是人读版本，改协议先改本文。

## 1. 范围

| 边界 | 通道 | 本文章节 |
|---|---|---|
| 界面进程 ↔ 主进程 | Tauri 命令和事件；位图走自定义协议 `magpdf://` | 2、3 |
| 主进程 ↔ 引擎进程、任务进程 | 命名管道（消息）+ 共享内存（位图） | 2、3 |
| 引擎服务 ↔ PDFium 分支 | C 接口，`MAG_*` 扩展 | 9 |

## 2. 分层与转发

```
界面进程 ──Tauri invoke / 事件──▶ 主进程 ──命名管道──▶ 引擎进程
界面进程 ◀──magpdf:// 取位图──── 主进程 ◀──共享内存── 引擎进程
                                     └──命名管道──▶ 任务进程（P2 起，按需启动）
```

- 文档类请求，主进程原样转发给引擎，不解析业务字段。
- 模板库、组件库、印章库、偏好设置、文件对话框、更新检查由主进程自己处理（方案 3.1）。
- 引擎重启时，未完成的请求统一返回 `E_ENGINE_RESTARTED`；界面等收到 `engine.restored` 后再重试。

## 3. 消息与传输

### 3.1 消息格式

采用 JSON-RPC 2.0 的格式：

```json
{ "jsonrpc": "2.0", "id": 17, "method": "edit.transform",
  "params": { "docId": 1, "baseVersion": 42, "ids": [301, 302], "matrix": [1, 0, 0, 1, 12.5, 0], "clipFollows": true } }

{ "jsonrpc": "2.0", "id": 17, "result": { "version": 43 } }

{ "jsonrpc": "2.0", "method": "doc.changed", "params": { "docId": 1, "version": 43, "changes": [ … ] } }
```

- 请求带 `id`，响应带同一个 `id`，内容是 `result` 或 `error`（第 8 节）；事件没有 `id`。
- 字段名用小驼峰。
- **几何量**一律用 PDF 用户空间：单位 pt，坐标系与内容流相同（未经页面旋转）。页面的 `/Rotate`、裁剪框偏移和屏幕单位换算由界面负责。
- **矩阵**写成 6 个数 `[a, b, c, d, e, f]`。
- **ID** 是 JavaScript 安全整数（小于 2^53）。
- **时间**用 ISO 8601 字符串。

### 3.2 命名管道

- 管道名 `\\.\pipe\magpdf-<主进程 PID>-<随机串>`，访问控制只允许当前用户。
- 帧格式：4 字节小端长度 + UTF-8 JSON。单帧上限 64 MB，位图等大数据走共享内存。
- 引擎的通信线程和 PDFium 线程分开（方案 3.3），PDFium 在忙时通信线程仍能应答心跳。

### 3.3 位图

- 引擎为每个会话建一块命名共享内存 `Local\MagPDF-<会话 ID>-tiles`，切成固定大小的槽位，每个槽位放一张 512×512 设备像素的瓦片（方案 7），像素格式 BGRA、预乘透明度。
- 瓦片渲染完成后，引擎发 `render.tileReady` 事件，带槽位号和代数（槽位每复用一次代数加 1）。
- 界面用 `fetch("magpdf://tile/<槽位>/<代数>")` 取原始像素。主进程从共享内存读出后返回；代数对不上（槽位已被复用）时返回 410，界面重新请求渲染。
- 界面把像素直接上传成 WebGL 纹理，在着色器里交换 R、B 通道，不做 PNG 编解码。以后需要时可改用 WebView2 的 SharedBuffer 做到零拷贝（方案 3.1）。

## 4. 会话

| 方法 | 说明 |
|---|---|
| `session.hello` | 主进程启动引擎后发的第一条消息。参数 `{protocol, appVersion, locale, userDataDir, cacheDir}`；返回 `{protocol, engineVersion, pdfiumRevision, capabilities}`。协议版本不一致时，主进程提示"安装文件不完整，请重新安装" |
| `session.ping` | 主进程每 2 秒发一次；5 秒没有响应即判定引擎挂死，结束进程后重启（方案 9.3） |
| `session.shutdown` | 正常退出 |

`capabilities` 列出可选能力，如 `ocr.server`（已安装高精度 OCR 模型）、`gpu.windowsml`、`gpu.directml`，界面据此显示或隐藏相应选项。

## 5. 标识与快照

### 5.1 标识

| 标识 | 说明 |
|---|---|
| `docId` | 打开文档时分配，会话内唯一 |
| `pageId` | 页面在会话内的稳定 ID，页面重排后不变；页码另用 `index` 表示 |
| `objectId` | 页面对象的稳定 ID，编辑后不变，删除后不复用 |
| `compId` | 组件 ID；组件包含哪些对象在快照里给出 |
| `groupId` | 编组 ID |
| `jobId` | 任务 ID |
| `blockId` | 正在编辑的文字块 ID |

这些 ID 只在一次会话内有效，不写进文件（方案 4.1：内容流里的对象没有稳定编号）。引擎重启后全部重新分配，界面收到 `engine.restored` 后丢弃旧快照重新拉取。

### 5.2 文档版本

- 每个文档有版本号 `version`，从 0 开始，每条成功的修改命令加 1；撤销、重做也各加 1。
- 修改类请求都带 `baseVersion`，和当前版本不一致时返回 `E_VERSION_CONFLICT`。界面先补上缺的 `doc.changed`，或重新拉快照，再重试。
- 引擎按版本顺序推送 `doc.changed`；界面发现版本不连续，就对受影响的页面调用 `doc.snapshot`（方案 3.1）。
- 命令是原子的：失败时文档和版本号都不变。

### 5.3 快照数据

```ts
interface DocInfo {
  docId: number; path: string | null; title: string; version: number; pageCount: number;
  dirty: boolean; signed: boolean; encrypted: boolean; pdfVersion: string;
  permissions: { edit: boolean; print: "none" | "low" | "high"; copy: boolean };
  template?: { kind: "normal" | "overlay"; name: string; rev: number };
}

interface PageInfo {
  pageId: number; index: number; mediaBox: Rect; cropBox: Rect; rotate: 0 | 90 | 180 | 270;
  scan: "no" | "yes" | "yesWithText";          // 方案 6.1
  fidelity: "pending" | "ok" | "overlayOnly";   // 方案 2.3
  fidelityReason?: string; objectCount: number;
}

interface ObjectSummary {
  id: number; kind: "text" | "path" | "image" | "shading" | "form" | "component" | "group" | "annot";
  bbox: Rect; quad?: Quad; z: number; parent?: number; children?: number[];
  name?: string; locked: boolean; ocg?: { name: string; print: boolean };
  comp?: { type: string; summary: string; hashOk: boolean; checks: Check[] };
  text?: { preview: string; editable: boolean; reason?: string };
}

interface Check { severity: "error" | "warning"; key?: string; message: string }
```

对象很多的页面（方案 4.3），`obj.list` 分页返回，单次最多 2000 条。

## 6. 方法

下表"改"一栏为"是"的方法会修改文档：必须带 `baseVersion`，成功后返回新的 `version`，并推送 `doc.changed`。

### 6.1 文档

| 方法 | 改 | 说明 |
|---|---|---|
| `doc.open` | 否 | 参数 `{path, password?}`，返回 `DocInfo`。可能的错误：文件不存在、需要密码、密码错误、文件损坏且修复失败、不支持（如纯 XFA 表单，方案 1.3） |
| `doc.newFromTemplate` | 否 | 参数 `{templatePath}`，返回一份未命名副本；`onCreate` 模式的日期组件刷新为当天 |
| `doc.close` | 否 | 参数 `{docId, discard}` |
| `doc.save` | 否 | 参数 `{docId, mode: "incremental" \| "full", path?}`。先写临时文件再替换（方案 9.1）；已签名文档要求完整重写时返回 `E_SIGNED_FULL_SAVE`（方案 9.2） |
| `doc.snapshot` | 否 | 参数 `{docId, pageIds?}`，返回 `{version, pages, objects}`，`objects` 只含顶层对象 |
| `doc.unlock` | 否 | 参数 `{docId, ownerPassword}`，输入权限密码后返回新的 `permissions` |
| `doc.export` | 否 | 参数 `{docId, pageIds, format: "png" \| "jpeg", dpi, quality?}`（P3） |

## 7. 事件

| 事件 | 发出方 | 时机与内容 |
|---|---|---|
| `doc.changed` | 引擎 | 修改命令成功后：`{docId, version, changes: [{pageId, added, removed, modified}], pagesChanged}` |
| `doc.dirtyChanged` | 引擎 | 文档"已修改"状态变化 |
| `doc.saved` | 引擎 | 保存完成：`{docId, path, mode}` |
| `render.tileReady` | 引擎 | `{requestId, docId, pageId, scale, x, y, version, slot, generation}` |
| `fidelity.result` | 引擎 | `{docId, pageId, status, reason?}` |
| `ocr.progress` | 引擎 | `{docId, done, total, currentPageId}` |
| `ocr.pageDone` | 引擎 | `{docId, pageId, lineCount, lowConfidenceCount}` |
| `job.progress` | 任务进程 | `{jobId, done, total, message}` |
| `job.done` | 任务进程 | `{jobId, result}`，`result` 视任务而定，如新文档路径 |
| `job.failed` | 任务进程 | `{jobId, error}` |
| `warning` | 引擎 | `{docId, code, message, objectIds?}`，如"字体已替换"、"保存后签名将显示为签名后已修改" |
| `engine.busy` | 引擎 | PDFium 线程上单个任务超过 30 秒，界面在状态栏显示"正在处理…" |
| `engine.restarting` | 主进程 | 引擎崩溃，正在重启 |
| `engine.restored` | 主进程 | `{docIds}`，已从恢复文件重新载入的文档（方案 9.3） |

## 8. 错误

错误对象为 `{code, message, data?}`。`message` 是可以直接显示给用户的中文；`data` 放结构化信息，如组件参数的 `Check[]`。

| 码 | 名称 | 含义 | 界面处理 |
|---|---|---|---|
| 1001 | `E_PROTOCOL` | 协议版本不符或消息格式错误 | 提示重新安装 |

## 9. `MAG_*` 扩展接口（PDFium 分支）

### 9.1 约定

- 风格与 PDFium 公共接口一致（`FPDF_EXPORT … FPDF_CALLCONV`），声明放在独立头文件 `public/mag_edit.h`，实现放在独立源文件，不改现有逻辑（方案 15）。
- 生成器的缺陷修复不属于扩展接口，直接改上游代码并尽量提交回上游（方案 2.1）。
- 能提交上游的接口按上游命名风格提交；合入后，`MAG_` 版本改为调用上游接口，再逐步废弃。
